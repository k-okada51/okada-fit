# データフロー（DFD） — okada-fit

> **目的**: システムの**静的な地図**（データがどこから来て・どう変換され・どこへ出るか）を Level0（コンテキスト）／Level1（主要プロセス）で示す。時系列の動きは扱わない。
> **書き方**:（記入例は example-suido-fax の対応ファイル参照）作図方針・記法凡例・チェックリストは本ファイル内に記載。**ビジネス（人・意思決定・成果）を第一級で含める**（利用者・承認者・経営などのアクターと業務上の意思決定/成果フロー）。時系列の動きはDFDでなくシーケンス図／`03_ドメインイベント.md` で。

> 📖 ID（`FEAT-` `NFR-` `RULE-` 等）の意味は [ID早見表](../00_ID早見表.md) を参照。

## 1. 記法凡例
> 📝 ここに本書で用いる記法を記載（`DFD_テンプレート.md §記法凡例` を踏襲）。{要素／意味／Mermaid形状}

| 要素 | 意味 | Mermaid形状（例） |
|---|---|---|
| 外部エンティティ | システム外の相手（人・組織・外部システム） | `([人/組織])` `[[外部システム]]` |
| プロセス | システム内の処理（P1, P2 …と採番） | `((処理))` |

| データフロー | 流れる**業務データ**（矢印ラベルに明記） | `-- 業務データ -->` |

## 4. データストア一覧
> 📝 ここに登場するデータストアを記載。物理DB・DMと対応づける。{ID／データストア／物理／所有・公開／主内容／対応DM-ID}

| ID | データストア | 物理 | 所有/公開 | 主内容 | 対応DM |
|---|---|---|---|---|---|
| D1 | 器具・部位タグ | Supabase/PostgreSQL | 岡田さん/非公開 | ジム・器具・種目（部位:胸/背中/脚/肩/腕） | DM-02(gyms)/DM-04(training_menus)/DM-05(training_machines) |
| D2 | トレーニング記録 | 同上 | 岡田さん/非公開 | 入館・実施日・種目・実行済 | DM-03(gym_visits)/DM-06(training_sessions)/DM-07(training_session_details) |
| D3 | プロフィール | 同上 | 岡田さん/非公開 | 体重、目標トレーニング回数（必要タンパク質量は体重×2gで算出） | DM-01(users) |
| D4 | 食事マスタ | 同上 | 岡田さん/非公開 | 食品名・タンパク質量（CSV由来・不足分提示） | DM-09(foods) |
| D5 | 食事記録/摂取量 | 同上 | 岡田さん/非公開 | 摂取日時・栄養4項目（当日合計は算出） | DM-08(meal_logs) |

> ⚠️ 要確認（人間判断）: 詳細なデータモデル（DM-ID・正規化・リレーション）は `30_データ・IF設計/01_データモデル.md`（設計PR2）で確定。

## 5. 信頼境界
> 📝 ここにDFD上の信頼境界を記載（詳細は `02_境界.md`）。{境界／相手／制御}。非公開データ（先方不可視🔒）は必ず注記。

| 境界 | 相手 | 制御 |
|---|---|---|
| Flutter アプリ ↔ Supabase | 岡田さん（端末） | HTTPS・Supabase Auth の JWT（DEC-D03・ADR-0004）。遮断はRLSが担う |
| Edge Function ↔ Google Gemini API | 外部API | Edge Function からのみ呼び出し・APIキーはFunction Secrets🔒。食事写真を外部送信するが**保存はしない**（解析後に破棄・DEC-D04確定/ADR-0003） |
| Supabase 内部（PostgREST/RPC ↔ DB） | Supabase | 全表でRLS有効。`anon` ロールに権限を与えない🔒 |

> 関連: 構成要素＝`01_構成要素.md` / 信頼境界の詳細＝`02_境界.md` / 外部連携＝`04_外部連携.md`。
