## 1. エラー処理
> 📝 ここに共通のエラー処理方針を記載。{例外の分類（業務エラー/システムエラー/一時失敗）／ERR-IDへのマッピング／共通エラー応答契約（`02_API設計.md`）との対応／ログ出力（`05_ログ設計.md`）／利用者向けメッセージの出し方／握り潰し禁止の原則}。

エラーを扱う場所は**2つ**。役割を分ける。

| 層 | 実装 | 役割 |
|---|---|---|
| Edge Function（Deno/TS） | `supabase/functions/_shared/*.ts` | 例外を共通契約の JSON へ落として返す。Gemini（EXT-01）の失敗を ERR-ID へ写像する |
| Flutter（Dart） | `app/lib/data/error_mapper.dart` | 受け取った失敗を利用者向けメッセージへ変換し SnackBar で出す |

呼び出し経路によって、通る層が違う。

| 経路 | 使う機能 | エラーの出どころ |
|---|---|---|
| Edge Function（`functions.invoke`） | FEAT-03 / FEAT-08 | Edge Function が返す `{ error_code, message, retryable }` |
| PostgREST 直接（`from(...)`） | FEAT-01 / FEAT-02 / FEAT-06 / FEAT-08 第2段 | Postgres と RLS。Edge Function を経由しない |
| RPC（`rpc(...)`） | FEAT-04 / FEAT-05 / FEAT-09 / FEAT-10 | Postgres 関数と RLS。Edge Function を経由しない |

**PostgREST／RPC 直接の経路には Edge Function が挟まらない。** そのため共通ヘルパーも通らない。この経路の一次防御は RLS であり、Flutter は `PostgrestException` を受けて自前で写像する。

**分類（Edge Function 側の判定）**

| 分類 | 判定 | 振る舞い | ERR/ログ |
|---|---|---|---|
| 業務エラー | 利用者の入力・前提データで決まる**予見可能**な失敗。zod 検証違反・enum 外の値・前提データ未登録（体重未設定／対象器具0件 等）。実装は `AppError` を明示 throw する | 400 を返し処理を中断。**DBへ到達する前に弾く**（書き込みを一切行わない）。`retryable: false`。メッセージは「何をどう直せばよいか」が分かる日本語 | 既定 `ERR-VALIDATION-001`(400)。機能固有ERRの接頭辞は各 `08_機能別詳細設計/FEAT-*.md` で割り当てる。ログは **WARN**（受領値の要約＋相関ID・機微はマスキング／`05_ログ設計.md`） |
| システムエラー | **想定外**の例外。`AppError` 以外の throw は全てここへ落ちる（DB例外・未捕捉の TypeError・外部の永続失敗）。Gemini API の課金停止・日次クォータ枯渇は時間をおいても解消しないため本分類 `[仮]` | 500 を返す（AI起因は `ERR-AI-FAIL`(500)、課金/クォータ枯渇のみ 402）。`retryable: false`。利用者向けメッセージは**定型文のみ**（例外メッセージ・SQL・モデル名を転記しない） | `ERR-AI-CREDIT`(402) / `ERR-AI-FAIL`(500) / 機能固有の 500 系。ログは **ERROR**＋スタックトレース（Edge Function ログのみ・`05_ログ設計.md`） |
| 一時失敗 | 時間をおけば成功しうる失敗。Gemini API の 429（レート制限）と応答タイムアウト（`AbortSignal` 発火） | **429 のみ** §4 のバックオフで自動再試行。上限到達時と 504 はそのまま返し `retryable: true`。UI は SnackBar ＋再試行アクション。**AI機能のみ縮退し記録・閲覧は継続**（NFR-AVAIL-05） | `ERR-AI-RATE`(429) / `ERR-AI-TIMEOUT`(504)。ログは **WARN**＋試行回数・所要時間・相関ID（外部送信の記録＝NFR-SEC-AUDIT-01） |

> ⚠️ 要確認（人間判断）: Gemini API は 402 を返さない。レート制限もクォータ枯渇も 429（`RESOURCE_EXHAUSTED`）で来る。`ERR-AI-RATE`(429・一時失敗) と `ERR-AI-CREDIT`(402・永続失敗) の切り分けは、応答本文の理由コードを見て Edge Function 側で行う必要がある `[仮]`。判定材料が取れない場合は全て `ERR-AI-RATE` に倒すか、切り分けを諦めるかの決定が要る。詳細は `03_外部連携IF/10_GeminiAPI連携.md`。

**共通エラー応答**は `../30_データ・IF設計/02_API設計.md §5` の形と**完全一致**させる（`{ error_code, message, retryable }`）。形を各 Edge Function で組み立てず、次の共通ヘルパーを必ず経由する。

```ts
// supabase/functions/_shared/errors.ts —— エラー表現の正本（形は ../30_データ・IF設計/02_API設計.md §5）
export class AppError extends Error {
  constructor(
    readonly code: string,          // "ERR-..." （ERR-ID）
    readonly status: number,        // HTTPステータス
    readonly userMessage: string,   // 利用者向け日本語。技術詳細を含めない
    readonly retryable: boolean,    // 利用者の手動再試行が有意味か（自動リトライとは別概念・§4）
    options?: { cause?: unknown; logDetail?: Record<string, unknown> },
  ) { super(code, { cause: options?.cause }); }
}

// 未知の例外も含め、必ず共通契約の JSON へ落とす（握り潰し・素の500返却を禁止）
export function toErrorResponse(e: unknown, correlationId: string): Response;

// 個別ERRのファクトリ（ERR-IDとHTTP・retryable の対応を1箇所に閉じ込める）
export const errAuth: () => AppError;                       // ERR-AUTH-001 / 401 / false
export const errValidation: (msg: string) => AppError;       // ERR-VALIDATION-001 / 400 / false
export function mapGeminiError(e: unknown): AppError;        // Gemini の 429/5xx/中断 → ERR-AI-* へ写像
```

```ts
// supabase/functions/_shared/handler.ts —— 全 Edge Function の唯一の入口
export type FnContext = { user: AuthedUser; supabase: SupabaseClient; correlationId: string };
export function withApi(
  handler: (req: Request, ctx: FnContext) => Promise<Response>,

// 責務: ①相関IDの発番 → ②requireUser（JWT検証） → ③handler 実行 → ④try/catch で toErrorResponse へ集約

// supabase/functions/_shared/auth.ts —— JWT 検証の共通化（全 Edge Function で同一実装を使う）
export async function requireUser(req: Request): Promise<AuthedUser>;
// 責務: Authorization ヘッダの JWT を Supabase Auth で検証する（ADR-0004）。
```

```dart
// app/lib/data/error_mapper.dart —— Flutter 側のエラー表現の正本
class AppFailure {
  final String code;       // "ERR-..."（ERR-ID）
  final String message;    // 利用者向け日本語
  final bool retryable;    // 再試行アクションを出すか
}

AppFailure mapError(Object e);
// 写像元（supabase_flutter が throw する例外）:
//   FunctionException  → 本文の { error_code, message, retryable } をそのまま採用（Edge Function 経由）
//   PostgrestException → SQLSTATE で分岐。42501（RLS 拒否）→ ERR-AUTH-001 / 23505（UNIQUE 違反）→ §3 参照
//   AuthException      → ERR-AUTH-001（サインイン画面へ戻す）
//   StorageException   → 画像アップロード失敗（FEAT-08 第1段の前段）
//   その他（SocketException 等） → 通信エラーの定型文・retryable: true
```

- 表示は `ScaffoldMessenger.of(context).showSnackBar(...)` に統一する。`retryable: true` のときだけ `SnackBarAction`（再試行）を付ける。
- ダイアログは使わない。操作を止めずに知らせる（SCR-01〜05 共通）。

**認証** — Flutter が JWT を保持し、全経路に自動で付く。

| 項目 | 内容 |
|---|---|
| 保持場所 | 端末。`supabase_flutter` がセッションを永続化し、期限前に自動リフレッシュする |
| 付与 | `Authorization: Bearer <JWT>` を PostgREST・RPC・Edge Function・Storage の**全リクエストに自動付与**。アプリのコードでヘッダを組み立てない |
| 一次防御 | **RLS**（`user_id = auth.uid()` 相当・ADR-0004）。DB が本人の行しか返さない・書かせない |
| Edge Function | JWT 検証を**明示的に行う**（`requireUser`）。既定の JWT 必須設定を外さない（`--no-verify-jwt` を付けない） |
| Flutter 側の絞り込み | `.eq('user_id', ...)` は**絞り込みであって防御ではない**。防御は RLS 側にある |

旧構成との違いを対比する（旧＝Vercel + Next.js 前提・ADR-0002）。

| 観点 | 旧構成 | 新構成 |
|---|---|---|
| セッションの持ち方 | サーバの HttpOnly Cookie | 端末に保存した JWT |
| 検証する場所 | サーバの全API入口（1箇所） | Edge Function（明示検証）＋ Postgres（RLS） |
| 一次防御 | アプリ側の本人チェック。RLS は二重防御 | **RLS が一次防御**。アプリ側は絞り込み |
| 未認証の到達範囲 | サーバで止まる | DB まで届くが RLS が 0件／拒否を返す |

- **順序を固定する**（Edge Function 内）: ①JWT検証 → ②入力バリデーション → ③DB照会/書き込み → ④Gemini 呼び出し。**未認証のリクエストで DB にも EXT-01 にも到達させない**（NFR-SEC-01・従量課金の悪用防止）。
- 未認証は例外なく `ERR-AUTH-001`(401)。「対象が0件」との区別のため 404 や 200 に丸めない。
- RLS 拒否（SQLSTATE 42501）も `ERR-AUTH-001` として扱う。理由の詳細を利用者に出さない。
- 認証の成否は監査ログに記録する（NFR-SEC-AUDIT-02・`05_ログ設計.md`）。
- `users.id`(bigint) と `auth.uid()`(uuid) の紐付け方式は未確定のため、`requireUser` が返す `AuthedUser` の実体は本書では決めない（正本は `06_DB設計規約.md`）。⚠️ 要確認（人間判断）。

**握り潰し禁止の原則**

- `catch {}`（空ブロック）・ログ出力の無い catch を禁止する。catch したら必ず「`AppError`／`AppFailure` に変換して再 throw」または「利用者へ提示」のどちらかを行う。
- **Deno 側と Dart 側で失敗の返り方が違う。** 取り違えると失敗が消える。

| 実装 | ライブラリの挙動 | 実装者がやること |
|---|---|---|
| Edge Function（TS） | 例外を投げず `{ data, error }` を返す | `error` を**必ず判定する**。判定しないと null への後続処理が別のエラーとして現れ、原因が消える |
| Flutter（Dart） | `PostgrestException` 等を**throw する** | `try`/`catch` で捕捉する。`await` を付け忘れると catch できない |

- 利用者向けメッセージには技術詳細（例外文言・SQL・スタックトレース・モデルID・APIキーの一部）を含めない。**スタックトレースは Edge Function のログのみ**（`05_ログ設計.md`）。
- 相関ID（`../30_データ・IF設計/02_API設計.md §1` の共通ヘッダ）はログと応答の突合に使う。応答本文には含めない `[仮]`（含めるならヘッダで返す）。

> ERRの完全列挙（分岐網羅の母集合）の正本は `../60_テスト設計/02_RED母集合_受入基準・状態・エラー.md`（段6で集約・本PR対象外）。本節と各 `08_機能別詳細設計/FEAT-*.md` の §6 がその入力となる。

> ⚠️ 要確認（人間判断）: 本書は Flutter + Supabase 構成（Vercel 不使用）で記述している。一方 ADR-0001（Vercel AI Gateway 採用）・ADR-0002（Next.js + Mantine 採用）・`30_データ・IF設計/02_API設計.md`（`/api/*` の Route Handler 契約）は Vercel 前提のまま。後継ADRの起票と段3の改訂が必要。

## 2. トランザクション境界
> 📝 ここにトランザクション境界の原則を記載。{1ユースケース＝1トランザクションの原則／境界の単位（サービス/ユースケース）／外部呼び出しをトランザクション内に含めない方針／分散時の整合（Outbox・Saga等）／状態遷移の永続化タイミング}。

- 境界の単位: **1ユースケース＝1トランザクション**。実体は「1回の RPC 呼び出し」または「1回の Edge Function 呼び出し」。複数の呼び出しにまたがるトランザクションは作らない。単一テーブルへの1文（INSERT/UPDATE/DELETE/SELECT）で完結する処理は、**明示トランザクションを張らない**（PostgreSQL の暗黙トランザクションで足りる）。
- 外部I/Oの扱い: **トランザクション外**。EXT-01（Gemini API）の呼び出しをトランザクション内に含めない。補償処理も持たない（§3 の二段構えで構造的に不要にする）。
- 分散整合: **Outbox / Saga はいずれも不採用**。関連 ADR-0004。

**Supabase クライアントの制約と、それに対する設計判断**

Supabase のクライアント（Flutter の `supabase_flutter`・Edge Function 内の supabase-js）はどちらも PostgREST 経由である。したがって**複数文をまたぐ `BEGIN`〜`COMMIT` をアプリ側から張れない**。「複数テーブルに原子的に書く」ユースケースは、次のいずれかを選ぶ必要がある。

| 案 | 方式 | 評価 |
|---|---|---|
| **A（採用）** | **Postgres 関数（RPC）で1文にまとめる**。`supabase.rpc('...')` で呼ぶ。関数本体は単一の暗黙トランザクションで実行されるため原子性が保証される | 原子性が実装者の注意力に依存しない。`SECURITY INVOKER` にすれば RLS が効いたまま。関数は `supabase/migrations/*.sql` で版管理でき可逆にできる（`04_移行設計.md §3`） |
| B | 明細を配列で受け、**親を作らず単一 INSERT** にする | 親（`training_sessions`）が必要な本PJのモデルでは成立しない。親の採番結果を子が参照するため2文が不可避 |
| C | アプリ側で「親INSERT → 子INSERT → 失敗時に親を DELETE で補償」 | 補償の失敗経路が新たに生まれ、孤児行の混入を防ぎきれない。**不採用** |

- **複数テーブルにまたがる書き込みは案 A（RPC）を採る。** 該当するのは現時点で FEAT-04（`create_training_session`：`training_sessions` ＋ `training_session_details`）のみ。
- Edge Function 内から書く場合も同じ制約を受ける。Edge Function だからトランザクションが張れるわけではない。

```sql
-- FEAT-04 のセッション＋明細を1トランザクションで作る（関数シグネチャのみ・実装は FEAT-04 の詳細設計）
-- SECURITY INVOKER（既定）とし、RLS を迂回しない
CREATE FUNCTION create_training_session(p_performed_date date, p_menu_ids bigint[])
  RETURNS bigint AS $$ ... $$ LANGUAGE plpgsql;
-- 内部: training_sessions を1行 INSERT → RETURNING id → training_session_details を
--       p_menu_ids の要素数ぶん INSERT（is_done は既定 false ＝ ST-01 / 遷移 T01）
```

- **RPC に置くのは永続化だけ**にする。バリデーション・業務判定（RULE-*）は Dart の純関数に残す（`app/lib/domain/*.dart`・単体テスト対象・NFR-QUAL-01）。SQL 関数に業務ロジックを流出させない。
- 追加した関数は `01_DB物理設計.md §3` に無いため、DDL への反映要否は ⚠️ 要確認（人間判断）とし本書では追加しない。

**外部I/O（EXT-01）をトランザクションに含めない ―― 二段構え**

AI 呼び出しは数秒〜20秒かかり（NFR-PERF-03/04）、トランザクション内に置くと接続とロックをその間占有する。本PJでは**呼び出しの分割そのものでこれを構造的に防ぐ**。

| FEAT | 第1段（外部I/Oのみ・DB書き込みなし） | 第2段（DB書き込みのみ・外部I/Oなし） |
|---|---|---|
| FEAT-08 | `supabase.functions.invoke('analyze-meal')`（Storage の画像→EXT-01→栄養4項目を返すだけ。画像は推論完了と同時に Storage から削除・ADR-0003） | `supabase.from('meal_logs').insert(...)`（栄養4項目を単一 INSERT） |
| FEAT-03 | `supabase.functions.invoke('generate-menu')`（部位＋器具→EXT-01→提案メニューを返すだけ） | 提案の保存は行わない（表示のみ）。利用者が採用した場合の登録は FEAT-01 の `training_menus` INSERT |

- 第1段は**業務データの書き込みを持たないためトランザクションが存在しない**。第2段は単一テーブル1文のため明示トランザクション不要。両者の間に整合を取るべき共有状態が無い。
- FEAT-08 の Storage は**保管庫ではなく転送路**。アップロードと削除は業務テーブルと無関係なので、上の原則を崩さない。削除に失敗しても業務データは壊れない（残骸が残るだけ）。
- 第1段成功・第2段失敗のとき、AI の課金は済んでいるが記録は残らない。**再解析（再課金）を避けるため、第1段の結果は Flutter の画面状態に保持し、第2段のみ再送できる UI にする**（`08_機能別詳細設計/FEAT-08_*.md` で具体化）。
- 状態遷移の永続化タイミング: T01（新規→ST-01）は上記 RPC の中で明細作成と同時。T02（ST-01→ST-02）は `training_session_details.is_done` の UPDATE 単文（§3 の状態ガード付き）。イベント定義の正本は `../30_データ・IF設計/03_ドメインイベント.md`。

**Outbox / Saga を採らない理由**

| 理由 | 内容 |
|---|---|
| 更新先が1つ | 書き込み先は Supabase の単一DBのみ。複数データストアにまたがる更新が無い |
| 外部に確定させる連携が無い | EXT-01 は読み取り的な呼び出し。副作用は従量課金だけで、ロールバックすべき外部状態を持たない |
| ディスパッチャを置けない | Outbox は常駐プロセスか定期実行を要する。本PJには非同期基盤が無い（`02_バッチ設計.md`）。導入は NFR-MAINT-01 に反する |

## 3. 冪等性
> 📝 ここに冪等性の担保方針を記載。{冪等キーの発行・伝播（`02_API設計.md` の共通ヘッダ）／状態ガード（許可遷移のみ・終端不変）による二重反映防止／重複リクエストの検知・棄却／リトライ安全な操作設計}。二重処理が発生しないことが読み取れるように。

| 対象操作 | 冪等の担保方式 | 根拠 |
|---|---|---|
| 参照系 全般（`get_dashboard`・`get_protein_remaining` の RPC／`training_menus` 等の select） | **自然に冪等**（副作用なし）。何度呼んでもDBを変えない。リトライ安全 | `../30_データ・IF設計/02_API設計.md §1` |
| `create_training_session` RPC の明細登録 | **DB一意制約**。`training_session_details` の `(session_id, menu_id)` UNIQUE（`uq_tsd_session_menu`）で同一セッション内の同一種目の二重登録を防ぐ。RPC 内では `ON CONFLICT DO NOTHING` で受け、重複をエラーにしない | `01_DB物理設計.md §2.3・§3` |
| `training_session_details.is_done` の更新（T02） | **状態ガード**。許可遷移 ST-01→ST-02 のみ実行する。`update({'is_done': true}).eq('id', id).eq('is_done', false)` とし、既に ST-02 の行は更新0件で正常終了（終端は不変）。2回押されても結果は同一 | `../30_データ・IF設計/03_ドメインイベント.md §2`（T02） |
| `users` の更新（FEAT-06） | **全項目置換の update**。同じ値を何度送っても結果が同一（自然に冪等） | `../30_データ・IF設計/02_API設計.md §3` |
| `analyze-meal`・`generate-menu`（Edge Function） | **非冪等**。冪等キーを持たない。同じ画像・同じ条件でも呼ぶたびに EXT-01 へ課金され、生成結果も一致しない。担保手段は **Flutter 側の二重送信抑止のみ**（§5・実行中はボタンを無効化） | ADR-0001（従量課金・自動リトライなし）・`../30_データ・IF設計/02_API設計.md §1` |
| `meal_logs` への insert（FEAT-08 第2段） | **サーバ側では防げない**。`meal_logs` に自然キーが無く、同一栄養値の食事を2回記録するのは**正当な操作**のため一意制約を張れない。担保は §5 のUI抑止＋「成功時に結果画面を閉じて再送信できなくする」`[仮]` | `01_DB物理設計.md §2.4`（一意制約なし）・下記 ⚠️ |
| `gym_visits` への insert（FEAT-04） | **担保なし**。同日同ジムの重複入館を防ぐ一意制約が無く重複行が入りうる。ヒートマップは実施有無の2値のため表示への影響は無い `[仮]` | `01_DB物理設計.md §2.1` |
| `replace_foods` RPC（FEAT-10） | **全置換のため自然に冪等**（同じCSVを2回取り込んでも結果が同一）。`foods` を削除して入れ直す方式を前提とする `[仮]`。差分取込に変える場合は `foods.name` に一意制約が無く重複を生むため、重複判定の方式を FEAT-10 側で確定する | `01_DB物理設計.md §1.5`・`08_機能別詳細設計/FEAT-10_食事マスタCSVインポート.md` |

- **冪等キー方式は当面採らない。** `../30_データ・IF設計/02_API設計.md §1` は「書き込み系は冪等キー（任意）」としているが、サーバ側で「処理済みキー」を保持する保存先が `01_DB物理設計.md` に無く、本PJの方針で新テーブルを追加しないため。
- **リトライ安全な操作設計の原則**: 自動リトライ（§4）を掛けてよいのは「冪等な操作」に限る。上表で非冪等と判定した操作には、**自動リトライを一切掛けない**。
- **UNIQUE 違反を業務エラーにしない**: 二重登録の防止は「利用者の入力ミス」ではないため、`uq_tsd_session_menu` 違反は 400 ではなく「無視して成功扱い」とする（`ON CONFLICT DO NOTHING`）。Flutter 側へ SQLSTATE 23505 を漏らさない。

> ⚠️ 要確認（人間判断）: `meal_logs` への二重 insert は、テーブル構造上サーバ側で防げない。(a) UI抑止のみで許容するか、(b) 冪等キーを受けるための保存先（新テーブルまたは既存列の転用）を認めるか、(c) 「直近N秒以内の同一栄養値・同一日付の記録は警告する」という業務的な重複検知を入れるか。本書は (a) を `[仮]` としている。

## 4. リトライ
> 📝 ここにリトライの共通方針を記載。{リトライ対象（一時失敗）と非対象（永続失敗）の区別／回数・バックオフ（指数/ジッタ）／上限到達時の扱い（隔離・通知 ERR-__）／外部システムのレート制限との整合}。値の根拠（DEC-ID）を併記。

| パラメータ | 値 | 根拠 |
|---|---|---|
| リトライ対象 | （一時失敗のみ）**`ERR-AI-RATE`(429) だけ**を Edge Function 内で自動再試行する。AI呼び出しそのものは原則として自動リトライしない | ADR-0001（従量課金）・`../30_データ・IF設計/02_API設計.md §1`「AI呼び出しは非冪等・自動リトライしない。429時のみ指数バックオフ」 |
| 最大回数 | **2回**（初回＋再試行2回＝最大3試行）`[仮]` | DEC未起票。429 はトークンを消費せず即座に返るため回数を許容できる。⚠️ 要確認（人間判断） |
| バックオフ | **指数バックオフ**。初期待機 **1000ms**・乗数 **2.0**（1s → 2s）・総待機上限 **4秒** `[仮]`。応答に `Retry-After` があればその値を優先する。**ジッタは付けない**（単一利用者で群衆同期が起きないため・NFR-SCALE-01） | DEC未起票。⚠️ 要確認（人間判断） |
| デッドライン | 残余時間が1試行分に満たなければ再試行せず打ち切る。予算は FEAT-03=15秒（NFR-PERF-03）／FEAT-08=20秒（NFR-PERF-04）。Edge Function 側は `AbortSignal.timeout()` で全体を打ち切る | NFR-PERF-03/04 |
| モデルフォールバック | **持たない**（下記）。回数のカウント対象外 | 下記・EXT-01 |
| 上限到達時 | （隔離・通知 `ERR-AI-RATE`(429)）**隔離キューは持たない**（非同期基盤が無いため・`02_バッチ設計.md`）。`retryable: true` のまま Flutter へ返し、SnackBar ＋ `SnackBarAction`（再試行）で**手動再試行**に委ねる。AI機能のみ不可・記録/閲覧は継続（NFR-AVAIL-05） | NFR-AVAIL-05・ADR-0001 |

**リトライ非対象**（永続失敗。再送しても結果が変わらないか、害が大きい）

| 対象 | 理由 |
|---|---|
| `ERR-AI-CREDIT`(402) | 課金設定・クォータを直すまで必ず失敗する |
| `ERR-AI-TIMEOUT`(504) | 再送は二重課金になる。NFR-PERF-03/04 の予算も超える |
| `ERR-VALIDATION-001`(400) | 入力を直さない限り失敗する |
| `ERR-AUTH-001`(401) | 再サインインするまで失敗する |
| DB書き込みの失敗 | 二重登録のリスクがある（§3） |

**`retryable` フラグと「自動リトライ」は別概念**

- 応答の `retryable`（`../30_データ・IF設計/02_API設計.md §5`）は「**利用者が手動で再試行する価値があるか**」を示す UI 向けの情報である。サーバが自動再送したことを意味しない。
- したがって `ERR-AI-TIMEOUT`(504) は `retryable: true`（再試行アクションを出す）だが、**自動再送はしない**。両者を混同すると二重課金になる。

**モデルフォールバックは持たない**

| 項目 | 内容 |
|---|---|
| 現状 | Edge Function は `GEMINI_MODEL`（既定 `gemini-3.5-flash`）を1つだけ呼ぶ。代替モデルへの切替を持たない |
| なぜ持たないか | 自動切替を担っていたゲートウェイ層が構成から無くなったため。同等の機能は Edge Function 内に自前で実装するしかない |
| 実装するなら | `try` で既定モデル → 失敗時に代替モデルで1回だけ呼び直す、を Edge Function 内に書く。所要時間が単純加算され NFR-PERF-03/04 を超えやすくなる `[仮]` |
| 現在の縮退 | モデル1本が失敗したら、そのまま `ERR-AI-FAIL` で縮退する（NFR-AVAIL-05） |

- 外部送信の記録（NFR-SEC-AUDIT-01）には**実際に応答したモデルID**を残す。自前フォールバックを入れた場合はどちらで応答したかが分かるようにする。

**その他**

- 自動リトライした場合は、**試行ごとに1行ログを出す**（試行番号・待機時間・ERR-ID・相関ID）。「静かに2回呼んだ」状態を作らない（§1 握り潰し禁止）。
- **Flutter 側の自動リトライは実装しない。** Edge Function 側のリトライと二重になり、課金が掛け算になるため。参照系の再取得のみ、利用者操作（引き下げ更新・再試行アクション）を起点に行う。
- 通信断・アプリのバックグラウンド遷移で `functions.invoke` の応答を取りこぼした場合も、**自動では投げ直さない**。課金済みの可能性があるため、利用者に再実行させる。

## 5. 多重制御・排他
> 📝 ここに同時実行・多重処理の制御方針を記載。{直列化が必要な処理と同時実行の上限／排他の手段（分散ロック・FIFOキュー・処理中フラグ）／多重ディスパッチ防止（`is_processing` 等）／スタック検知と救済／冪等（§3）との役割分担}。関連DEC-__。

**直列化・排他は採らない。** 前提は次の2点。

| 前提 | 根拠 |
|---|---|
| 利用者は岡田さん1名。同一行への同時書き込みが実質起きない | NFR-SCALE-01（マルチテナント適用外） |
| 行レベルの同時更新は PostgreSQL の既定の行ロック＋§3 の状態ガードで足りる | §3 |

不採用にするものと、その理由。

| 手段 | 不採用の理由 | 根拠 |
|---|---|---|
| 分散ロック | 解放漏れという新しい障害モードを持ち込む。個人保守に見合わない | NFR-MAINT-01 |
| FIFOキュー | ワーカー基盤が要る。本PJに非同期基盤が無い | NFR-MAINT-01・`02_バッチ設計.md` |
| `is_processing` フラグ | 該当列が無く、列を追加しない方針。競合の実測母数も無い | `01_DB物理設計.md` |

実際に必要な多重制御は次の**2点のみ**。

| # | 対象 | 手段 | 目的 |
|---|---|---|---|
| 1 | 二重送信防止 | **Flutter 側でボタンを無効化する。** 実行中フラグを持ち `onPressed: busy ? null : submit` とする。完了・失敗まで再実行を受け付けない。フォーム送信も同じフラグで抑止する | **非冪等な操作（`analyze-meal`・`generate-menu`・`meal_logs` の insert）の唯一の担保手段**（§3）。二重タップ＝二重課金・二重登録に直結する |
| 2 | AI呼び出しのレート制限 | Edge Function 2本（`analyze-meal`・`generate-menu`）に上限を課す。実装先は未確定（下記 ⚠️）。超過時は `ERR-AI-RATE`(429) を返す | コスト暴走・悪用の防止（NFR-SEC-05） |

- 二重送信抑止は**アプリ側にしか無い**。アプリを再インストールされても、別端末から呼ばれても効かない。JWT さえあれば Edge Function は呼べる。これがレート制限（#2）が要る理由でもある。
- 参照系の連打（部位の高速切替など）は排他ではなく**古い応答の破棄**で扱う。Dart の `Future` はキャンセルできないため、リクエストに発行順の連番を持たせ、**最新でない応答を捨てて**最後の操作の結果だけを描画する（実装例は `08_機能別詳細設計/FEAT-02_部位選択と器具絞り込み.md §7`）。
- スタック救済: **本PJでは該当なし**。非同期ジョブ・処理中フラグ・キューを一切持たない（`02_バッチ設計.md`）ため、「処理中のまま放置される」状態が構造的に存在しない。Edge Function は実行終了とともにメモリごと解放される（ADR-0003 と同じ性質）ので、タイムアウト検知・再ディスパッチの機構も不要。
- 冪等（§3）との役割分担: **§3 は「同じ操作が2回届いたときに結果を1回分に収める」**（DB一意制約・状態ガード）、**§5 は「そもそも2回届かせない」**（UI抑止・レート制限）。参照系と DB 書き込みは §3 で守れるが、**AI呼び出しは §3 で守れない**（冪等キーを持てない・非冪等）ため、§5 の #1 が唯一の防波堤になる。

> ⚠️ 要確認（人間判断）: レート制限（#2）の実装先が未確定。Edge Function はリクエストごとに独立して起動するため、関数内のインメモリカウンタは機能しない。候補は次の3つ。いずれも `[仮]`。
> - (a) **Postgres のカウンタテーブル**を Edge Function から読み書きする（例: `ai_call_counters(user_id, window_start, count)`）。確実だが**テーブル追加＝`01_DB物理設計.md` の改訂**を伴う。
> - (b) **Supabase の組み込み制限に依存する**（プロジェクト側のリクエスト上限）。アプリ実装は不要だが、AI呼び出しだけを狙って絞れるかは未確認。
> - (c) **実装しない**。単一利用者かつ TestFlight 配布で外部からの悪用経路が乏しいため、当面は許容する。
>
> 閾値（回/分・回/日）も未定。
