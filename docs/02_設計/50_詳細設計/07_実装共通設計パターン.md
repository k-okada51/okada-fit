## 1. エラー処理
> 📝 ここに共通のエラー処理方針を記載。{例外の分類（業務エラー/システムエラー/一時失敗）／ERR-IDへのマッピング／共通エラー応答契約（`02_API設計.md`）との対応／ログ出力（`05_ログ設計.md`）／利用者向けメッセージの出し方／握り潰し禁止の原則}。

### エラーを扱う2つの層

役割を分ける。

| 層 | 実装 | 役割 |
|---|---|---|
| Edge Function（Deno/TS） | `supabase/functions/_shared/*.ts` | 例外を共通契約の JSON へ落として返す。Gemini（EXT-01）の失敗を ERR-ID へ写像する |
| Flutter（Dart） | `app/lib/data/error_mapper.dart` | 受け取った失敗を利用者向けメッセージへ変換し SnackBar で出す |

呼び出し経路によって、通る層が違う。

| 経路 | 使う機能 | エラーの出どころ |
|---|---|---|
| Edge Function（`functions.invoke`） | FEAT-03 / FEAT-08 | Edge Function が返す `{ error_code, message, retryable }` |
| PostgREST 直接（`from(...)`） | FEAT-01 / FEAT-02 / FEAT-06 / FEAT-08 第2段 | Postgres と RLS。Edge Function を経由しない |
| RPC（`rpc(...)`） | FEAT-04 / FEAT-05 / FEAT-09 / FEAT-10 | Postgres 関数と RLS。Edge Function を経由しない |

PostgREST／RPC 直接の経路には Edge Function が挟まらない。

| 帰結 | 内容 |
|---|---|
| 共通ヘルパー | 通らない |
| 一次防御 | **RLS** |
| Flutter 側 | `PostgrestException` を受けて自前で写像する |

### エラーの分類（Edge Function 側の判定）

失敗を3つに分ける。

| 分類 | 何が起きたか | 例 |
|---|---|---|
| 業務エラー | 利用者の入力・前提データで決まる**予見可能**な失敗 | zod 検証違反／enum 外の値／前提データ未登録（体重未設定・対象器具0件 等） |
| システムエラー | **想定外**の例外。`AppError` 以外の throw は全てここへ落ちる | DB例外／未捕捉の TypeError／外部の永続失敗 |
| 〃 | Gemini API の**課金無効**（400 `failed_precondition` → `ERR-AI-CREDIT`・402） | ADR-0011 |
| 〃 | Gemini API の**日次クォータ超過**（429 `quota_exceeded` → `ERR-AI-QUOTA`・429） | 当日は回復しない |
| 一時失敗 | 時間をおけば成功しうる失敗 | Gemini API の 429 `rate_limit_exceeded`（`ERR-AI-RATE`）／応答タイムアウト |

| 分類 | 振る舞い | retryable | ERR | ログ |
|---|---|---|---|---|
| 業務エラー | 400 を返して中断。**DBへ到達する前に弾く**（書き込みを一切行わない） | false | 既定 `ERR-VALIDATION-001`(400) | **WARN**。受領値の要約＋相関ID。機微はマスキング |
| システムエラー | 500 を返す。AI起因は `ERR-AI-FAIL`(500)、課金・クォータ枯渇のみ 402 | false | `ERR-AI-CREDIT`(402) ／ `ERR-AI-FAIL`(500) ／ 機能固有の 500 系 | **ERROR**＋スタックトレース。Edge Function ログのみ |
| 一時失敗（再送で通る） | **429 のみ** §4 のバックオフで自動再試行。上限到達時はそのまま返す | true | `ERR-AI-RATE`(429) | **WARN**＋試行回数・所要時間・相関ID |
| 一時失敗（再送しない） | 504 は自動再試行せずそのまま返す。再試行は利用者の操作に委ねる | false | `ERR-AI-TIMEOUT`(504) | **WARN**＋所要時間・相関ID |

- 業務エラーは実装で `AppError` を明示 throw する。
- 業務エラーのメッセージは「何をどう直せばよいか」が分かる日本語にする。
- 業務エラーの機能固有 ERR の接頭辞は各 `08_機能別詳細設計/FEAT-*.md` で割り当てる。
- システムエラーの利用者向けメッセージは**定型文のみ**。例外メッセージ・SQL・モデル名を転記しない。
- Gemini API の課金停止・クォータ枯渇は時間をおいても解消しないため、一時失敗ではなくシステムエラーに置く。
- 一時失敗の UI は SnackBar ＋再試行アクション。**AI機能のみ縮退し記録・閲覧は継続**（NFR-AVAIL-05 AI障害時の縮退）。
- 一時失敗のログは外部送信の記録を兼ねる（NFR-SEC-AUDIT-01）。ログ方針の正本は `05_ログ設計.md`。

> ~~⚠️ 要確認（人間判断）: レート制限もクォータ枯渇も 429 で来るため切り分けられない。~~（**解決**・2026-08-08）
> **この前提は誤りだった。** 公式のエラーコード仕様で**区別できる**（ADR-0011）。

3つは `status` と `error.status` の組で判別する。**429 は2種類あり retryable が逆になる。**

| Gemini の応答 | 本PJの ERR | HTTP | retryable |
|---|---|---|---|
| 429 `rate_limit_exceeded` | `ERR-AI-RATE` | 429 | **true**（待てば通る） |
| 429 `quota_exceeded` | `ERR-AI-QUOTA` | 429 | **false**（当日は通らない） |
| 400 `failed_precondition` | `ERR-AI-CREDIT` | 402 | false（課金設定の是正が要る） |

`error.status` を見ずに 429 だけで判定すると、日次クォータ切れをバックオフで叩き続ける。詳細は `03_外部連携IF/10_GeminiAPI連携.md`。

### 共通ヘルパー

**共通エラー応答**の形は `../30_データ・IF設計/02_API設計.md §5` と**完全一致**させる。

形は `{ error_code, message, retryable }`。各 Edge Function で組み立てず、次のヘルパーを必ず経由する。

```ts
// supabase/functions/_shared/errors.ts —— エラー表現の正本（形は ../30_データ・IF設計/02_API設計.md §5）
export class AppError extends Error {
  constructor(
    readonly code: string,          // "ERR-..." （ERR-ID）
    readonly status: number,        // HTTPステータス
    readonly userMessage: string,   // 利用者向け日本語。技術詳細を含めない
    readonly retryable: boolean,    // 利用者の手動再試行が有意味か（自動リトライとは別概念・§4）
    options?: { cause?: unknown; logDetail?: Record<string, unknown> },
  ) { super(code, { cause: options?.cause }); }
}

// 未知の例外も含め、必ず共通契約の JSON へ落とす（握り潰し・素の500返却を禁止）
export function toErrorResponse(e: unknown, correlationId: string): Response;

// 個別ERRのファクトリ（ERR-IDとHTTP・retryable の対応を1箇所に閉じ込める）
export const errAuth: () => AppError;                       // ERR-AUTH-001 / 401 / false
export const errValidation: (msg: string) => AppError;       // ERR-VALIDATION-001 / 400 / false
export function mapGeminiError(e: unknown): AppError;        // Gemini の 429/5xx/中断 → ERR-AI-* へ写像
```

```ts
// supabase/functions/_shared/handler.ts —— 全 Edge Function の唯一の入口
export type FnContext = { user: AuthedUser; supabase: SupabaseClient; correlationId: string };
export function withApi(
  handler: (req: Request, ctx: FnContext) => Promise<Response>,
): (req: Request) => Promise<Response>;
// 責務: ①相関IDの発番 → ②requireUser（JWT検証） → ③handler 実行 → ④try/catch で toErrorResponse へ集約

// supabase/functions/_shared/auth.ts —— JWT 検証の共通化（全 Edge Function で同一実装を使う）
export async function requireUser(req: Request): Promise<AuthedUser>;
// 責務: Authorization ヘッダの JWT を Supabase Auth で検証する（ADR-0004）。
//       無効・失効・欠落は errAuth() を throw（ERR-AUTH-001 / 401 / retryable:false）
export type AuthedUser = { id: string };   // uuid。auth.uid() ＝ users.id と同値（ADR-0005）
```

```dart
// app/lib/data/error_mapper.dart —— Flutter 側のエラー表現の正本
class AppFailure {
  final String code;       // "ERR-..."（ERR-ID）
  final String message;    // 利用者向け日本語
  final bool retryable;    // 再試行アクションを出すか
}

AppFailure mapError(Object e);
// 写像元（supabase_flutter が throw する例外）:
//   FunctionException  → 本文の { error_code, message, retryable } をそのまま採用（Edge Function 経由）
//   PostgrestException → SQLSTATE で分岐。42501（RLS 拒否・401/403）→ ERR-AUTH-001 / 23505（UNIQUE 違反・409）→ §3 参照
//   AuthException      → ERR-AUTH-001（サインイン画面へ戻す）
//   その他（SocketException 等） → 通信エラーの定型文・retryable: true
```

- 表示は `ScaffoldMessenger.of(context).showSnackBar(...)` に統一する。
- `retryable: true` のときだけ `SnackBarAction`（再試行）を付ける。
- ダイアログは使わない。操作を止めずに知らせる（SCR-01〜05 共通）。

### PostgREST・RPC の SQLSTATE 写像（正本・2026-08-08 確定）

PostgREST 公式の Errors リファレンスで確認した。**本表が各 `FEAT-*.md` の正本**である。

| SQLSTATE | 発生 | PostgREST が返す HTTP | 本PJの扱い |
|---|---|---|---|
| `23505` | UNIQUE 違反 | **409** | 機能別 ERR。`ON CONFLICT DO NOTHING` の箇所は成功扱い（§3） |
| `23503` | FK 違反 | **409** | **業務エラー**（使用中で削除できない）。500 に落とさない |
| `42501` | 権限不足・RLS 拒否 | **401 または 403**（認証済みかで変わる） | `ERR-AUTH-001` |
| `23514` | CHECK 違反 | `[仮]`（公式の写像表に記載が無い） | 機能別 ERR |
| `PTxyz` | 関数が `errcode` で指定した独自コード | **xyz の3桁がそのまま HTTP ステータス** | `PT400`→400 ／ `PT409`→409 ／ `PT500`→500 |

- `PTxyz` は「`PT` に続く3桁をそのまま HTTP ステータスにする」PostgREST の規約である。
- `PT402` を raise すれば 402 が返る。FEAT-05 の `PT400` / `PT409` はそのまま成立する。
- **`23503` を 400 系として扱わない。409 が正しい。**
- `42501` は認証済みなら 403、未認証なら 401 になる。どちらも `ERR-AUTH-001` に写す。
- `23514` の HTTP だけは公式に記載が無い。確定するまで `[仮]` のまま残す。

エラー応答の本文は4フィールドである。

| フィールド | 内容 |
|---|---|
| `code` | SQLSTATE または PostgREST 独自コード（`PGRST*`） |
| `message` | 例外メッセージ。`RAISE EXCEPTION` の本文がここに載る |
| `details` | 制約名などの詳細。**FK・UNIQUE の判別材料はここに入る** |
| `hint` | 是正のヒント。`null` になりうる |

- どこまで返すかは PostgREST の **`client-error-verbosity`** 設定で決まる。
- `verbose` は4つ全部を返す。`minimal` は `code` と `message` だけになる。
- 制約名で FK を判別する設計（FEAT-01 §6.1）は `details` を要する。設定の確認が要る（§5 #12）。

### 認証

Flutter が JWT を保持し、全経路に自動で付く。

| 項目 | 内容 |
|---|---|
| 保持場所 | 端末。`supabase_flutter` がセッションを永続化し、期限前に自動リフレッシュする |
| 付与 | `Authorization: Bearer <JWT>` を PostgREST・RPC・Edge Function の**全リクエストに自動付与**。アプリのコードでヘッダを組み立てない |
| 一次防御 | **RLS**（`user_id = auth.uid()`・ADR-0004 / ADR-0005）。DB が本人の行しか返さない・書かせない |
| Edge Function | JWT 検証を**明示的に行う**（`requireUser`）。既定の JWT 必須設定を外さない（`--no-verify-jwt` を付けない） |
| Flutter 側の絞り込み | `.eq('user_id', ...)` は**絞り込みであって防御ではない**。防御は RLS 側にある |

### 認証主体の実体（2026-08-08 確定・ADR-0005）

**案A で確定した。** `users.id` を uuid にし、`auth.users.id` と同じ値を入れる。

| 項目 | 内容 |
|---|---|
| `users.id` | **uuid**。`auth.users(id)` を参照する（`ON DELETE CASCADE`）。自動採番しない |
| 各履歴の `user_id` | **uuid**。`gym_visits` / `training_menus` / `training_sessions` / `meal_logs` |
| 他テーブルの `id` | **bigint のまま**。型を変えたのは上の2行だけ |
| 認証主体の実体 | `auth.uid()` が返す uuid **1種類のみ**。アプリ側で対応表を引かない |
| `requireUser` の戻り値 | `AuthedUser`＝`{ id: string /* uuid ＝ auth.uid() ＝ users.id */ }` |
| RLS の述語 | `auth.uid()` との**直接比較**。型変換・サブクエリを要しない |
| `users` 行の作成 | `auth.users` への AFTER INSERT トリガ（`handle_new_user`）で1行作る |
| 正本 | `01_DB物理設計.md §3`・`06_DB設計規約.md` |

### RLS の3区分（横断方針）

全テーブルで `ALTER TABLE … ENABLE ROW LEVEL SECURITY` を入れる。ポリシーは3つの型のどれかに収まる。

| 区分 | テーブル | ポリシーの述語 |
|---|---|---|
| **本人のみ** | `users` | `id = auth.uid()` |
| 〃 | `training_menus` / `gym_visits` / `training_sessions` / `meal_logs` | `user_id = auth.uid()` |
| **共通マスタ** | `gyms` / `training_machines` / `foods` | `TO authenticated USING (true)` |
| **親経由** | `machine_menus` | `EXISTS (… training_menus m WHERE m.id = menu_id AND m.user_id = auth.uid())` |
| 〃 | `training_session_details` | `EXISTS (… training_sessions s WHERE s.id = session_id AND s.user_id = auth.uid())` |

- **新しいテーブルを足すときは、この3区分のどれかに必ず割り当てる。** どれにも当てはまらない表を作らない。
- 区分ごとのポリシー本文（`FOR SELECT/INSERT/UPDATE/DELETE` の分割・`WITH CHECK`）は `[仮]`。正本は `01_DB物理設計.md §3`。
- 共通マスタは**認証済みなら誰でも書き換えられる**。単一利用者の現行運用では実害が無い。

> ⚠️ 要確認（人間判断）: 共通マスタ（`gyms`・`training_machines`・`foods`）の書き込みを Phase2（NFR-SCALE-01・複数利用者）でどう絞るか。現行のまま複数利用者に広げると、他人のマスタを壊せる。

### 旧構成との対比

旧＝Vercel + Next.js 前提（ADR-0002）。

| 観点 | 旧構成 | 新構成 |
|---|---|---|
| セッションの持ち方 | サーバの HttpOnly Cookie | 端末に保存した JWT |
| 検証する場所 | サーバの全API入口（1箇所） | Edge Function（明示検証）＋ Postgres（RLS） |
| 一次防御 | アプリ側の本人チェック。RLS は二重防御 | **RLS が一次防御**。アプリ側は絞り込み |
| 未認証の到達範囲 | サーバで止まる | DB まで届くが RLS が 0件／拒否を返す |

- **Edge Function 内の順序を固定する**: ①JWT検証 → ②入力バリデーション → ③DB照会/書き込み → ④Gemini 呼び出し。
- 未認証のリクエストを **DB にも EXT-01 にも到達させない**（NFR-SEC-01・従量課金の悪用防止）。
- 未認証は例外なく `ERR-AUTH-001`(401)。「対象が0件」との区別のため 404 や 200 に丸めない。
- RLS 拒否（SQLSTATE 42501）も `ERR-AUTH-001` として扱う。理由の詳細を利用者に出さない。
- 認証の成否は監査ログに記録する（NFR-SEC-AUDIT-02・`05_ログ設計.md`）。
- `users.id` と `auth.uid()` はどちらも uuid で**同じ値**（ADR-0005）。紐付けの変換は存在しない。
- `requireUser` が返す `AuthedUser` の実体は **`auth.uid()` の uuid** で確定する（「認証主体の実体」の表）。

### 握り潰し禁止の原則

- `catch {}`（空ブロック）と、ログ出力の無い catch を禁止する。
- catch したら必ずどちらかを行う。「`AppError`／`AppFailure` に変換して再 throw」または「利用者へ提示」。
- **Deno 側と Dart 側で失敗の返り方が違う。** 取り違えると失敗が消える。

| 実装 | ライブラリの挙動 | 実装者がやること |
|---|---|---|
| Edge Function（TS） | 例外を投げず `{ data, error }` を返す | `error` を**必ず判定する**。判定しないと null への後続処理が別のエラーとして現れ、原因が消える |
| Flutter（Dart） | `PostgrestException` 等を**throw する** | `try`/`catch` で捕捉する。`await` を付け忘れると catch できない |

- 利用者向けメッセージに技術詳細を含めない。例外文言・SQL・スタックトレース・モデルID・APIキーの一部が該当する。
- **スタックトレースは Edge Function のログのみ**（`05_ログ設計.md`）。
- 相関ID（`../30_データ・IF設計/02_API設計.md §1` の共通ヘッダ）はログと応答の突合に使う。
- 相関IDは応答本文に含めない `[仮]`。含めるならヘッダで返す。

> ERRの完全列挙（分岐網羅の母集合）の正本は `../60_テスト設計/02_RED母集合_受入基準・状態・エラー.md`（段6で集約・本PR対象外）。本節と各 `08_機能別詳細設計/FEAT-*.md` の §6 がその入力となる。

## 2. トランザクション境界
> 📝 ここにトランザクション境界の原則を記載。{1ユースケース＝1トランザクションの原則／境界の単位（サービス/ユースケース）／外部呼び出しをトランザクション内に含めない方針／分散時の整合（Outbox・Saga等）／状態遷移の永続化タイミング}。

**境界の単位は「1ユースケース＝1トランザクション」。** 実体は1回の RPC 呼び出し、または1回の Edge Function 呼び出し。

| 論点 | 方針 |
|---|---|
| 複数の呼び出しにまたがる境界 | 作らない |
| 単一テーブルへの1文（INSERT/UPDATE/DELETE/SELECT） | **明示トランザクションを張らない**。PostgreSQL の暗黙トランザクションで足りる |
| 外部I/O（EXT-01 Gemini API） | **トランザクション外**。呼び出しを内側に含めない |
| 補償処理 | 持たない。§3 の二段構えで構造的に不要にする |
| 分散整合（Outbox / Saga） | **いずれも不採用**。関連 ADR-0004 |

### 複数テーブルへの書き込みは RPC に一本化する

**結論: Postgres 関数（RPC）で1文にまとめる（案A）。**

Supabase のクライアントはどちらも PostgREST 経由である。
Flutter の `supabase_flutter` も、Edge Function 内の supabase-js も同じ。

そのため**複数文をまたぐ `BEGIN`〜`COMMIT` をアプリ側から張れない**。選択肢は3つ。

| 案 | 方式 | 評価 |
|---|---|---|
| **A（採用）** | **Postgres 関数（RPC）で1文にまとめる**。`supabase.rpc('...')` で呼ぶ | 関数本体は単一の暗黙トランザクション。原子性が実装者の注意力に依存しない |
| B | 明細を配列で受け、**親を作らず単一 INSERT** にする | 本PJのモデルでは成立しない。親の採番結果を子が参照するため2文が不可避 |
| C | 「親INSERT → 子INSERT → 失敗時に親を DELETE で補償」をアプリ側に置く | 補償の失敗経路が新たに生まれる。孤児行の混入を防ぎきれない。**不採用** |

- 案A の副次的な利点: `SECURITY INVOKER` にすれば RLS が効いたまま使える。
- 案A の副次的な利点: 関数は `supabase/migrations/*.sql` で版管理でき、可逆にできる（`04_移行設計.md §3`）。
- 案A の対象は現時点で FEAT-04（トレーニング記録）の `create_training_session` のみ。
- 対象テーブルは `training_sessions` ＋ `training_session_details`。
- Edge Function 内から書く場合も同じ制約を受ける。Edge Function だからトランザクションが張れるわけではない。

```sql
-- FEAT-04 のセッション＋明細を1トランザクションで作る（関数シグネチャのみ・実装は FEAT-04 の詳細設計）
-- SECURITY INVOKER（既定）とし、RLS を迂回しない
CREATE FUNCTION create_training_session(p_performed_date date, p_menu_ids bigint[])
  RETURNS bigint AS $$ ... $$ LANGUAGE plpgsql;
-- 内部: training_sessions を1行 INSERT → RETURNING id → training_session_details を
--       p_menu_ids の要素数ぶん INSERT（is_done は既定 false ＝ ST-01 / 遷移 T01）
```

- **RPC に置くのは永続化だけ**にする。SQL 関数に業務ロジックを流出させない。
- バリデーション・業務判定（RULE-*）は Dart の純関数に残す（`app/lib/domain/*.dart`）。単体テストの対象とする（NFR-QUAL-01）。
- 追加した関数は `01_DB物理設計.md §3` に無い。DDL への反映要否は ⚠️ 要確認（人間判断）とし本書では追加しない。

### 削除の波及（`ON DELETE` 方針・2026-08-08 確定）

削除の連鎖はアプリのコードで組まない。**FK の `ON DELETE` に寄せる。** 正本は `01_DB物理設計.md §3`。

| FK | ON DELETE | 意図 |
|---|---|---|
| `users.id` → `auth.users(id)` | CASCADE | 退会で本人データを消す |
| `gym_visits.user_id` / `training_menus.user_id` / `training_sessions.user_id` / `meal_logs.user_id` → `users` | CASCADE | 同上 |
| `training_session_details.session_id` → `training_sessions` | CASCADE | セッションを消せば明細も消える |
| `machine_menus.machine_id` → `training_machines` | CASCADE | 紐づけだけが消える。履歴に影響しない |
| `machine_menus.menu_id` → `training_menus` | 同上 | 同上 |
| **`training_session_details.menu_id` → `training_menus`** | **NO ACTION** | **履歴がある種目は物理削除できない**（案a・ADR-0006） |
| `gym_visits.gym_id` → `gyms` | NO ACTION | 履歴を守る |
| `training_machines.gym_id` → `gyms` | NO ACTION | 器具が残るジムは消せない |

読み方は2つだけ。

| 方針 | 対象 | 意味 |
|---|---|---|
| CASCADE | 本人データ・紐づけ | 親を消せば子も消える。孤児行を作らない |
| NO ACTION | 履歴を参照される親 | **親の削除が失敗する**。履歴が壊れるより削除できないほうを選ぶ |

- `NO ACTION` の削除失敗は SQLSTATE **23503**（外部キー違反）で返る。
- PostgREST が返す HTTP は **409**（§1 の写像表・2026-08-08 確定）。400 系ではない。
- 23503 は「使用中のため削除できません」という**業務エラー**として扱う（§1）。500 に落とさない。
- 種目の削除は UI 側でも先に使用有無を確認し、削除できない理由を出す（FEAT-01）。

### 外部I/O（EXT-01）は境界の外に置く ―― 二段構え

AI 呼び出しは数秒〜20秒かかる（NFR-PERF-03/04）。トランザクション内に置くと接続とロックをその間占有する。

本PJでは**呼び出しの分割そのものでこれを構造的に防ぐ**。

| FEAT | 第1段（外部I/Oのみ・DB書き込みなし） | 第2段（DB書き込みのみ・外部I/Oなし） |
|---|---|---|
| FEAT-08 | `supabase.functions.invoke('analyze-meal')`（画像を直接受け取り EXT-01 へ渡して栄養4項目を返すだけ。画像は永続化しない・ADR-0003） | `supabase.from('meal_logs').insert(...)`（栄養4項目を単一 INSERT） |
| FEAT-03 | `supabase.functions.invoke('generate-menu')`（部位＋器具→EXT-01→**今日やる種目の `menu_id` と実施順**を返すだけ） | 保存は行わない（表示のみ）。**種目の登録も行わない**（ADR-0021）。選ばれた `menu_id` は FEAT-04 の記録へ渡す |

- 第1段は業務データを書かない。**トランザクションがそもそも存在しない**。
- 第2段は単一テーブル1文のため明示トランザクションが要らない。
- 両者の間に、整合を取るべき共有状態が無い。
- FEAT-08 の画像は Edge Function のメモリ上のみに存在し、**どこにも永続化しない**（ADR-0003）。
- 直接POSTのため、掃除すべき残骸も生じない。
- これは ADR-0003 の当初方針そのものである。**ADR-0003 の改訂は不要**。
- ~~ADR-0001・ADR-0002・段3 API設計の改訂が要る点は変わらない（§1 の ⚠️）。~~（**解決**・2026-08-08）
- **段3は改訂済み。** `../30_データ・IF設計/02_API設計.md §4.1` が Edge Function `analyze-meal` の契約になっている。ADR-0001・ADR-0002 も Superseded 済み（§1）。
- 第1段成功・第2段失敗のとき、AI の課金は済んでいるが記録は残らない。
- 再解析（再課金）を避けるため、**第1段の結果は Flutter の画面状態に保持し、第2段のみ再送できる UI にする**。
- 上記の UI は `08_機能別詳細設計/FEAT-08_*.md` で具体化する。

状態遷移の永続化タイミング。イベント定義の正本は `../30_データ・IF設計/03_ドメインイベント.md`。

| 遷移 | 永続化のタイミング |
|---|---|
| T01（新規→ST-01） | 上記 RPC の中で明細作成と同時 |
| T02（ST-01→ST-02） | `training_session_details.is_done` の UPDATE 単文（§3 の状態ガード付き） |

### Outbox / Saga を採らない理由

| 理由 | 内容 |
|---|---|
| 更新先が1つ | 書き込み先は Supabase の単一DBのみ。複数データストアにまたがる更新が無い |
| 外部に確定させる連携が無い | EXT-01 は読み取り的な呼び出し。副作用は従量課金だけで、ロールバックすべき外部状態を持たない |
| ディスパッチャを置けない | Outbox は常駐プロセスか定期実行を要する。本PJには非同期基盤が無い（`02_バッチ設計.md`）。導入は NFR-MAINT-01 に反する |

### 「当日」は端末の時刻で判定する（2026-08-08 確定・ADR-0014）

日付を決めるのはアプリ側の責務。**RPC は渡された日付を使うだけ**にする。

| 項目 | 内容 |
|---|---|
| 日付を決める場所 | **Flutter（端末のタイムゾーン）** |
| 渡し方 | RPC の引数に日付を渡す |
| 禁止 | RPC 内で `CURRENT_DATE` を使わない。Supabase は UTC のため |
| 対象 | `meal_logs.eaten_date` の採番／残量のリセット／ヒートマップと「今月」の範囲 |

- `CURRENT_DATE` は UTC の暦日を返す。日本時間の朝9時までが前日に入る。
- 「日付の判定」は業務ロジックである。§2 の原則どおり SQL 関数へ流出させない。
- 対象機能は FEAT-05（ヒートマップ・今月）／FEAT-08（`eaten_date`）／FEAT-09（残量）。
- 海外にいるときは現地の日付で区切られる。これは意図した挙動である。
- 端末の日付を変えられると記録日がずれる。単一利用者のため許容する（ADR-0014）。

## 3. 冪等性
> 📝 ここに冪等性の担保方針を記載。{冪等キーの発行・伝播（`02_API設計.md` の共通ヘッダ）／状態ガード（許可遷移のみ・終端不変）による二重反映防止／重複リクエストの検知・棄却／リトライ安全な操作設計}。二重処理が発生しないことが読み取れるように。

| 対象操作 | 冪等の担保方式 | 根拠 |
|---|---|---|
| 参照系 全般（`get_dashboard`・`get_protein_remaining` の RPC／`training_menus` 等の select） | **自然に冪等**（副作用なし）。何度呼んでもDBを変えない。リトライ安全 | `../30_データ・IF設計/02_API設計.md §1` |
| `create_training_session` RPC の明細登録 | **DB一意制約**。`(session_id, menu_id)` の UNIQUE（`uq_tsd_session_menu`）で同一セッション内の同一種目の二重登録を防ぐ。RPC 内は `ON CONFLICT DO NOTHING` で受け、重複をエラーにしない | `01_DB物理設計.md §2.3・§3` |
| `training_session_details.is_done` の更新（T02） | **状態ガード**。許可遷移 ST-01→ST-02 のみ実行する。2回押されても結果は同一 | `../30_データ・IF設計/03_ドメインイベント.md §2`（T02） |
| `users` の更新（FEAT-06） | **全項目置換の update**。同じ値を何度送っても結果が同一（自然に冪等） | `../30_データ・IF設計/02_API設計.md §3` |
| `analyze-meal`・`generate-menu`（Edge Function） | **非冪等**。冪等キーを持たない。同じ画像・同じ条件でも呼ぶたびに EXT-01 へ課金され、生成結果も一致しない。担保手段は **Flutter 側の二重送信抑止のみ**（§5・実行中はボタンを無効化） | ADR-0001（従量課金・自動リトライなし）・`../30_データ・IF設計/02_API設計.md §1` |
| `meal_logs` への insert（FEAT-08 第2段） | **サーバ側では防げない**。`meal_logs` に自然キーが無く、同一栄養値の食事を2回記録するのは**正当な操作**のため一意制約を張れない。担保は §5 のUI抑止＋「成功時に結果画面を閉じて再送信できなくする」`[仮]` | `01_DB物理設計.md §2.4`（一意制約なし）・下記 ⚠️ |
| `gym_visits` への insert（FEAT-04） | **担保なし**。同日同ジムの重複入館を防ぐ一意制約が無く重複行が入りうる。ヒートマップは実施有無の2値のため表示への影響は無い `[仮]` | `01_DB物理設計.md §2.1` |
| `import_foods` RPC（FEAT-10） | **DB一意制約**。`foods.name` の UNIQUE（`uq_foods_name`）に対し `INSERT … ON CONFLICT (name) DO NOTHING` で追加する。同じCSVを2回流しても結果は同一（NFR-MIGR-02）。既存と同名で値が違う行は**上書きせずスキップ**する | `01_DB物理設計.md §1.5・§3`・`08_機能別詳細設計/FEAT-10_食事マスタCSVインポート.md`・ADR-0007 |

T02 の状態ガードの実装。

| 項目 | 内容 |
|---|---|
| 更新文 | `update({'is_done': true}).eq('id', id).eq('is_done', false)` |
| 既に ST-02 の行 | 更新0件で正常終了する（終端は不変） |

**冪等キー方式は当面採らない。** `../30_データ・IF設計/02_API設計.md §1` は「書き込み系は冪等キー（任意）」としているが、次の2点で成立しない。

| 理由 | 内容 |
|---|---|
| 保存先が無い | サーバ側で「処理済みキー」を保持する場所が `01_DB物理設計.md` に無い |
| 追加できない | 本PJの方針で新テーブルを追加しない |

- **リトライ安全な操作設計の原則**: 自動リトライ（§4）を掛けてよいのは「冪等な操作」に限る。
- 上表で非冪等と判定した操作には、**自動リトライを一切掛けない**。
- **UNIQUE 違反を業務エラーにしない**: 二重登録の防止は「利用者の入力ミス」ではない。
- `uq_tsd_session_menu` 違反は 400 ではなく「無視して成功扱い」とする（`ON CONFLICT DO NOTHING`）。
- Flutter 側へ SQLSTATE 23505 を漏らさない。

> ⚠️ 要確認（人間判断）: `meal_logs` への二重 insert は、テーブル構造上サーバ側で防げない。(a) UI抑止のみで許容するか、(b) 冪等キーを受けるための保存先（新テーブルまたは既存列の転用）を認めるか、(c) 「直近N秒以内の同一栄養値・同一日付の記録は警告する」という業務的な重複検知を入れるか。本書は (a) を `[仮]` としている。

## 4. リトライ
> 📝 ここにリトライの共通方針を記載。{リトライ対象（一時失敗）と非対象（永続失敗）の区別／回数・バックオフ（指数/ジッタ）／上限到達時の扱い（隔離・通知 ERR-__）／外部システムのレート制限との整合}。値の根拠（DEC-ID）を併記。

### リトライのパラメータ

| パラメータ | 値 | 根拠 |
|---|---|---|
| リトライ対象 | 一時失敗のうち **`ERR-AI-RATE`(429) だけ**を Edge Function 内で自動再試行する | ADR-0001（従量課金）・`../30_データ・IF設計/02_API設計.md §1` |
| 対象外の原則 | AI呼び出しそのものは原則として自動リトライしない | 同上「AI呼び出しは非冪等・自動リトライしない。429時のみ指数バックオフ」 |
| 最大回数 | **2回**（初回＋再試行2回＝最大3試行）`[仮]` | DEC未起票。429 はトークンを消費せず即座に返るため回数を許容できる。⚠️ 要確認（人間判断） |
| バックオフ | **指数バックオフ**。初期待機 **1000ms**・乗数 **2.0**（1s → 2s）・総待機上限 **4秒** `[仮]` | DEC未起票。⚠️ 要確認（人間判断） |
| `Retry-After` | 応答にあればその値を優先する | 同上 |
| ジッタ | **付けない** | 単一利用者で群衆同期が起きないため（NFR-SCALE-01） |
| デッドライン | 残余時間が1試行分に満たなければ再試行せず打ち切る | NFR-PERF-03/04 |
| 時間予算 | FEAT-03＝15秒（NFR-PERF-03）／FEAT-08＝20秒（NFR-PERF-04） | NFR-PERF-03/04 |
| 打ち切り方 | Edge Function 側は `AbortSignal.timeout()` で全体を打ち切る | NFR-PERF-03/04 |
| モデルフォールバック | **持たない**（下記）。回数のカウント対象外 | 下記・EXT-01 |
| 上限到達時 | **隔離キューは持たない**（非同期基盤が無いため・`02_バッチ設計.md`）。`ERR-AI-RATE`(429) を `retryable: true` のまま Flutter へ返す | NFR-AVAIL-05・ADR-0001 |
| 上限到達時のUI | SnackBar ＋ `SnackBarAction`（再試行）で**手動再試行**に委ねる。AI機能のみ不可・記録/閲覧は継続 | NFR-AVAIL-05 |

Edge Function の実行時間上限（無料150秒／有料400秒）より画面側の予算のほうが厳しい。打ち切りは常に本表の値で決まる。

### リトライ非対象

永続失敗。再送しても結果が変わらないか、害が大きい。

| 対象 | 理由 |
|---|---|
| `ERR-AI-CREDIT`(402) | 課金設定・クォータを直すまで必ず失敗する |
| `ERR-AI-TIMEOUT`(504) | 再送は二重課金になる。NFR-PERF-03/04 の予算も超える |
| `ERR-VALIDATION-001`(400) | 入力を直さない限り失敗する |
| `ERR-AUTH-001`(401) | 再サインインするまで失敗する |
| DB書き込みの失敗 | 二重登録のリスクがある（§3） |

### `retryable` フラグと「自動リトライ」は別概念

| 概念 | 意味 | 決めるもの |
|---|---|---|
| 応答の `retryable` | **利用者が手動で再試行する価値があるか** | UI に再試行アクションを出すか |
| 自動リトライ | サーバが自分で再送するか | Edge Function の再送処理 |

- `retryable` の正本は `../30_データ・IF設計/02_API設計.md §5`。サーバが自動再送したことを意味しない。
- 例: `ERR-AI-RATE`(429) は `retryable: true` で、**サーバが §4 のバックオフで自動再送する**。
- 例: `ERR-AI-TIMEOUT`(504) は `retryable: false`。自動再送も、UI の再試行アクションも出さない。
- 両者を混同すると二重課金になる。

> ⚠️ 要確認（人間判断）: **`ERR-AI-TIMEOUT` に UI の再試行アクションを出すか**が未決 `[仮]`。現在は `retryable: false` で統一しており、出さない扱いになる。ただしタイムアウトは再試行で成功しうるため、利用者は撮り直しからやり直すことになる。1回の再試行あたり約 $0.01（ADR-0011 の実測）。UX とコストの兼ね合いで決める。同じ論点が `ERR-AI-SCHEMA`(502) にもある。

### モデルフォールバックは持たない

| 項目 | 内容 |
|---|---|
| 現状 | Edge Function は `GEMINI_MODEL`（既定 `gemini-3.5-flash`）を1つだけ呼ぶ。代替モデルへの切替を持たない |
| なぜ持たないか | 自動切替を担っていたゲートウェイ層が構成から無くなったため。同等の機能は Edge Function 内に自前で実装するしかない |
| 実装するなら | `try` で既定モデル → 失敗時に代替モデルで1回だけ呼び直す、を Edge Function 内に書く。所要時間が単純加算され NFR-PERF-03/04 を超えやすくなる `[仮]` |
| 現在の縮退 | モデル1本が失敗したら、そのまま `ERR-AI-FAIL` で縮退する（NFR-AVAIL-05） |

- 外部送信の記録（NFR-SEC-AUDIT-01）には**実際に応答したモデルID**を残す。
- 自前フォールバックを入れた場合は、どちらのモデルで応答したかが分かるようにする。

### 記録と、Flutter 側の自動リトライ禁止

- 自動リトライしたら**試行ごとに1行ログを出す**（試行番号・待機時間・ERR-ID・相関ID）。
- 「静かに2回呼んだ」状態を作らない（§1 握り潰し禁止）。
- **Flutter 側の自動リトライは実装しない。** Edge Function 側と二重になり、課金が掛け算になるため。
- 参照系の再取得のみ、利用者操作（引き下げ更新・再試行アクション）を起点に行う。
- 通信断やアプリのバックグラウンド遷移で `functions.invoke` の応答を取りこぼしても、**自動では投げ直さない**。
- 課金済みの可能性があるため、利用者に再実行させる。

## 5. 多重制御・排他
> 📝 ここに同時実行・多重処理の制御方針を記載。{直列化が必要な処理と同時実行の上限／排他の手段（分散ロック・FIFOキュー・処理中フラグ）／多重ディスパッチ防止（`is_processing` 等）／スタック検知と救済／冪等（§3）との役割分担}。関連DEC-__。

### 直列化・排他は採らない

**分散ロックも FIFOキューも処理中フラグも置かない。** 前提は次の2点。

| 前提 | 根拠 |
|---|---|
| 利用者は岡田さん1名。同一行への同時書き込みが実質起きない | NFR-SCALE-01（マルチテナント適用外） |
| 行レベルの同時更新は PostgreSQL の既定の行ロック＋§3 の状態ガードで足りる | §3 |

不採用にするものと、その理由。

| 手段 | 不採用の理由 | 根拠 |
|---|---|---|
| 分散ロック | 解放漏れという新しい障害モードを持ち込む。個人保守に見合わない | NFR-MAINT-01 |
| FIFOキュー | ワーカー基盤が要る。本PJに非同期基盤が無い | NFR-MAINT-01・`02_バッチ設計.md` |
| `is_processing` フラグ | 該当列が無く、列を追加しない方針。競合の実測母数も無い | `01_DB物理設計.md` |

### 実際に必要な多重制御は2点のみ

| # | 対象 | 手段 | 目的 |
|---|---|---|---|
| 1 | 二重送信防止 | **Flutter 側でボタンを無効化する。** 実行中フラグを持ち `onPressed: busy ? null : submit` とする | **非冪等な操作の唯一の担保手段**（§3）。二重タップ＝二重課金・二重登録に直結する |
| 1 | 同上（適用範囲） | 完了・失敗まで再実行を受け付けない。フォーム送信も同じフラグで抑止する | 対象は `analyze-meal`・`generate-menu`・`meal_logs` の insert |
| 2 | AI呼び出しの上限 | **アプリ側では実装しない。Gemini API の日次クォータに委ねる。** 超過は `ERR-AI-QUOTA`(429) | コスト暴走の防止（下記・NFR-SEC-05） |

- 二重送信抑止は**アプリ側にしか無い**。アプリを再インストールされても、別端末から呼ばれても効かない。
- JWT さえあれば Edge Function は呼べる。アプリ側に上限が無いため、ここは日次クォータが最後の砦になる。
- レート制限（#2）の実装先は **(c) 実装しない で確定**（下記）。

**参照系の連打**（部位の高速切替など）は排他ではなく**古い応答の破棄**で扱う。

- Dart の `Future` はキャンセルできない。代わりにリクエストへ発行順の連番を持たせる。
- **最新でない応答を捨てて**、最後の操作の結果だけを描画する。
- 実装例は `08_機能別詳細設計/FEAT-02_部位選択と器具絞り込み.md §7`。

**スタック救済は本PJでは該当なし。**

| 理由 | 内容 |
|---|---|
| 放置される状態が無い | 非同期ジョブ・処理中フラグ・キューを一切持たない（`02_バッチ設計.md`） |
| 後始末が要らない | Edge Function は実行終了とともにメモリごと解放される（ADR-0003 と同じ性質） |
| よって | タイムアウト検知・再ディスパッチの機構も不要 |

**冪等（§3）との役割分担。**

| 節 | 役割 | 手段 |
|---|---|---|
| §3 | 同じ操作が2回届いたときに、結果を1回分に収める | DB一意制約・状態ガード |
| §5 | そもそも2回届かせない | UI抑止（レート制限は持たない） |

- 参照系と DB 書き込みは §3 で守れる。
- **AI呼び出しは §3 で守れない**（冪等キーを持てない・非冪等）。§5 の #1 が唯一の防波堤になる。

### レート制限の実装先

**(c) 実装しない で確定した**（2026-08-08）。Edge Function はリクエストごとに独立して起動するため、関数内のインメモリカウンタは機能しない。候補は3つあった。

| 案 | 方式 | 得られるもの | 引き換えに要るもの | 採否 |

| (b) | **Supabase の組み込み制限に依存する**（プロジェクト側のリクエスト上限） | アプリ実装が不要 | AI呼び出しだけを狙って絞れるかは未確認 | **不採用** |
| (c) | **実装しない**。当面は許容する | 実装コストがゼロ | 単一利用者かつ TestFlight 配布で悪用経路が乏しい、という前提への依存 | **採用** |
