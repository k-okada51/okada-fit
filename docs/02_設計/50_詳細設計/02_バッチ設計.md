# バッチ設計 — okada-fit（定期実行バッチ・非同期ジョブは存在しない）

> **目的**: 定期実行・非同期処理（ポーリング・再送・集計・アーカイブ等）の実装設計を、トリガ・処理内容・例外/リトライ・多重制御まで実装が迷わない粒度で固定する。
> **書き方**:（記入例は example-suido-fax の対応ファイル参照）実データは書かず、`{ }` を自プロジェクトの語に置き換える。**正本は要件定義（FEAT/状態）**とし、状態イベントは `30_データ・IF設計/03_ドメインイベント.md`、外部照会IFは `03_外部連携IF/README.md` を参照。関連DECを併記する。

> ⚠️ **本書はたたき台（2026-08-02 生成・2026-08-07 改訂）**。岡田さんのレビューで確定する。**本PJには定期実行バッチ・非同期ジョブが1つも存在しない**。本書は「無いこと」と「その根拠」、および「将来必要になる条件」を記録するために置く（節は削除せず該当なしで埋める）。前提は Flutter アプリ＋ Supabase（Edge Functions / PostgreSQL / Storage）。**Vercel は使わない**（2026-08-07 決定）。

| 項目 | 内容 |

| 実行基盤 | 本PJでは該当なし（Supabase pg_cron・Edge Function の Scheduled 実行のいずれも採用しない） |
| トリガ（起動間隔） | 本PJでは該当なし（**全処理がユーザー操作起点の同期処理**。FEAT-01〜10 のいずれも1回の呼び出しで完結し、応答後に走る処理を持たない） |
| 処理対象（抽出条件） | 本PJでは該当なし（未終端の状態を溜める「処理待ち行列」が存在しない。永続状態は `training_session_details.is_done`（ST-01/ST-02）のみで、遷移は利用者のチェック操作でのみ起きる） |

| 多重制御 | 本PJでは該当なし（非同期ディスパッチが無いため多重ディスパッチも起きない。UIの二重送信防止とAI呼び出しのレート制限は `07_実装共通設計パターン.md §5` を正本とする） |

**なぜバッチが無いのか（根拠）**

| # | 一般にバッチが要る理由 | 本PJで不要な根拠 |
|---|---|---|
| 1 | 保持期間を過ぎたデータの定期削除 | **データ保持期間の制限を設けない**（全履歴を保持）。当初検討された「3ヶ月で削除」は撤回済み（`../30_データ・IF設計/01_データモデル.md §7`・同 §8-7）。削除対象が発生しない |
| 2 | 画像・添付ファイルの定期削除 | **食事写真を永続化しない**（ADR-0003）。Storage は保管庫ではなく転送路で、Edge Function が推論を終えた時点で同じ処理内で削除する。溜まるものが無い（下記 ⚠️） |
| 3 | 通知・リマインドのプッシュ配信 | 通知はすべて**画面内の SnackBar**（`ScaffoldMessenger`）で、利用者が操作している最中にのみ出る。プッシュ通知・メール送信の要件が無い（`../30_データ・IF設計/03_ドメインイベント.md §4`） |
| 4 | 集計テーブルの事前作成（夜間バッチ） | ダッシュボード（FEAT-05）・タンパク質残量（FEAT-09）は**呼び出しのたびに RPC で都度集計**する。個人利用でデータ量が小さく（NFR-SCALE-01：マルチテナント適用外）、`ix_meal_logs_user_date` 等の複合INDEXで NFR-PERF-01（≤2秒）を満たせる見込み |
| 5 | 外部連携の非同期化（ポーリング・再送） | EXT-01（Gemini API）は**同期呼び出し**で、Edge Function の実行内に応答が返る（NFR-PERF-03 ≤15秒／NFR-PERF-04 ≤20秒）。結果待ち行列・再送キューを持たない。失敗時は縮退して利用者の手動再試行に委ねる（NFR-AVAIL-05・`07_実装共通設計パターン.md §4`） |
| 6 | 大量データの一括処理 | 唯一これに近いのが FEAT-10 の食事マスタCSVインポートだが、**定期実行ではなくユーザー操作起点の一括処理**（下記） |

> ⚠️ 要確認（人間判断）: #2 の「削除は同じ処理内で行うから溜まらない」は、削除が必ず成功する前提に立っている。Edge Function が推論後に落ちた場合、`meal-photos` バケットに写真が残る。(a) 残骸を許容する、(b) Storage のライフサイクル設定で自動削除する、(c) 掃除バッチ（pg_cron）を1本だけ持つ、のいずれを採るか。ADR-0003（写真を保持しない）との整合上、放置は選べない。

**バッチに最も近い処理＝FEAT-10 食事マスタCSVインポート（バッチではない）**

CSVのパースは Flutter 側で行い、結果を `replace_foods` RPC に渡して一括投入する。バッチの設計項目はいずれも当てはまらない。

| 本書の設計項目 | FEAT-10 での該当 |
|---|---|
| 実行基盤（スケジューラ） | 無い。利用者が SCR-05 でファイルを選んで実行する |
| 起動間隔 | 無い |
| 抽出条件 | 無い（対象は利用者が選んだファイルそのもの） |
| 多重ディスパッチ制御 | 無い。二重送信抑止は UI 側（`07_実装共通設計パターン.md §5`） |

- 処理内容・分割・エラー行の扱い・件数照合・冪等性（再取込）は `08_機能別詳細設計/FEAT-10_食事マスタCSVインポート.md` を正本とする。**本書では再定義しない。**
- 初期データ投入という観点での位置づけは `04_移行設計.md §2`（NFR-MIGR-02）を参照。
- 性能目標は NFR-PERF-05（数百件を ≤5秒）。同期処理のため、これを超える件数を扱う必要が出た時点で「非同期化＝バッチ導入」の検討トリガになる（下表 #3）。

**将来バッチが必要になる条件と、その際の実行基盤候補**

実行基盤の候補は**2つだけ**。Vercel Cron Jobs は構成から消えたため使えない。

| 候補 | 何ができるか | 向く用途 |
|---|---|---|
| **Supabase pg_cron** | DB内でSQLを定時実行する。アプリを経由しない | 削除・集計など、SQLだけで完結する処理 |
| **Edge Function の Scheduled 実行** | Deno/TS のコードを定時実行する | 外部API呼び出し・整形が要る処理 |

| # | 条件（トリガ） | 必要になる処理 | 実行基盤の候補 |
|---|---|---|---|
| 1 | データ保持期間を設ける決定がされた（`../30_データ・IF設計/01_データモデル.md §8-7` の撤回を再撤回する） | 保持期間超過レコードの定期削除 | **pg_cron** `[仮]` |
| 2 | Storage に写真の残骸が溜まることが判明した（上記 ⚠️） | 一定時間より古い `meal-photos` の掃除 | **pg_cron**（Storage のメタデータ経由）または **Scheduled Edge Function** `[仮]` |
| 3 | 週次/月次のサマリー通知を入れる（「今週は目標の何%」等） | 集計＋プッシュ/メール送信 | **Scheduled Edge Function** `[仮]`。別途、通知チャネル（メール／プッシュ通知基盤）の追加が要る |
| 4 | AI解析を非同期化する（NFR-PERF-04 の20秒に収まらない／ストリーミングでも足りない場合） | ジョブ登録 → 定時実行で EXT-01 呼び出し → 結果保存 → アプリへ反映 | **Scheduled Edge Function** によるポーリング `[仮]`。**ジョブ状態を持つテーブルの新設が必須**になり `01_DB物理設計.md` の改訂を伴う |
| 5 | CSVインポート件数が NFR-PERF-05 の想定（数百件）を大きく超える | 分割投入・進捗表示・再開 | 同上（#4 と同じ基盤・状態テーブルが要る） |
| 6 | マルチユーザー化（NFR-SCALE-01 の Phase2） | 全ユーザー横断の集計・定期メンテナンス | **pg_cron** / **Scheduled Edge Function** `[仮]` |

> ⚠️ 要確認（人間判断）: 上表はいずれも現時点で**採用しない**前提の候補列挙。pg_cron の有効化可否（拡張の利用可否）と、無料枠での実行回数・実行時間の制限は未調査のため `[仮]`。実際に必要になった時点で ADR を起票して確定する。

## 2. 処理ロジック
> 📝 ここに1回の起動で行う処理を擬似コード/箇条書きで記載。対象抽出→各対象の処理分岐→状態遷移→次回への持ち越し、を明示する。%% ここに記載（実データは書かない）

```
本PJでは該当なし（定期実行バッチが存在しないため、1回の起動で行う処理も存在しない）

# 以下は「将来バッチを導入する場合の骨格」であり、現時点の実装対象ではない。
# §1 の「将来バッチが必要になる条件」#1〜#6 のいずれかが発生した時点で、
# ADR を起票したうえで本節を実装対象として具体化する。
#
# スケジューラ（pg_cron / Scheduled Edge Function）→ 処理本体:
#   対象抽出 = 未終端レコードの抽出            ← 本PJには未終端の待ち行列が無い
#   各対象:
#     排他フラグ = true（多重ディスパッチ防止）  ← 該当列が 01_DB物理設計.md に無い（要スキーマ変更）
#     処理 → 結果分岐 → 状態遷移
#   スタック救済: 排他フラグがしきい値を超えて放置 → false へリセット
```

- 現在、応答を返した後に走り続ける処理は1つも無い。Edge Function は「JWT検証 → 検証 → DB/EXT-01 → 応答」で完結する（順序の正本は `07_実装共通設計パターン.md §1`）。
- PostgREST・RPC の直接呼び出しも、1回の呼び出しで完結して終わる。
- FEAT-10 のCSVインポートは Flutter でのパース＋ `replace_foods` RPC の呼び出しであり、疑似コードは `08_機能別詳細設計/FEAT-10_食事マスタCSVインポート.md` を正本とする。

## 3. 例外・リトライ・多重制御
> 📝 ここに例外事象ごとの判定条件・振る舞い・状態/エラーを記載。{事象／判定条件／振る舞い／ST・ERR}

| 事象 | 判定 | 振る舞い | ST/ERR |
|---|---|---|---|
| 結果待ちタイムアウト | 本PJでは該当なし（結果待ち行列が無い） | 同等の関心事は**Edge Function の実行内**で処理する。EXT-01 の応答が予算（NFR-PERF-03/04）を超えたら `AbortSignal` で打ち切り、その場で利用者へ返す | `ERR-AI-TIMEOUT`(504)（`../30_データ・IF設計/02_API設計.md §5`）。ST遷移なし |
| 多重ディスパッチ | 本PJでは該当なし（ディスパッチする主体が無い） | 同等の関心事は**Flutter 側の二重送信防止**（実行中はボタンを無効化）。正本は `07_実装共通設計パターン.md §5` | — |
| 処理中スタック | 本PJでは該当なし（`is_processing` 相当の処理中フラグを持たず、`01_DB物理設計.md` にも該当列が無い） | 構造的に発生しない。Edge Function は実行終了とともに解放されるため、放置される「処理中」状態が残らない | — |
| 継続据え置き | 本PJでは該当なし（次回起動へ持ち越す概念が無い） | 失敗は持ち越さずその場で利用者へ返し、手動再試行に委ねる（縮退＝AI機能のみ不可・記録/閲覧は継続・NFR-AVAIL-05） | `ERR-AI-RATE`(429) / `ERR-AI-FAIL`(500) |

- 間隔・回数の根拠: 本PJでは該当なし（起動間隔・ポーリング回数を持たない）。同期処理側のリトライ値（429時の最大2回・初期待機1秒・乗数2.0＝いずれも `[仮]`）とその根拠は `07_実装共通設計パターン.md §4` を正本とする。
- リトライ対象/非対象: 本書では定義しない。**正本は `07_実装共通設計パターン.md §4`**（一時失敗＝`ERR-AI-RATE` のみ自動再試行／永続失敗＝`ERR-AI-CREDIT`・400/401 系は再送しない）。

## 4. 状態確定と結果反映
> 📝 ここに終端状態への確定と結果反映の流れを記載。冪等（状態ガード・許可遷移のみ・終端不変）で二重反映を防ぐ点を明示する。{結果／遷移ID／反映先／冪等の担保}

**本PJでは該当なし**（バッチによる状態確定は行わない）。本PJの状態遷移は、すべて**ユーザー操作起点の同期処理**で確定する。

- （新規）→ **ST-01 `not_done`**（遷移 **T01**）: FEAT-04 のトレーニング記録時に、`create_training_session` RPC が `training_session_details` を `is_done = false` で作成して確定する。反映先はヒートマップの実施有無（FEAT-05）。冪等の担保は `(session_id, menu_id)` UNIQUE（`uq_tsd_session_menu`）。
- ST-01 → **ST-02 `done`**（遷移 **T02**）: 利用者が明細の実行済をチェックした時点で確定する。反映先はダッシュボード更新＋保存完了の SnackBar。冪等の担保は**状態ガード**（`is_done = false` の行だけを更新対象にする・終端は不変・2回押しても結果同一）。
- 食事解析（FEAT-08）・入館記録（FEAT-04）・CSV取込（FEAT-10）は**状態を持たない一過性イベント**で、終端状態への確定という概念自体が無い（`../30_データ・IF設計/03_ドメインイベント.md §2・§3`）。
- 状態・遷移の定義の正本は `../30_データ・IF設計/03_ドメインイベント.md`、冪等の担保方式の正本は `07_実装共通設計パターン.md §3`。**本書では再定義しない。**
