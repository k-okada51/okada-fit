# バッチ設計 — okada-fit（定期実行バッチ・非同期ジョブは存在しない）

> **目的**: 定期実行・非同期処理（ポーリング・再送・集計・アーカイブ等）の実装設計を、トリガ・処理内容・例外/リトライ・多重制御まで実装が迷わない粒度で固定する。
> **書き方**:（記入例は example-suido-fax の対応ファイル参照）実データは書かず、`{ }` を自プロジェクトの語に置き換える。**正本は要件定義（FEAT/状態）**とし、状態イベントは `30_データ・IF設計/03_ドメインイベント.md`、外部照会IFは `03_外部連携IF/README.md` を参照。関連DECを併記する。

> ⚠️ **本書はたたき台（2026-08-02 生成／2026-08-07 改訂）**。岡田さんのレビューで確定する。
> - 本書は「バッチが無いこと」「その根拠」「将来必要になる条件」を記録するために置く
> - テンプレの節は削除せず、**該当なし**と明記して埋める
> - 前提は Flutter アプリ ＋ Supabase（Edge Functions / PostgreSQL）
> - **Vercel は使わない**（2026-08-07 決定）

**結論: 本PJに定期実行バッチ・非同期ジョブは1本も無い。** 全機能（FEAT-01〜10）がユーザー操作起点の同期処理で完結する。

## 1. 概要
> 📝 ここにバッチの実行基盤・起動条件・対象・目的を記載。{実行基盤（スケジューラ→ワーカー等）／起動間隔（DEC-__）／処理対象（抽出条件）／目的／多重制御方式}

### 1.1 バッチの有無

| 項目 | 本PJでの扱い |
|---|---|
| バッチ名 | 該当なし。定期実行バッチを1本も持たない |
| 実行基盤 | 該当なし。pg_cron・Scheduled Edge Function のいずれも採用しない |
| トリガ（起動間隔） | 該当なし。**全処理がユーザー操作起点の同期処理** |
| 処理対象（抽出条件） | 該当なし。未終端の状態を溜める「処理待ち行列」が無い |
| 目的 | 該当なし |
| 多重制御 | 該当なし。非同期ディスパッチが無く、多重ディスパッチも起きない |

- FEAT-01〜10 はいずれも1回の呼び出しで完結する。応答後に走る処理を持たない。
- 永続状態は `training_session_details.is_done`（ST-01/ST-02）だけ。遷移は利用者のチェック操作でのみ起きる。
- UIの二重送信防止とAI呼び出しのレート制限は `07_実装共通設計パターン.md §5` が正本。

### 1.2 なぜバッチが無いのか（根拠）

| # | 一般にバッチが要る理由 | 本PJで不要な根拠 | 補足 |
|---|---|---|---|
| 1 | 保持期間を過ぎたデータの定期削除 | **データ保持期間の制限を設けない**（全履歴を保持）。削除対象が発生しない | 当初の「3ヶ月で削除」は撤回済み（`../30_データ・IF設計/01_データモデル.md §7`・同 §8-7） |
| 2 | 画像・添付ファイルの定期削除 | **食事写真を永続化しない**（ADR-0003）。**溜まるファイルがそもそも存在しない** | Flutter から Edge Function へ直接POST。関数のメモリ上でのみ扱う |
| 3 | 通知・リマインドのプッシュ配信 | 通知はすべて**画面内の SnackBar**（`ScaffoldMessenger`）。プッシュ・メールの要件が無い | 利用者が操作している最中にのみ出る（`../30_データ・IF設計/03_ドメインイベント.md §4`） |
| 4 | 集計テーブルの事前作成（夜間バッチ） | ダッシュボード（FEAT-05）・タンパク質残量（FEAT-09）は**都度 RPC で集計**する | 個人利用でデータ量が小さい（NFR-SCALE-01）。`ix_meal_logs_user_date` 等でNFR-PERF-01（≤2秒）を満たす見込み |
| 5 | 外部連携の非同期化（ポーリング・再送） | EXT-01（Gemini API）は**同期呼び出し**。結果待ち行列・再送キューを持たない | 応答は Edge Function の実行内に返る（NFR-PERF-03 ≤15秒／NFR-PERF-04 ≤20秒） |
| 6 | 大量データの一括処理 | 唯一近いのが FEAT-10 のCSVインポート。**定期実行ではなく操作起点**（§1.3） | 性能目標は NFR-PERF-05 |

- #2 は**オブジェクトストレージを使わない**ため、掃除すべき残骸が生まれない。
- #5 の失敗時は縮退し、利用者の手動再試行に委ねる（NFR-AVAIL-05・`07_実装共通設計パターン.md §4`）。

### 1.3 バッチに最も近い処理＝FEAT-10 食事マスタCSVインポート（バッチではない）

CSVのパースと正規化は Flutter 側で行う。結果を `import_foods` RPC に渡して一括投入する（追加＋重複スキップ）。バッチの設計項目はいずれも当てはまらない。

| 本書の設計項目 | FEAT-10 での該当 |
|---|---|
| 実行基盤（スケジューラ） | 無い。利用者が SCR-05 でファイルを選んで実行する |
| 起動間隔 | 無い |
| 抽出条件 | 無い（対象は利用者が選んだファイルそのもの） |
| 多重ディスパッチ制御 | 無い。二重送信抑止は UI 側（`07_実装共通設計パターン.md §5`） |

- 処理内容・分割・エラー行の扱い・件数照合・冪等性（再取込）は `08_機能別詳細設計/FEAT-10_食事マスタCSVインポート.md` が正本。**本書では再定義しない。**
- 初期データ投入という観点での位置づけは `04_移行設計.md §2`（NFR-MIGR-02）を参照。
- 性能目標は NFR-PERF-05（数百件を ≤5秒）。これを超える件数が要るなら「非同期化＝バッチ導入」の検討トリガになる（§1.4 の #4）。

### 1.4 将来バッチが必要になる条件と実行基盤候補

実行基盤の候補は**2つだけ**。Vercel Cron Jobs は構成から消えたため使えない。

| 候補 | 何ができるか | 向く用途 |
|---|---|---|
| **Supabase pg_cron** | DB内でSQLを定時実行する。アプリを経由しない | 削除・集計など、SQLだけで完結する処理 |
| **Edge Function の Scheduled 実行** | Deno/TS のコードを定時実行する | 外部API呼び出し・整形が要る処理 |

| # | 条件（トリガ） | 必要になる処理 | 実行基盤の候補 |
|---|---|---|---|
| 1 | データ保持期間を設ける決定がされた | 保持期間超過レコードの定期削除 | **pg_cron** `[仮]` |
| 2 | 週次/月次のサマリー通知を入れる | 集計 ＋ プッシュ/メール送信 | **Scheduled Edge Function** `[仮]` |
| 3 | AI解析を非同期化する | ジョブ登録 → 定時実行で EXT-01 → 結果保存 → アプリへ反映 | **Scheduled Edge Function** のポーリング `[仮]` |
| 4 | CSV件数が NFR-PERF-05 の想定（数百件）を大きく超える | 分割投入・進捗表示・再開 | 同上（#3 と同じ基盤） |
| 5 | マルチユーザー化（NFR-SCALE-01 の Phase2） | 全ユーザー横断の集計・定期メンテナンス | **pg_cron** / **Scheduled Edge Function** `[仮]` |

- #1 の条件は `../30_データ・IF設計/01_データモデル.md §8-7` の撤回を再撤回すること。
- #2 は別途、通知チャネル（メール／プッシュ通知基盤）の追加が要る。
- #3 の条件は NFR-PERF-04 の20秒に収まらず、ストリーミングでも足りない場合。
- #3・#4 は**ジョブ状態を持つテーブルの新設が必須**。`01_DB物理設計.md` の改訂を伴う。

> ⚠️ 要確認（人間判断）: 上表はいずれも現時点で**採用しない**前提の候補列挙。
> - pg_cron の有効化可否（拡張の利用可否）は未調査 `[仮]`
> - 無料枠での実行回数・実行時間の制限も未調査 `[仮]`
> - 実際に必要になった時点で ADR を起票して確定する

## 2. 処理ロジック
> 📝 ここに1回の起動で行う処理を擬似コード/箇条書きで記載。対象抽出→各対象の処理分岐→状態遷移→次回への持ち越し、を明示する。%% ここに記載（実データは書かない）

**該当なし。** 定期実行バッチが無いため、1回の起動で行う処理も無い。フェンスは将来導入する場合の骨格として残す。

```
本PJでは該当なし（定期実行バッチが存在しないため、1回の起動で行う処理も存在しない）

# 以下は「将来バッチを導入する場合の骨格」であり、現時点の実装対象ではない。
# §1 の「将来バッチが必要になる条件」#1〜#5 のいずれかが発生した時点で、
# ADR を起票したうえで本節を実装対象として具体化する。
#
# スケジューラ（pg_cron / Scheduled Edge Function）→ 処理本体:
#   対象抽出 = 未終端レコードの抽出            ← 本PJには未終端の待ち行列が無い
#   各対象:
#     排他フラグ = true（多重ディスパッチ防止）  ← 該当列が 01_DB物理設計.md に無い（要スキーマ変更）
#     処理 → 結果分岐 → 状態遷移
#   スタック救済: 排他フラグがしきい値を超えて放置 → false へリセット
```

- 現在、応答を返した後に走り続ける処理は1つも無い。
- Edge Function は「JWT検証 → 検証 → DB/EXT-01 → 応答」で完結する（順序の正本は `07_実装共通設計パターン.md §1`）。
- PostgREST・RPC の直接呼び出しも、1回の呼び出しで完結して終わる。
- FEAT-10 のCSVインポートは Flutter でのパース ＋ `import_foods` RPC の呼び出し。
- その疑似コードの正本は `08_機能別詳細設計/FEAT-10_食事マスタCSVインポート.md`。

## 3. 例外・リトライ・多重制御
> 📝 ここに例外事象ごとの判定条件・振る舞い・状態/エラーを記載。{事象／判定条件／振る舞い／ST・ERR}

**4事象とも本PJでは該当なし。** 同等の関心事をどこで処理するかを示す。

| 事象 | 該当なしの理由 | 同等の関心事の処理先 | ST/ERR |
|---|---|---|---|
| 結果待ちタイムアウト | 結果待ち行列が無い | **Edge Function の実行内**。予算（NFR-PERF-03/04）超過で `AbortSignal` 打ち切り | `ERR-AI-TIMEOUT`(504)。ST遷移なし |
| 多重ディスパッチ | ディスパッチする主体が無い | **Flutter 側の二重送信防止**（実行中はボタンを無効化） | — |
| 処理中スタック | `is_processing` 相当の処理中フラグを持たない | 構造的に発生しない。Edge Function は実行終了とともに解放される | — |
| 継続据え置き | 次回起動へ持ち越す概念が無い | 失敗は持ち越さずその場で返し、**手動再試行**に委ねる | `ERR-AI-RATE`(429) / `ERR-AI-FAIL`(500) |

- ERR の正本は `../30_データ・IF設計/02_API設計.md §5`。
- 処理中フラグに相当する列は `01_DB物理設計.md` にも無い。
- 縮退は「AI機能のみ不可・記録／閲覧は継続」（NFR-AVAIL-05）。
- 二重送信防止の正本は `07_実装共通設計パターン.md §5`。

**間隔・回数の根拠**

| 項目 | 本PJでの値 | 正本 |
|---|---|---|
| 起動間隔・ポーリング回数 | 該当なし（持たない） | — |
| 同期処理側のリトライ値 | 429時 最大2回・初期待機1秒・乗数2.0（いずれも `[仮]`） | `07_実装共通設計パターン.md §4` |
| 自動再試行の対象 | 一時失敗＝`ERR-AI-RATE` のみ | 同上 |
| 自動再試行の対象外 | 永続失敗＝`ERR-AI-CREDIT`・400/401 系 | 同上 |

## 4. 状態確定と結果反映
> 📝 ここに終端状態への確定と結果反映の流れを記載。冪等（状態ガード・許可遷移のみ・終端不変）で二重反映を防ぐ点を明示する。{結果／遷移ID／反映先／冪等の担保}

**本PJでは該当なし。** バッチによる状態確定は行わない。状態遷移はすべて**ユーザー操作起点の同期処理**で確定する。

| 遷移 | いつ確定するか | 反映先 | 冪等の担保 |
|---|---|---|---|
| （新規）→ **ST-01 `not_done`**（**T01**） | FEAT-04 の記録時。`create_training_session` RPC が `is_done = false` で明細を作成 | ヒートマップの実施有無（FEAT-05） | `(session_id, menu_id)` UNIQUE（`uq_tsd_session_menu`） |
| ST-01 → **ST-02 `done`**（**T02**） | 利用者が明細の実行済をチェックした時点 | ダッシュボード更新 ＋ 保存完了の SnackBar | **状態ガード**（`is_done = false` の行だけを更新） |

- 状態ガードは終端不変。2回押しても結果は同一になる。
- 食事解析（FEAT-08）・入館記録（FEAT-04）・CSV取込（FEAT-10）は**状態を持たない一過性イベント**。
- 上記3件には終端状態への確定という概念自体が無い（`../30_データ・IF設計/03_ドメインイベント.md §2・§3`）。
- 状態・遷移の定義の正本は `../30_データ・IF設計/03_ドメインイベント.md`。
- 冪等の担保方式の正本は `07_実装共通設計パターン.md §3`。**本書では再定義しない。**
