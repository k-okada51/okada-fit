# 機能別詳細設計 — 索引＋共通

> **目的**: 段5（詳細設計）のうち、**FEAT単位**の実装設計を1機能=1ファイルで固定する。段4（`../../40_機能設計/01_シーケンス設計.md`）が「振る舞いの流れ」を担うのに対し、本フォルダは**入出力の実装レベル契約・バリデーション・クエリ・エラー・画面挙動・実装単位**まで踏み込み、AIが読んで実装できる粒度にする。
> **書き方**: 実データは書かない。上位の正本（API契約＝`../../30_データ・IF設計/02_API設計.md` ／ 物理DB＝`../01_DB物理設計.md` ／ シーケンス＝`../../40_機能設計/01_シーケンス設計.md`）と矛盾させず、参照はIDで行う。横断方針（エラー分類・トランザクション境界・冪等・リトライ・多重制御）は `../07_実装共通設計パターン.md` を正本とし、各機能ファイルで再定義しない。

> ⚠️ **本フォルダはたたき台（2026-08-02 生成 / 2026-08-07 脱Vercel改訂）**。岡田さんのレビューで確定する。各ファイルの §10 に敵対的検証の指摘を残してあるので、**先に §10 だけを横断で読む**と論点が把握できる。

> ⚠️ **Vercel は使わない**（2026-08-07 決定）。クライアントは Flutter、サーバは Supabase。
> ADR-0001（Vercel AI Gateway）・ADR-0002（Next.js + Mantine）・`../../30_データ・IF設計/02_API設計.md`（`/api/*` 契約）は**まだ Vercel 前提のまま**。後継ADRの起票と段3の改訂が要る。

## 構成

```
Flutter アプリ（Dart・iOS先行・TestFlight配布）
  └ supabase_flutter
      ├ Auth              サインイン・JWT保持
      ├ PostgREST         テーブルを直接CRUD（RLSで保護）
      ├ Storage           食事写真の一時置き場（推論後に即削除）
      └ Functions.invoke  Edge Function 呼び出し

Supabase
  ├ Auth / PostgreSQL + RLS / Storage
  └ Edge Functions（Deno）
      └ Google Gemini API を直接呼ぶ（APIキーは環境変数）
```

呼び出し方式は3つに分かれる。

| 方式 | 使う場面 | 該当FEAT |
|---|---|---|
| PostgREST 直接 | 単純なCRUD | 01・02・06・08（保存） |
| RPC（Postgres関数） | 集計・複数テーブルの一括更新 | 04・05・09・10 |
| Edge Function | AIを呼ぶとき | 03・08（解析） |

**AIを呼ぶ機能だけ Edge Function を経由する。** APIキーを端末に置かないため（NFR-SEC-02）。

## 共通の約束（各ファイルはこれに従う）

### ID・エラーコード
- ERRの共通コード（`ERR-AUTH-001` / `ERR-VALIDATION-001` / `ERR-AI-CREDIT` / `ERR-AI-RATE` / `ERR-AI-TIMEOUT` / `ERR-AI-FAIL`）の正本は `../../30_データ・IF設計/02_API設計.md §5`。
- 機能固有のERRは `ERR-{DOMAIN}-{3桁}` で、機能ごとにドメイン接頭辞を割り当てて衝突を避けている（`ERR-MACHINE-*` / `ERR-MENU-*` / `ERR-TRAINING-*` / `ERR-DASHBOARD-*` / `ERR-PROFILE-*` / `ERR-MEAL-*` / `ERR-PROTEIN-*` / `ERR-FOOD-*`）。
- **ERR・ST・受入基準の完全な母集合は段6**（`../../60_テスト設計/02_RED母集合_受入基準・状態・エラー.md`）に集約する。本フォルダの §6・§9 はその**入力**であり正本ではない。

### 状態
- 本PJで永続する状態は `training_session_details.is_done`（ST-01 未実行 / ST-02 実行済）**のみ**。他機能は状態を持たない一過性の記録イベント（`../../30_データ・IF設計/03_ドメインイベント.md`）。

### 認証・分離
- 全APIが Supabase Auth による認証必須。DB側は RLS で本人行のみ（ADR-0004）。
- `foods`（食品マスタ）だけは `user_id` を持たない共通マスタで、RLS の扱いが他テーブルと異なる。

> ⚠️ 要確認（人間判断）: `users.id`（bigint）と Supabase `auth.uid()`（uuid）の紐付け方式が未確定。各機能ファイルはこの方式を決めず、正本の `../06_DB設計規約.md` を参照している。**実装着手の前に確定が必要**（RLSポリシーが書けないため）。
