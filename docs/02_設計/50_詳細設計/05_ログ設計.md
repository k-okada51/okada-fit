# ログ設計 — 監査ログ／操作ログ／アプリケーションログ

> **目的**: 「**誰が・いつ・何を・結果どうなったか**」を後から追跡・証明できるログ基盤を設計する。**業務ログ（業務が進んだ記録）とは別に、可監査性のための監査ログ**を定義し、記録項目・出力タイミング・保存/保持・改ざん防止・アクセス制御まで実装が迷わない粒度で固定する。
> **書き方**:（記入例は example-suido-fax の対応ファイル参照）実データは書かず `{ }` を置き換える。**監査ログ“要求”の正本は `01_要件定義/04_非機能要件.md（§3 セキュリティ）`（NFR-SEC-AUDIT）**、保持・監視の運用面は `01_要件定義/04_非機能要件.md（§4 運用）`（NFR-OPS）を参照。

## 1. ログ種別と方針
> 📝 ここにログの種別と使い分けを記載。**監査ログと業務ログ/アプリログを明確に分ける**。{種別／目的／代表イベント／保存先}

> ⚠️ **本書はたたき台（2026-08-02 生成）**。岡田さんのレビューで確定する。
> **個人利用のモバイルアプリ**という前提で、NFR-SEC-AUDIT-01/02 を満たす**最小構成**に寄せている。
> 従うのは NFR-SEC-AUDIT の ⚠️「個人利用のため厳格な監査は必須ではない。最低限、外部送信・エラーの記録に留め、詳細はログ設計で確定する」。

### ログ種別

| 種別 | 目的 | 代表イベント | 保存先 |
|---|---|---|---|
| 監査ログ | 可監査性・不正検知・調査（誰が何を） | EXT-01 への外部送信（NFR-SEC-AUDIT-01・FEAT-03/08）／認証成否（NFR-SEC-AUDIT-02） | **Supabase Edge Function ログ**に構造化JSON（`level:"audit"`） |
| 操作ログ | 利用者操作の記録 | 画面操作（SCR-01〜05 の遷移・ボタン押下） | **本PJでは採らない**（記録しない） |
| アプリログ | 障害調査・性能 | 未捕捉例外／`ERR-*` を返した応答／AI応答の所要時間（NFR-PERF-03/04）／DBクエリ失敗 | Edge Function ログ（`level:"error"/"warn"/"info"`）＋ Postgres ログ |
| 業務ログ | 業務進行の記録（**監査ログとは別**） | `is_done` の ST-01→ST-02（T02）／`gym_visits` の入館記録／`meal_logs` の食事記録 | **業務テーブルそのもの**（`01_DB物理設計.md` の10表） |

| 種別 | 補足 |
|---|---|
| 監査ログ | 外部送信＝AIメニュー提案（FEAT-03）・食事写真解析（FEAT-08）。**権限変更は本PJに存在しない** |
| 監査ログ | 認証は **Supabase Auth ログ**が自動記録する。専用テーブル・専用ストアは持たない（§1-1） |
| 操作ログ | 採らない理由は2つ。(1) 単一利用者で得る知見が乏しい (2) Flutter 側にログ収集基盤が無い（下表） |
| アプリログ | 未捕捉例外・`ERR-*` は Edge Function のもの。DB側の失敗は Postgres ログ |
| 業務ログ | イベントストア・履歴テーブルは持たない（`../30_データ・IF設計/03_ドメインイベント.md`） |

### ログを出せる経路

**アプリからログを出せる経路は Edge Function だけ。** ここが本構成でいちばん効く制約になる。

| 経路 | ログの出所 | アプリから任意のログを出せるか |
|---|---|---|
| Edge Function（`generate-menu` / `analyze-meal`） | Edge Function ログ | ○ `console.log` で出せる |
| Supabase Auth（サインイン・サインアウト） | Supabase Auth ログ | △ 自動記録のみ。項目はプラットフォーム既定 |
| PostgREST 直接（`supabase.from(...)`） | Supabase の Postgres ログ | **× 出せない**。アプリのコードがサーバ側で動かない |
| RPC（`supabase.rpc(...)`） | Supabase の Postgres ログ | **× 実質出せない**。SQL関数内の `RAISE LOG` は書けるが、構造化JSONの体裁を揃えられない |
| Flutter アプリ | 端末内のみ。収集先を持たない | **× スコープ外** |

**Flutter 側のログ・クラッシュ収集はスコープ外とする。** Crashlytics 等の SDK は入れない。

| # | 理由 |
|---|---|
| 1 | 利用者は岡田さん1名で、不具合は本人が再現できる |
| 2 | SDK追加は依存・同意文言・ビルド設定の保守を増やす。NFR-MAINT-01 に逆行する |

- 結果として **PostgREST 直接アクセス・RPC の呼び出しは監査ログに残らない**。
- 対象イベントごとの明示は §3 で行う。

### 1-1. 設計判断: 専用の監査ログテーブルを作らない

**判断: 作らない。** 監査ログは Supabase のプラットフォームログに構造化JSONで出力するにとどめる。

| 論点 | 理由 |
|---|---|
| 要求水準 | NFR-SEC-AUDIT-01/02 が求めるのは「外部送信の時刻・用途・成否」と「認証の時刻・成否」だけ |
| 保持の要求 | いずれも「個人利用のため最小限 `[仮]`」。**行レベルの証跡DBは要求されていない** |
| テーブル追加のコスト | `01_DB物理設計.md` の10表に11番目を足す。DB設計・RLS・マイグレーション・容量の保守が増え、NFR-MAINT-01 に逆行する |
| 認証イベントの出所 | NFR-SEC-AUDIT-02（ログイン成否）は **Supabase Auth 側で発生**する。アプリのDBトランザクションからは書けず、DBテーブルに寄せても片肺になる |
| 改ざん耐性 | 自前テーブルは**本人が管理者であるDB上**にある。プラットフォームログより改ざんに弱く、証跡としての価値が下がる |
| トレードオフ | **プラットフォームログの保持期間が短い**（§4 の ⚠️）。長期の証跡は残らない。必要なら Log Drain（有料プラン）か定期エクスポートで補う |

**出力形式**（アプリログ・監査ログ共通）:

| 項目 | 内容 |
|---|---|
| 出力方法 | Edge Function 内の `console.log`／`console.error` に **1行1JSON** |
| なぜJSONか | Edge Function ログはテキスト行として収集される。後から検索・突合できるよう構造化する |
| 共通フィールド | `service`・`level`（`audit`/`error`/`warn`/`info`）・`correlation_id`（§6） |
| `service` の値 | `okada-fit-app`（Flutter）／`okada-fit-fn`（Edge Function）／`okada-fit-db`（Supabase）。定義は `06_DB設計規約.md §5` |
| 実際に出る値 | **`okada-fit-fn` のみ**。上表のとおり他の2つはログを出す経路を持たない |

## 2. 監査ログの記録項目
> 📝 ここに監査ログ1レコードの項目を記載。**主体・時刻・対象・操作・結果・相関ID**を最低限含める。{項目／型／必須／説明}

本節は **Edge Function が出す監査ログ1行**の項目を定める。
Supabase Auth ログの項目はプラットフォーム既定であり、本書では定義できない。

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| event_id | `string`（uuid v4） | ○ | 一意なイベントID。Edge Function 内で `crypto.randomUUID()` により発番（Deno 標準API） |
| occurred_at | `string`（ISO 8601・UTC。例 `2026-08-02T12:34:56.789Z`） | ○ | 発生時刻（サーバ時刻・UTC）。`new Date().toISOString()`。**端末時刻は使わない** |
| actor | `string` | ○ | 主体（利用者ID／サービスID）。JWT から得た `user.id`（uuid）。未認証・失敗時は `"anonymous"`、システム起因は `"okada-fit-fn"` |
| action | `string`（`<対象>.<操作>` のドット表記・小文字） | ○ | 操作。語彙は **`ai.generate_menu` / `ai.analyze_meal` の2つだけ** |
| target | `string`（`<リソース種別>:<id>`） | ○ | 対象リソース（種別＋ID）。外部送信は `ext:EXT-01`。特定できない場合は種別のみ |
| result | `"success"` または `"failure"` | ○ | 結果。HTTPステータス（2xx=success）または例外の有無から決定する |
| correlation_id | `string`（uuid v4） | ○ | リクエスト相関ID（追跡用）。発番と伝播の規則は §6 |
| source_ip / ua | `string` | △ | 発信元。`req.headers.get('x-forwarded-for')`／`req.headers.get('user-agent')` |
| detail | `object`（JSON・可変キー） | △ | 要点（**機微情報はマスキング**）。中身は下表 |

| 項目 | 補足 |
|---|---|
| actor | 取得は `Authorization` ヘッダのJWTから `supabase.auth.getUser()`。この uuid は **`users.id` と同値**（ADR-0005）。対応表を引く必要は無い |
| action | `foods.import` / `machines.delete` / `menus.delete` は Edge Function を通らないため出力できない（§3） |
| correlation_id | `x-correlation-id` があればその値。無ければ入口で `crypto.randomUUID()` 発番（`../30_データ・IF設計/02_API設計.md` §1 の共通ヘッダと整合） |
| source_ip / ua | **Supabase が Edge Function にこれらを付与するかは未確認 `[仮]`**。取得できなければ省略してよい（個人利用のため） |
| detail | 外部送信＝`model_id` / `prompt_token_count` / `candidates_token_count` / `duration_ms` `[仮]`／エラー＝`error_code` / `http_status` |

- `detail` に **`estimated_cost_usd` と `fallback_used` は持たない。**
- 理由: Gemini API を直接呼ぶ構成で、課金額を返すゲートウェイもフォールバック機構も無い（EXT-01）。
- コスト把握は Google Cloud 側のコンソールで行う。
- トークン数のフィールド名は Gemini の `usageMetadata` に依存する `[仮]`。実装時に公式ドキュメントで確認する。

### 2-1. 機微情報のマスキング（**ログに出してはならないもの**）

以下は `detail` を含むどのフィールドにも出力しない。
**「マスクする」ではなく「そもそも渡さない」。** 部分マスクは実装漏れを生む。

| 対象 | 理由 | 代わりに記録してよいもの |
|---|---|---|
| **食事写真の画像バイナリ／base64／data URL** | ADR-0003 で「写真は永続化しない」と決めた。**ログに残せば実質的な永続化になる** | `bytes`（サイズ）・`mime_type`・`duration_ms` のみ |
| **`GEMINI_API_KEY`／`x-goog-api-key`／`Authorization` ヘッダ** | Edge Function の環境変数のみで保持する秘密（NFR-SEC-02・NFR-OPS-02） | 使用したモデルID（`model_id`）のみ |
| **Supabase のアクセストークン／リフレッシュトークン／`SUPABASE_SERVICE_ROLE_KEY`** | 窃取でなりすまし・RLS迂回が可能になる（NFR-SEC-01/02） | `actor`（ユーザーID）のみ |
| **AIへ送るプロンプト本文・AI応答の生テキスト** | 写真由来の情報を含み得る。構造化後の栄養4項目・メニュー名だけで運用上は足りる | トークン数・成否・所要ms |
| **パスワード／メールリンクのトークン／OAuth の code・state** | 認証情報そのもの | `result`（success/failure）のみ |

- Edge Function ログは本文をそのまま保持する。画像を1回出せば ADR-0003 の決定を破る。
- APIキー・ヘッダがログに出た時点で、キーのローテーションが必要になる。

実装規約:

| # | 規約 | 理由 |
|---|---|---|
| 1 | ログ出力は **`supabase/functions/_shared/logger.ts` の単一関数を通す**。`console.log` の直接呼び出しを禁止する | 出力経路を1つに絞らないと規約が守られたか検証できない |
| 2 | 同関数は**許可リスト（allowlist）方式**で `detail` のキーを絞り、未知のキーは捨てる | 拒否リストは新しいキーの追加に追随できない |
| 3 | **例外オブジェクトをそのまま出力しない**（`console.error(err)` を禁止）。`err.name` / `err.message` / `err.stack` に限定する | fetch 由来の例外は `request`/`response` を抱えており、`x-goog-api-key` ごと出力され得る |
| 4 | **リクエストボディ・ヘッダの丸ごとダンプを禁止する** | `analyze-meal` は**入力そのものが画像バイト**（直接POST）。ボディを1回ダンプしただけで写真がログに残り、ADR-0003 を破る |

## 3. 出力タイミング（記録対象イベント）
> 📝 ここに「どのイベントで監査ログを出すか」を記載。認証・認可・重要データ操作・外部送信/確定・設定変更などを列挙。{イベント／トリガ／記録内容／関連ST/FEAT/NFR}

| イベント | トリガ | 記録内容 | 関連 |
|---|---|---|---|
| 認証 | サインイン成功／失敗／セッション失効。**Supabase Auth が自動記録する**。アプリからは出さない | Auth ログの既定項目（時刻・イベント種別・成否・IP `[仮]`）。本書の共通フィールドは載らない | **NFR-SEC-AUDIT-02**・NFR-SEC-01・`ERR-AUTH-001` |
| 権限変更 | **本PJでは該当なし**。ロール・権限付与の概念が無く、利用者は岡田さん本人1人 | — | NFR-SCALE-01（マルチテナント適用外） |
| 外部送信（AIメニュー提案） | Edge Function `generate-menu` が EXT-01 を呼ぶ直前と応答受領後の2点 | `action`(`ai.generate_menu`)・`actor`・`target`(`ext:EXT-01`)・`result`・`occurred_at`・`detail`（`model_id`・トークン数・`duration_ms`） | **NFR-SEC-AUDIT-01**・FEAT-03・EXT-01・NFR-PERF-03 |
| 外部送信（食事写真解析） | Edge Function `analyze-meal` が EXT-01 を呼ぶ直前と応答受領後の2点。**画像そのものは記録しない**（§2-1） | 上と同じ（`action`＝`ai.analyze_meal`）＋ `detail.bytes`・`detail.mime_type` | **NFR-SEC-AUDIT-01**・FEAT-08・EXT-01・ADR-0003・NFR-PERF-04 |
| CSV一括投入 | Flutter がCSVをパースし RPC `import_foods` を呼ぶ。**Edge Function を通らない** | **監査ログを出せない。** Postgres ログに関数呼び出しの痕跡が残るのみ | FEAT-10・NFR-PERF-05・NFR-MIGR-02・下記 ⚠️ |
| 記録の削除 | `supabase.from('training_machines').delete()` 等の PostgREST 直接呼び出し | **監査ログを出せない**（同上） | FEAT-01・NFR-AVAIL-04（**物理削除で復元不可**＝`06_DB設計規約.md §4`）・下記 ⚠️ |
| エラー | Edge Function が `ERR-*` を返す応答と未捕捉例外（アプリログとして出力。監査ログではない） | `level`(`error`)・`error_code`・`http_status`・`correlation_id`・`duration_ms`・`err.name`/`err.message`/`err.stack` | NFR-OPS-01・NFR-AVAIL-05・`../30_データ・IF設計/02_API設計.md` §5 |

**権限変更の代わりになるもの:** RLS ポリシーの変更は `supabase/migrations/*.sql` で行う。Git 履歴がそのまま証跡になる。

**外部送信は「呼ぶ前」と「返ってきた後」の2点で記録する。**

| # | 理由 |
|---|---|
| 1 | 呼ぶ前に記録しないと、タイムアウト（`ERR-AI-TIMEOUT`）や強制終了で**送信した事実が残らない** |
| 2 | NFR-SEC-AUDIT-01 が求めるのは「送信したか」。成否より先に「送ろうとした」を残す |

**もともと記録しないもの。**

| 対象 | 例 |
|---|---|
| 参照系 | `get_dashboard` / `get_protein_remaining` の RPC |
| 通常の記録追加 | `meal_logs` / `training_sessions` / `gym_visits` の INSERT |
| 状態遷移 | `is_done` の ST-01→ST-02（T02） |

- いずれも**業務テーブル自体が記録**であり（§1）、監査ログに二重に持つ意味が無い。
- **ログ出力自体はリクエスト処理を止めない。** 書き込み失敗は握り潰し、業務処理は続行する。
- 個人利用のため、証跡確保より機能継続を優先する（NFR-AVAIL-05 と同じ思想）。

> ⚠️ 要確認（人間判断）: **CSV一括投入（FEAT-10）と記録の削除（FEAT-01）の監査ログが取れなくなった。**
> 新構成ではこの2つが PostgREST／RPC の直接呼び出しになり、ログを出す主体が存在しない（§1）。旧構成では全操作がサーバ側のハンドラを経由したため記録できた。
> NFR-SEC-AUDIT-01/02 が要求するのは外部送信と認証だけなので**要件違反ではない**。
> ただし「物理削除で復元不可」（`06_DB設計規約.md §4`）と重なると、**誤削除の追跡手段が完全に無くなる**。
> 選択肢は3つ。いずれかを人間が決定する。
>
> - (a) 現状のまま許容する
> - (b) 削除だけを Edge Function 経由にする
> - (c) Postgres のトリガで削除を別表に残す（＝11番目のテーブル追加・§1-1 の判断を覆す）

## 4. 保存・保持・ローテーション
> 📝 ここに保存先・保持期間・ローテーション・バックアップを記載。保持期間は要件（NFR）と法令/契約に整合させる。{保存先／保持期間（根拠）／ローテ／バックアップ}

| 項目 | 内容 |
|---|---|
| 保存先 | **Supabase のマネージドログのみ**（Edge Function ログ／Auth ログ／Postgres ログ） |
| 追記専用性 | アプリからは書き換えられないため事実上の追記専用 |
| 用意しないもの | WORM ストレージ・専用の監査ログDB（§1-1・§5） |
| ローカルファイル | **一切書かない。** Edge Function は実行のたびに破棄されるコンテナ上で動く |
| 保持期間 | **Supabase 無料枠の既定に従う `[仮]`** |
| 保持期間の根拠 | NFR-SEC-AUDIT-01/02 が「個人利用のため最小限 `[仮]`」。独自の保持要件・法令・契約上の要求が無い |
| 長期保持が要るとき | Log Drain（有料プラン）または定期エクスポートで補う（NFR-OPS-03 のバックアップ運用に相乗り） |
| ローテ/アーカイブ | **アプリ側では行わない**（プラットフォーム任せ）。アーカイブも当面行わない `[仮]` |
| ローテ不要の理由 | 単一利用者・1日あたり数十リクエスト想定。ログ量が問題になる規模ではない |

バックアップ/リカバリ: 可用性（NFR-AVAIL）と整合（**監査ログは喪失不可**）

- **本PJはこの原則を満たさない。** 無料枠のログは保持期間経過後に失われ、復元手段が無い。
- NFR-AVAIL-04 と同じ制約下にある（「無料枠のバックアップ範囲は限定的。定期エクスポート等で補完する ⚠️ 要確認」）。
- したがって **監査ログの喪失を許容する `[仮]`** という判断を本書で明示する。
- 業務データ（DB）のバックアップは NFR-OPS-03／NFR-AVAIL-04 の定期エクスポートで担保する。ログとは別扱い。

> ⚠️ 要確認（人間判断）: **Supabase 無料枠の実際のログ保持期間が未確認。**
> 無料プランのログは保持がごく短く（時間〜日オーダー）、ダッシュボードを開いた時点で既に流れている可能性がある。
> これが事実なら、**NFR-SEC-AUDIT-01（外部送信の記録）は「後から追える証跡」として機能せず、リアルタイム調査用にしかならない**。
> 実仕様を確認したうえで、次のいずれかを人間が決定する。
>
> - (a) 現状のまま許容する
> - (b) Log Drain（有料プラン）を契約する
> - (c) 外部送信の要約だけをDBの監査テーブルに残す（§1-1 の判断を覆す＝11番目のテーブル追加と `01_DB物理設計.md` の改訂が必要）

## 5. 改ざん防止・アクセス制御
> 📝 ここに証跡としての信頼性を担保する仕組みを記載。{追記専用・ハッシュ連鎖/署名・削除禁止・閲覧権限の最小化・分離保管}

### 改ざん防止

**WORM・ハッシュ連鎖・電子署名は本PJでは採らない。** 理由は3つ。

| # | 採らない理由 | 根拠 |
|---|---|---|
| 1 | 監査する側・される側・データ主体がすべて岡田さん本人1人。「本人による改ざんを本人から守る」構図に実益が無い | NFR-DATA-01・NFR-SCALE-01 |
| 2 | 外部監査・法令・契約上の要求が存在しない | NFR-SEC-AUDIT の ⚠️（個人利用のため厳格な監査は必須ではない） |
| 3 | 出力先が Supabase のマネージドログ。**アプリのコードからは更新・削除ができない**。追記専用性は実装コストゼロで担保される | §4 |

ハッシュ連鎖の導入は、将来プロダクト化（Phase2）で第三者の利用者を持つ段階まで見送る。

### アクセス制御

**Supabase ダッシュボードのログイン権限（岡田さん本人のアカウントのみ）に依存する。**

| 項目 | 内容 |
|---|---|
| アプリ側の閲覧画面 | 作らない（SCR-01〜05 のいずれにも）。アプリ経由でログに触れる経路は無い |
| 分離保管 | 行わない。環境は `dev`/`prod` の2つ |
| 環境ごとの扱い | それぞれの Supabase プロジェクトのログを本人だけが見る（`../20_インフラ設計/01_システム構成・環境.md` §2） |
| 実質的な統制 | 「**Supabase プロジェクトにメンバーを招待しないこと**」の1点に集約される |

> ⚠️ 要確認（人間判断）: **アクセス制御が Supabase アカウントの強度そのものになる。**
> ログには `actor`・`source_ip`・モデル利用状況が載る。アカウントが乗っ取られればログも一緒に見られる。
> 確認が必要なのは2点。**Supabase アカウントに2要素認証を設定済みか**、**過去に他者を Supabase プロジェクトへ招待していないか**。
> いずれもアプリ側の設計では担保できない（NFR-SEC-01 の範囲外）。

## 6. 相関・追跡
> 📝 ここにリクエストを端から端まで追える仕組みを記載。{correlation_id の発番・伝播／分散トレース／ログ集約}

**相関ID: `correlation_id`（uuid v4）を Edge Function の入口で1回だけ確定させ、その処理内の全ログに載せる。**

| 手順 | 内容 |
|---|---|
| ① 受け取る | リクエストヘッダ `x-correlation-id` があればその値を採用する |
| ① の補足 | Flutter からは `supabase.functions.invoke(name, headers: {...})` で付けられる（再現テストからの指定も許す） |
| ② 無ければ発番 | `crypto.randomUUID()` で発番する |
| ② の根拠 | `../30_データ・IF設計/02_API設計.md` §1 の共通ヘッダは**任意ヘッダ**。ゆえに「無ければ発番」が必須の挙動になる |
| ③ 載せる | その Edge Function 実行内で出力する全ログ行に付ける |

伝播先:

| 先 | 扱い |
|---|---|
| Edge Function のアプリログ・監査ログ全行（§2） | 必須 |
| EXT-01（Gemini API）への呼び出し前後のログ行 | 必須。外部へは送らない |
| エラー応答 | 必須（下記） |
| **PostgREST／RPC の直接呼び出し** | **載せられない。** Flutter から Supabase へ直接飛び、Edge Function を経由しない（§1） |

- **利用者への露出**: エラー応答の `message`（`../30_データ・IF設計/02_API設計.md` §5）に相関IDを含めてよい `[仮]`。
- 個人利用のため、画面に出た値でログを引ける利点が漏洩リスクを上回る。
- **非同期処理・バッチは本PJに存在しない**（`02_バッチ設計.md`）。伝播は1回の Edge Function 実行内で完結する。
- **集約: 集中ログ基盤は持たない。** 単一利用者・低トラフィックで、横断検索基盤の導入コストが価値を上回る（NFR-MAINT-01）。
- 代わりに Edge Function ログ・Auth ログ・Postgres ログを人手で突き合わせる。
- 突合キーは `correlation_id`（Edge Function 側）と時刻（Auth／Postgres 側）。
- すべて同一の Supabase プロジェクト内にあるため、旧構成のような**別サービス間の突合は不要になった**。

> ⚠️ 要確認（人間判断）: **FEAT-08 の「AI解析は成功したがDB保存で失敗した」ケースを追えない。**
> 解析は Edge Function（相関IDあり）、`meal_logs` への保存は Flutter からの PostgREST 直接呼び出し（相関IDなし・ログなし）に分かれる。
> DB側の失敗は Postgres ログに残るが、どの解析結果に対応するかは時刻の目視照合でしか分からない。
> 実運用で調査が回らないと分かった時点で、次のいずれかを検討する。
>
> - (a) 保存まで Edge Function に含める
> - (b) Supabase の `application_name` に相関IDを載せる

> ⚠️ 要確認（人間判断）: **本書は「ログの設計」であって「監視・通知の設計」ではない。**
> NFR-OPS-01（Supabase のログを活用しエラー・AI連携失敗を確認できる `[仮]`）は**能動的な通知を含んでいない**。
> 現状では**岡田さんがダッシュボードを見に行かない限り障害・AIコスト超過に気づけない**。
