# Google Gemini API 連携 — EXT-01

> Google Gemini API の連携手順・status写像・識別子ライフサイクル。**外部ワイヤ（既存API契約）は改変しない**。直列化・冪等・再送などの共通非機能は [`README.md`](README.md#共通-連携の直列化冪等再送) を参照。

> ⚠️ **本書はたたき台（2026-08-02 生成／2026-08-08 改訂）**。岡田さんのレビューで最終確定する。EXT-01 は**同期リクエスト応答型**。ジョブも受付番号も作らない。テンプレの §2・§3 は非同期連携用の枠のため、該当なしを明記して代替を置く。

## 1. Google Gemini API 連携手順（EXT-01）
> 📝 ここに外部API呼び出しの手順（複数ステップの連携シーケンス）を記載。認証ヘッダ・文字コード・改変禁止の前提を冒頭に明記。%% ここに記載（実データは書かない）

呼び出しは**2つだけ**。どちらも1往復で終わる。

| Edge Function | 用途 | 入力 | 出力 | 目標 |
|---|---|---|---|---|
| `analyze-meal` | FEAT-08 食事写真 → 栄養価 | 画像 | 栄養4項目 | ≤20秒（NFR-PERF-04） |
| `generate-menu` | FEAT-03 部位＋器具 → メニュー案 | `body_part`・`machine_ids[]` | `menus[]` | ≤15秒（NFR-PERF-03） |

### 接続の前提

| 項目 | 値 |
|---|---|
| 呼び出し元 | Supabase Edge Function（Deno）。アプリから直接呼ばない |
| エンドポイント | `POST .../v1beta/models/{model}:generateContent` `[仮]` |
| 認証 | ヘッダ `x-goog-api-key: $GEMINI_API_KEY` |
| キーの置き場所 | Edge Function の環境変数のみ🔒（NFR-SEC-02） |
| モデル | `gemini-3.5-flash`。環境変数 `GEMINI_MODEL` で指定。ハードコードしない |
| 実装 | Deno の `fetch`。SDK は使わない |
| 形式 | UTF-8・`application/json` |
| 構造化出力 | `generationConfig.responseMimeType` ＋ `responseSchema` `[仮]` |
| 画像入力 | `contents[].parts[].inlineData: { mimeType, data }` `[仮]` |

- **Gemini API の契約は改変しない。**
- パス・フィールド名の細部は `[仮]`。実装時に公式ドキュメントで確認する。

### 処理の流れ

2つとも同じ4ステップを踏む。

> 📝 ここに各手順のエンドポイント・内容・記録先を表で記載。認証は `{Authorizationヘッダ形式}`（機密はSecrets管理）。{#／手順／エンドポイント／内容／記録先}

| # | 手順 | エンドポイント | 内容 | 記録 |
|---|---|---|---|---|
| ① | 認証・入力検証 | `functions.invoke('analyze-meal')` ／ `('generate-menu')` | JWT を検証。入力を検証。相関IDを発番 | Edge Function ログ |
| ② | 入力組立 | （内部） | プロンプトを組み立てる。**DBには書かない** | — |
| ③ | 推論 | `POST .../{model}:generateContent` `[仮]` | 構造化出力で受ける | **監査ログ**（NFR-SEC-AUDIT-01） |
| ④ | 応答整形 | （内部） | zod で検証して200を返す | アプリログ（所要時間） |

機能ごとに違うのは②と③の中身だけ。

| # | `analyze-meal`（FEAT-08） | `generate-menu`（FEAT-03） |
|---|---|---|
| ② | 画像バイトを base64 化 | `machine_ids` から器具・種目名をDB照会（AI不使用・RULE-004） |
| ③ | `responseSchema` = 栄養4項目＋料理名 `[仮]` | `responseSchema` = `{ menus: [{ name, how_to }] }` `[仮]` |
| ④ | 画像はメモリ上のみ。永続化しない（ADR-0003） | 提案は永続化しない |

### 写真の受け渡し（FEAT-08）

画像は Edge Function へ**直接POST**する。

| 項目 | 内容 |
|---|---|
| リサイズ | 送信前に長辺1024pxへ縮小（ADR-0003・必須） |
| サイズ | 実測で最大約300KB。base64 化しても約400KB |
| メモリ上限 | Edge Function は256MB。400KB は 0.2% 未満 |
| 保持 | メモリ上のみ。どこにも書かない |
| 経緯 | 一時 Storage 経由に改めたが、実測により直接POSTへ戻した（2026-08-08） |

**ADR-0003 との矛盾は無い。改訂も不要。** 直接POST・画像を保持しない、という当初方針のままである。

> ⚠️ 要確認（人間判断）: Edge Function の**リクエストボディ上限は未文書化**。実測400KBなら詰まる公算は低いが、実装時に1回検証する。検索で出る「10MB」は**デプロイサイズ**であり別物。

### 照会

**該当なし。** 1往復で完結し、外部に照会できるジョブを作らない。`../02_バッチ設計.md` のポーリングは EXT-01 では使わない。

### エラーの判定

失敗は3階層に分かれる。**(a) → (b) → (c) の順**に判定する。

| 階層 | 何が起きたか | 判定材料 |
|---|---|---|
| (a) HTTP | Gemini API が 401/403/429/5xx を返した | `response.status` |
| (b) 通信 | 接続断・タイムアウト・中断 | 例外種別 |
| (c) 検証 | 200 だが構造化出力が型どおりでない | zod の結果 |

**(c) は API の障害ではなく出力品質の問題。** (a)(b) と分けて扱う。

### ERRマッピング

共通契約（`../../30_データ・IF設計/02_API設計.md §5`）へ写像する。ERRの完全列挙の正本は段6（`../../60_テスト設計/02_RED母集合_受入基準・状態・エラー.md`）。

Gemini API の応答は `status` と `error.status` の組で判別する。公式のエラーコード仕様で確認済み（2026-08-08）。

| 検知 | Gemini の応答 | 階層 | error_code | HTTP | retryable |
|---|---|---|---|---|---|
| レート制限（分/秒） | 429 `rate_limit_exceeded` | (a) | `ERR-AI-RATE` | 429 | true |
| 日次クォータ超過 | 429 `quota_exceeded` | (a) | **`ERR-AI-QUOTA`** | 429 | **false** |
| 課金無効・請求未設定 | **400 `failed_precondition`** | (a) | `ERR-AI-CREDIT` | 402 | false |
| キー無効・権限なし | 401 `authentication` / 403 `permission_denied` | (a) | `ERR-AI-FAIL` | 500 | false |
| モデル不明 | 404 `model_not_found` | (a) | `ERR-AI-FAIL` | 500 | false |
| API側の障害 | 500 `api_error` / 503 `service_unavailable` | (a) | `ERR-AI-FAIL` | 500 | false |
| タイムアウト・接続断 | 504 `deadline_exceeded` ／ 例外 | (b) | `ERR-AI-TIMEOUT` | 504 | false |
| 構造化出力が型不一致 | 200 だが検証失敗 | (c) | **`ERR-AI-SCHEMA`** | 502 | false |

利用者への見せ方は次のとおり。

| error_code | 見せ方 |
|---|---|
| `ERR-AI-RATE` | 時間をおいて再操作を促す |
| `ERR-AI-QUOTA` | **当日は回復しない**旨を伝える |
| `ERR-AI-CREDIT` | 運用者（岡田さん）への気付きが要る |
| `ERR-AI-FAIL` | 構成不備・障害。`ERR-AUTH-001` に写像しない |
| `ERR-AI-TIMEOUT` | 「解析に失敗しました」 |
| `ERR-AI-SCHEMA` | 撮り直し／再入力を促す |

**429 は2種類あり、retryable が逆になる。** `rate_limit_exceeded` は待てば通るが、`quota_exceeded` は当日回復しない。`error.status` を見ずに 429 だけで判定すると、日次クォータ切れをバックオフで叩き続ける。

いずれも縮退は同じ。**AI機能だけ止まる。トレーニング記録と閲覧は継続する。ただし食事の記録はできない**（NFR-AVAIL-05・§4-5）。通知は `ScaffoldMessenger.showSnackBar`。

| 対象 | 縮退時の扱い |
|---|---|
| FEAT-08 食事記録 | **記録できない。** 撮り直すか諦めるかの2択になる |
| FEAT-08 の手入力 | **経路を持たない**（ADR-0015）。利用者はタンパク質量を知らず代替にならない |
| FEAT-03 メニュー提案 | 提案のみ停止。部位→器具の絞り込み（RULE-004）は影響を受けない |
| FEAT-04 トレーニング記録 | 影響なし。通常どおり記録できる |
| 閲覧（過去記録・FEAT-09 残量） | 影響なし。通常どおり表示できる |

- 手入力の前提は**撤回した**（2026-08-08）。AI が失敗した食事は記録できない。
- NFR-AVAIL-05 の「記録は継続する」という文言とは合わない。要件側の見直しが要る（§4-5）。

> ~~⚠️ 要確認（人間判断）: スキーマ検証失敗に対応する ERR が共通契約に無い。~~（**解決**・2026-08-08）
> **`ERR-AI-SCHEMA`(502) を新設して確定した**。`ERR-AI-FAIL` と分けたのは、呼び出し自体は成功しているため原因の切り分けが要るからである。自動再試行はしない（従量課金が二重になるため）。

> ~~⚠️ 要確認（人間判断）: `ERR-AI-CREDIT` の切り分け条件が未確定。残高切れは 429 に混ざって区別できない見込み。~~（**解決**・2026-08-08）
> **この想定は誤りだった。** 公式のエラーコード仕様で**区別できる**ことを確認した。課金無効は **400 `failed_precondition`**、レート制限は 429 `rate_limit_exceeded`、日次クォータは 429 `quota_exceeded` で返る。

> ⚠️ 要確認（人間判断）: 段3との乖離。`POST /api/meals/analyze` は `analyze-meal`、`POST /api/menus/generate` は `generate-menu` に置き換わる。FEAT-08 は直接POSTのままで、**変わるのは宛先だけ**。`../../30_データ・IF設計/02_API設計.md §4.1・§4.2` の改訂が要る。

## 2. Google Gemini API status → 本PJ status 写像 `[仮]`
> 📝 ここに外部システムのstatus値を本PJの状態（ST）へ写像する表を記載。正本は `01_DB物理設計.md` のenum・`30_データ・IF設計/03_ドメインイベント.md`。{外部status／区分／本PJ status／遷移ID}

**該当なし。** Gemini API は同期で答えを返すだけで、受付番号もジョブも持たない。写像する外部statusが存在しない。

| Gemini API status | 区分 | 本PJ status | 遷移 |
|---|---|---|---|
| 存在しない | 進行中 | 持たない（画面のローディングはアプリ内の一時状態） | なし |
| 存在しない | 成功 | 更新しない（結果を応答で返すのみ） | なし |
| 存在しない | 失敗 | 更新しない（ERRを返して縮退） | なし |

**ST-01／ST-02 はトレーニング明細の状態**（FEAT-04）。EXT-01 の成否では変わらない。

### モデルフォールバックは持たない `[仮]`

| 項目 | 内容 |
|---|---|
| 旧 | Gateway にモデル一覧を宣言し、失敗時に自動切替していた |
| 新 | 仲介する層が無い。宣言だけの切替はできない |
| 影響 | 既定モデルが失敗した時点で縮退する。可用性は旧設計より下がる |
| 代替 | **持たない**（2026-08-08 決定・§4 #2）。自前の切替も別プロバイダへの二重化も行わない |
| 帰結 | 縮退のみで受容する。EXT-ID は EXT-01 の1件のままとする |

## 3. 照会用識別子 ライフサイクル
> 📝 ここに外部連携で払い出される識別子（照会キー）の採番→保存→照会→終端までのライフサイクルを記載。突合キーと照会キーが別なら二本立てである旨を明示。

**該当なし。** 同期で完結するため、外部が採番する照会用識別子は存在しない。**DBに外部IDを持つ列も作らない**（`../01_DB物理設計.md`）。

代わりに**相関ID（`correlation_id`）**でログを追跡する。方式の正本は `../05_ログ設計.md §6`。

| 段階 | 内容 |
|---|---|
| 発番 | Edge Function の入口で1リクエスト1件。アプリが送ってきたらそれを使う |
| 伝播 | Edge Function ログ・監査ログ・エラーログに同じ値を付ける |
| 照会 | 障害調査時に Supabase のログを横断検索する。**外部への問い合わせには使わない** |
| 終端 | 応答を返して終わり。**DBに永続化しない** |

> ⚠️ 要確認（人間判断）: 発番方式（UUIDv4 ／ Supabase のリクエストID流用）と、応答ヘッダで返すかが未確定 `[仮]`。保持期間は `../05_ログ設計.md §4` の確定待ち。
