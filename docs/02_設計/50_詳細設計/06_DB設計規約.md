## 2. データ型規約
> 📝 ここに用途別の標準データ型を記載。{識別子（主キー/外部キー）／文字列（可変長・固定長・上限）／数値・金額（精度）／真偽値／日時（タイムゾーンの扱い）／enum（DB表現：文字列/整数）／JSON・半構造化／NULL可否の原則}。DB製品（PostgreSQL等）は `05_技術選定.md` に従う。

| 用途 | 標準型 | 備考 |
|---|---|---|
| 識別子（PK/FK） | `users.id` ＝`uuid`（`auth.users` に合わせる）／他9表の PK＝`bigint GENERATED ALWAYS AS IDENTITY`／FK＝参照先 `id` と同型 | `users.id` だけ uuid（案A・§4.2・ADR-0005）。認証主体 `auth.users.id` と同値にし、RLS を `auth.uid()` と直接比較するため。**採番はしない**（`auth.users` の値を入れる）。したがって各 `user_id` も `uuid`。それ以外に UUID は広げない（行数が小さく、可読性とINDEXサイズを優先）。`GENERATED ALWAYS` がアプリ側の採番を禁止する |
| 文字列 | `text` | 上限・可変/固定：**一律 `text`（可変）**。`varchar(n)` と `text` に性能差が無いため。固定長 `char(n)` は使わない。長さ上限は型ではなく `CHECK (char_length(col) <= N)` で表現する |
| 数値・金額 | 栄養値・体重＝`numeric(6,1)`／回数・件数＝`int` | 精度・スケール：小数第1位まで・最大 `99999.9`。浮動小数は使わない（合計・比較で丸め誤差が出るため・ADR-0022）。**金額は本PJで扱わない**（課金機能なし）。型の決定は ADR-0022（2026-08-08 確定） |
| 真偽値 | `boolean` | NOT NULL ＋ 既定値の明示を原則とし、NULL による3値論理を避ける（実態：`training_session_details.is_done` は `not null default false`） |
| 日時 | 監査列＝`timestamptz`／業務上の日付＝`date`・時刻＝`time` | TZの扱い：`timestamptz` は UTC で保存し、表示時にクライアント側で JST 変換する。TZなしの `timestamp` は使わない。業務日付（`visit_date` `eaten_date` `performed_date`）は TZ を持たない `date` が正しい |
| enum | `text` ＋ `CHECK (col IN (...))` | DB表現：文字列（日本語値をそのまま格納）。`CREATE TYPE ... AS ENUM` は採らない（理由は後述）。実態：`ck_menu_body_part`（`body_part`＝胸/背中/脚/肩/腕・RULE-003） |
| JSON/半構造化（列） | **当面不使用** | AI（EXT-01）の応答は Edge Function 内で zod 検証し、確定した列（栄養4項目）に展開して保存する（ADR-0003） |
| JSON/半構造化（RPC引数） | `jsonb` は**使ってよい** | `import_foods(p_rows jsonb)`（FEAT-10）。列に持たせる必要が出たら `json` ではなく `jsonb` を用い、検索対象キーには式INDEXを張る |

### NULL可否の原則

- FK・業務日付・集計対象の数量は **NOT NULL**（`user_id` `eaten_date` `protein_g` 等）。
- 理由は、集計（FEAT-05/09 の SUM）で NULL 混入を起こさないため。
- 「業務上、未入力があり得る」列だけ NULL 可とする。
- 実態は `users.weight_kg` `users.target_training_count` `training_menus.how_to` `gym_visits.visit_time` `meal_logs.eaten_time`。
- **空文字と NULL を混在させない**。未入力は NULL に寄せ、空文字を禁止したい列は `CHECK (col <> '')` を付ける。
- 既定値（DEFAULT）で NOT NULL を成立させてよいのは、業務的に意味のある既定がある列だけ。
- 該当するのは `created_at`＝`now()` と `is_done`＝`false`。

### enum に `CREATE TYPE` を採らない理由

| # | 理由 |
|---|---|
| 1 | 値の追加が `ALTER TYPE ... ADD VALUE` になり、**値の削除・改名が実質できない**（NFR-MIGR-03 に不利）。CHECK 制約なら `DROP CONSTRAINT` → 再作成で前後どちらにも戻せる |
| 2 | 本PJの enum 値は**日本語1種（`body_part` のみ）**で変更頻度も低い。型を1つ増やす利得が小さい |
| 3 | `text` のままなら CSV 取込・API のクエリ文字列（`?body_part=`）との写像が不要 |

## 3. 命名規約
> 📝 ここにテーブル・カラム等の命名規約を記載。{テーブル名（単数/複数・接頭辞）／カラム名（snake_case等）／主キー・外部キーの命名（{table}_id等）／インデックス・制約・シーケンスの命名／予約語回避／マルチテナントのテナント列}。

| 対象 | 規約 | 例 |
|---|---|---|
| テーブル名 | **複数形・snake_case**。業務名詞を英語化してそのまま使い、`t_` `m_` 等の接頭辞は付けない。中間テーブルは「親名＋役割」（`_details` 等） | `users` / `gyms` / `training_menus` / `training_session_details` |
| テーブル名（マスタ／履歴） | 区別を名前に埋め込まない。`01_DB物理設計.md` の節（§1マスタ／§2履歴）で表す | — |
| カラム名 | **snake_case・単数形**。**量を持つ列は単位を列名に含める**（`_kg` `_g` `_kcal`）。DB列名＝JSONフィールド名（§5） | `weight_kg` / `protein_g` / `calories_kcal` |
| カラム名（種類別） | 日付＝`_date`、時刻＝`_time`、真偽＝`is_` 接頭辞、件数＝`_count` | `eaten_date` / `visit_time` / `is_done` / `target_training_count` |
| 主キー | 単一列 `id` に固定（既定は `bigint GENERATED ALWAYS AS IDENTITY`。`users.id` のみ uuid・§2）。**複合PKは使わない**。業務上の一意性は UNIQUE INDEX で別に表現する | `training_session_details` は `id` がPKで、業務一意は `uq_tsd_session_menu` ／ `foods` は `id` がPKで、業務一意は `uq_foods_name` |
| 外部キー | `<参照先テーブルの単数形>_id`。参照は必ず参照先の `id` に張る。曖昧になる場合のみ役割語を前置する（`from_gym_id` 等） | `user_id`（→`users`）／`gym_id`（→`gyms`）／`menu_id`（→`training_menus`）／`session_id`（→`training_sessions`） |
| インデックス | 非一意＝`ix_<テーブル名>_<列の要約>`／一意＝`uq_<テーブル名>_<列の要約>` | `ix_meal_logs_user_date`（`user_id, eaten_date`）／`ix_gym_visits_user_date`（`user_id, visit_date`） |
| インデックス（要約の作り方） | 共通接尾辞（`_id` `_date`）を落とした短縮でよい。ただし**テーブル名は略さない**のを原則とする（識別子上限63バイトに十分収まる） | — |
| 制約 | CHECK＝`ck_<テーブル名>_<意味>`／FK＝`fk_<テーブル名>_<参照先>`／UNIQUE＝`uq_<テーブル名>_<列の要約>`／PK＝PostgreSQL既定名（`<テーブル名>_pkey`）でよい | `ck_meal_nutrients`（→規約形は `ck_meal_logs_nutrients`）／`ck_menu_body_part`（→規約形は `ck_training_menus_body_part`） |
| 制約（命名の必須性） | **制約には必ず名前を付ける**。無名だと差分マイグレーションで特定できない | — |

### 予約語・識別子の回避

- SQL/PostgreSQL の予約語（`user` `order` `group` `time` `session` 等）を**単独では**テーブル名・列名に使わない。
- 回避はほぼ済んでいる。テーブルを複数形にする規約（`users`）と、単位・役割の接頭/接尾辞（`visit_time` `eaten_time` `session_id`）による。
- **二重引用符でのクォートが必要になる識別子を作らない**（日本語名・大文字混在・空白）。
- ※値（enum の `胸` 等）が日本語であることは識別子の話とは別で、許容する（§5）。
- 識別子は 63 バイト以内（PostgreSQL の上限。超えると**警告なく切り詰められる**）。

### 既知の不統一（実態 vs 本規約）

`01_DB物理設計.md §3` の既存DDLは、テーブル名の短縮方法が3通り混在している。

|---|---|---|---|
| 1 | `ix_train_sessions_user_date` | `ix_training_sessions_user_date` | `training_sessions` → `train_sessions`（語の短縮） |
| 2 | `uq_tsd_session_menu` | `uq_training_session_details_session_menu` | `training_session_details` → `tsd`（頭字語） |
| 3 | `ck_meal_nutrients` / `ck_menu_body_part` | `ck_meal_logs_nutrients` / `ck_training_menus_body_part` | `meal_logs` → `meal`、`training_menus` → `menu`（語の脱落） |
| 4 | `ix_gym_visits_user_date` / `ix_meal_logs_user_date` | 同左（規約どおり） | テーブル名フル。#1〜#3 と方針が揃っていない |

> **テーブル名を略さない**に統一する。

| # | 理由 |
|---|---|
| 1 | **略し方の合意コストが高い。** 先頭2語か頭字語かを決めても、次のテーブルで再び迷う |

|---|---|

## 4. 監査列規約
> 📝 ここに全テーブル共通の監査列（作成・更新・削除・テナント等）を記載。{列名／型／必須／既定値／更新契機}。論理削除・楽観ロック（version）・相関IDの扱いも明記。監査ログ（証跡）そのものは `05_ログ設計.md`・NFR-SEC-AUDIT を正とする。

| 列名 | 型 | 必須 | 既定値 | 更新契機 |
|---|---|---|---|---|
| created_at | `timestamptz` | ○ | `now()` | INSERT時（**採用**。全10表に付与・`01_DB物理設計.md §1` 冒頭） |
| created_by | 不採用 | — | — | INSERT時（採用時）。**不採用**: 単一ユーザー運用（NFR-SCALE-01）で作成者は常に本人。`user_id` と完全に重複する |
| updated_at | `timestamptz` | ○（採用時） | `now()` | UPDATE時。**現時点は未採用**（`01_DB物理設計.md §3` の「更新頻度の高い表は `updated_at` も検討」段階） |
| updated_by | 不採用 | — | — | UPDATE時（採用時）。**不採用**: `created_by` と同じ理由（更新者は常に本人） |
| deleted_at | 不採用 | — | NULL | 論理削除時。**不採用**: 論理削除を採らず**物理削除**（`DELETE`）で運用する |
| tenant_id | 不採用 | — | — | INSERT時（採用時）。**不採用**: NFR-SCALE-01 でマルチテナントは適用外（個人利用で確定） |
| version | 不採用 | — | — | UPDATE時（楽観ロック）。**不採用**: 単一ユーザー・単一端末が前提で、同一行への同時更新が構造的に起きない |

判断の補足。

- `updated_at` の採用候補は更新のある3表。`users`（体重・目標）・`training_session_details`（`is_done`）・`meal_logs`。
- `updated_at` を採用する場合は **BEFORE UPDATE トリガで `now()` を入れる** `[仮]`。
- 理由: 更新は PostgREST 直接呼び出しが主。アプリが値を送ると端末時刻に依存し、サーバ側で検証できない。
- `deleted_at`: 個人の記録アプリでは「消したのに残っている」ほうが利用者の期待に反する。
- 全クエリに `deleted_at IS NULL` を付ける負債も避けたい。救済は定期エクスポート（NFR-AVAIL-04／NFR-OPS-03）に委ねる。
- `tenant_id`: **`user_id` が事実上の分離キー**として同じ役割を果たしている。
- 将来のマルチユーザー化（Phase2）は `user_id` ＋ RLS で吸収する（`../30_データ・IF設計/01_データモデル.md` §7・ADR-0004）。
- `version`: 競合が現実化する（複数端末での同時編集）まで導入しない。

- **相関ID（correlation_id）は DB列として持たない。** リクエスト追跡はログ側で完結させる（`05_ログ設計.md` §6）。
- 業務テーブルに追跡用の列を持ち込むと `01_DB物理設計.md` の10表すべてに影響が及ぶ。個人利用では得られる情報が少ない。
- 監査列を増やす／減らす判断は本書で行う。
- **実際の列追加は `01_DB物理設計.md` の改訂として行う**（本書は規約であり DDL の正本ではない）。

### 4.1 RLSポリシーの標準形

ADR-0004 により、本人分離は **RLS（Row Level Security）** で行う。
全テーブルで RLS を有効化し、以下を標準形とする。
本人IDの実体は **`auth.uid()`（uuid）**。§4.2 の案A採用で確定した（ADR-0005）。

**RLS が唯一の防御線になる。** Flutter が PostgREST を直接叩く構成では、サーバ側ハンドラでの二重チェックが無い。
ポリシーの1行の誤りが、そのままデータ漏洩になる。

テーブルは3区分に分ける（区分ごとの割り当ての正本は `01_DB物理設計.md §3.4`）。

| 区分 | 対象テーブル | 述語 |
|---|---|---|
| 本人のみ（自身のPK） | `users` | `id = auth.uid()` |
| 本人のみ（所有者列） | `training_menus` / `gym_visits` / `training_sessions` / `meal_logs` | `user_id = auth.uid()` |
| 共通マスタ | `gyms` / `training_machines` / `foods` | `TO authenticated USING (true)` |
| 親経由 | `machine_menus` / `training_session_details` | 親の `user_id` を `EXISTS` で辿る |

```sql
-- (1) user_id を持つ表: gym_visits / training_sessions / training_menus / meal_logs
--     ※ users 自身は user_id を持たないため、条件は user_id ではなく id = auth.uid() になる
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_<table>_self ON <table>
  FOR ALL TO authenticated
  USING      (user_id = auth.uid())   -- SELECT/UPDATE/DELETE で見える行
  WITH CHECK (user_id = auth.uid());  -- INSERT/UPDATE で書ける値（なりすまし INSERT を防ぐ）

-- (2) user_id を持たない子表: 親テーブルを EXISTS で辿る
CREATE POLICY p_training_session_details_self ON training_session_details
  FOR ALL TO authenticated
  USING (EXISTS (SELECT 1 FROM training_sessions s
                 WHERE s.id = training_session_details.session_id
                   AND s.user_id = auth.uid()))
  WITH CHECK (EXISTS (SELECT 1 FROM training_sessions s
                      WHERE s.id = training_session_details.session_id
                        AND s.user_id = auth.uid()));

-- (3) 共通マスタ gyms / training_machines / foods: 所有者列を持たず、本人分離の対象外。
--     認証済みなら読み書きできる（2026-08-08 確定）。
ALTER TABLE foods ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_foods_shared ON foods
  FOR ALL TO authenticated
  USING (true) WITH CHECK (true);
```

規約として固定する点:

- **ポリシー名は `p_<テーブル名>_<用途>`**（`p_meal_logs_self` / `p_foods_shared`）。
- 用途語は3区分に対応させる。本人のみ＝`_self`／共通マスタ＝`_shared`／親経由＝`_self`。
- **`WITH CHECK` を必ず書く**。`USING` だけだと他人の `user_id` を指定した INSERT を止められない。
- **`TO authenticated` を明示**し、`anon` ロールには一切の権限を与えない（NFR-SEC-01）。
- **全10表で `ENABLE ROW LEVEL SECURITY` を入れる。** 共通マスタも例外にしない（`anon` を締め出すため）。
- `users` 自身も RLS 対象とし、本人行のみ参照・更新できるようにする（FEAT-06（初期設定）の体重・目標）。
- **接続は常にユーザーのセッション（JWT）で行う。** Flutter は PostgREST・RPC・Edge Function をすべて本人のJWTで叩く。
- Edge Function も受け取ったJWTを引き継いで接続する。
- **service role キーの用途を限定する。** RLS を迂回するため、本人データに触れない処理だけに使う（例: `import_foods`・FEAT-10）。
- 置き場所は Edge Function の環境変数または `security definer` 関数の内側に限る。Flutter 側には一切置かない（NFR-SEC-02）。
- `FOR SELECT/INSERT/UPDATE/DELETE` に分割するかは `[仮]`。分ける必要が出るまで `FOR ALL` 1本で書く。

> ⚠️ 要確認（人間判断）: **共通マスタ3表（`gyms` / `training_machines` / `foods`）は、認証済みなら誰でも読み書きできる。**
> 所有者列を持たない扱いは 2026-08-08 に確定した（区分は上表・述語の正本は `01_DB物理設計.md §3.4`）。
> 単一ユーザー運用では実害が無い。**Phase2 のマルチユーザー化（NFR-SCALE-01）で書き込みを絞る必要がある。**
> 絞り方は「書き込みを service role／`security definer` 関数に限定する」「管理者ロールを設ける」の2案。

### 4.2 `users.id`（bigint）と Supabase `auth.uid()`（uuid）の紐付け ★本書が正本

**結論: 案A を採用する**（2026-08-08 決定・ADR-0005）。`users.id` を `uuid` にし、`auth.users(id)` を参照する。

ADR-0004 は「`user_id = auth.uid()` **相当**の RLS」と書いていたが、改訂前は**型が合わなかった**。

- 改訂前の `01_DB物理設計.md §1.1`: `users.id` は `bigint GENERATED ALWAYS AS IDENTITY`。各履歴の `user_id` も `bigint`。
- Supabase Auth: 認証済みユーザーの識別子は `auth.users.id`＝**`uuid`**、SQL からは `auth.uid()`（`uuid` を返す）で取得する。

したがって `user_id = auth.uid()` は `bigint = uuid` の比較になり、そのままでは実行できなかった。
検討した選択肢は次の3つ。

| 案 | 採否 | 内容 | 長所 | 短所 |
|---|---|---|---|---|
| **A** | **採用** | `users.id` を `uuid` に変え、`auth.users.id` と同値にする（`references auth.users(id)`） | RLSが最短形（`user_id = auth.uid()`）で書ける。Supabase の定石 | **10表すべての `id`/`user_id` 型変更**が要る。`01_DB物理設計.md` の前提（全 `id` は bigint）が崩れ、INDEXサイズも増える |
| B | 不採用 | `users` に `auth_user_id uuid unique not null` 列を追加し、`users.id`（bigint）は据え置く | 既存の型・DDLをほぼ維持できる。追加は1列 | RLSが `user_id = (SELECT id FROM users WHERE auth_user_id = auth.uid())` になり、**全ポリシーにサブクエリが入る**（`SELECT` を1回に畳む工夫が要る） |
| C | 不採用 | RLS を使わず、全アクセスを Edge Function 経由にして関数内で `user_id` を絞る | 型問題が起きない | **ADR-0004 の決定（RLSで本人分離）から外れる**。絞り忘れが即データ漏洩になり、防御が1層だけになる。さらに **PostgREST 直接アクセスを一切使えなくなり**、全CRUDを Edge Function で書き直すことになる（`07_実装共通設計パターン.md` の方式割り当てが崩れる） |

案Aを採った理由と、短所への対処。

| 項目 | 内容 |
|---|---|
| 決め手 | RLS の述語が `auth.uid()` との直接比較になり、**全ポリシーからサブクエリが消える**（案Bの短所を回避） |
| 型変更の範囲 | 実際に変わるのは `users.id` と4表の `user_id` のみ。**他テーブルの `id` は bigint のまま**（10表すべてではない） |
| INDEXサイズ | uuid は bigint より8バイト大きい。本PJの行数規模（数千行）では影響しない |
| 採番 | `users.id` は自動採番を持たない。サインアップ時のトリガで `auth.users.id` を入れる（`01_DB物理設計.md §3.1`・FEAT-06） |
| 波及 | 列定義・DDL＝`01_DB物理設計.md §1.1`／RLS＝同 §3.4／ADR＝ADR-0005（ADR-0004 の「相当」表現を具体化） |

各機能設計の RLS 記述は、抽象表現（`<本人ID>`）ではなく **`auth.uid()` を直接書いてよい**。

**`users` の一意キーも同時に解決した。** `users.id` が `auth.users(id)` と1対1に対応するため、「同じ人の `users` 行が2つできる」事故は PK が構造的に防ぐ（改訂前の `01_DB物理設計.md §1.1`「一意性: 単一ユーザー運用のため当面なし」を置き換える）。

|---|---|

| # | 理由 |
