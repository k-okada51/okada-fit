## 2. データ型規約
> 📝 ここに用途別の標準データ型を記載。{識別子（主キー/外部キー）／文字列（可変長・固定長・上限）／数値・金額（精度）／真偽値／日時（タイムゾーンの扱い）／enum（DB表現：文字列/整数）／JSON・半構造化／NULL可否の原則}。DB製品（PostgreSQL等）は `05_技術選定.md` に従う。

| 用途 | 標準型 | 備考 |
|---|---|---|
| 識別子（PK/FK） | PK＝`bigint GENERATED ALWAYS AS IDENTITY`／FK＝`bigint` | 全10表の `id` に適用。FKは参照先 `id` と同型。UUID は採らない（単一ユーザー・行数が小さく、可読性とINDEXサイズを優先）。`GENERATED ALWAYS` がアプリ側の採番を禁止する |
| 文字列 | `text` | 上限・可変/固定：**一律 `text`（可変）**。`varchar(n)` と `text` に性能差が無いため。固定長 `char(n)` は使わない。長さ上限は型ではなく `CHECK (char_length(col) <= N)` で表現する |
| 数値・金額 | 栄養値・体重＝`float`／回数・件数＝`int` | 精度・スケール：`float` は倍精度浮動小数で**スケールを持たない**。**金額は本PJで扱わない**（課金機能なし）。厳密計算が要るなら `numeric(p,s)`。型の決定は `../30_データ・IF設計/01_データモデル.md` §8-5 |
| 真偽値 | `boolean` | NOT NULL ＋ 既定値の明示を原則とし、NULL による3値論理を避ける（実態：`training_session_details.is_done` は `not null default false`） |
| 日時 | 監査列＝`timestamptz`／業務上の日付＝`date`・時刻＝`time` | TZの扱い：`timestamptz` は UTC で保存し、表示時にクライアント側で JST 変換する。TZなしの `timestamp` は使わない。業務日付（`visit_date` `eaten_date` `performed_date`）は TZ を持たない `date` が正しい |
| enum | `text` ＋ `CHECK (col IN (...))` | DB表現：文字列（日本語値をそのまま格納）。`CREATE TYPE ... AS ENUM` は採らない（理由は後述）。実態：`ck_menu_body_part`（`body_part`＝胸/背中/脚/肩/腕・RULE-003） |
| JSON/半構造化（列） | **当面不使用** | AI（EXT-01）の応答は Edge Function 内で zod 検証し、確定した列（栄養4項目）に展開して保存する（ADR-0003） |
| JSON/半構造化（RPC引数） | `jsonb` は**使ってよい** | `replace_foods(p_rows jsonb)`（FEAT-10）。列に持たせる必要が出たら `json` ではなく `jsonb` を用い、検索対象キーには式INDEXを張る |

### NULL可否の原則

- FK・業務日付・集計対象の数量は **NOT NULL**（`user_id` `eaten_date` `protein_g` 等）。
- 理由は、集計（FEAT-05/09 の SUM）で NULL 混入を起こさないため。
- 「業務上、未入力があり得る」列だけ NULL 可とする。
- 実態は `users.weight_kg` `users.target_training_count` `training_menus.how_to` `gym_visits.visit_time` `meal_logs.eaten_time` `meal_logs.intake_count`。
- **空文字と NULL を混在させない**。未入力は NULL に寄せ、空文字を禁止したい列は `CHECK (col <> '')` を付ける。
- 既定値（DEFAULT）で NOT NULL を成立させてよいのは、業務的に意味のある既定がある列だけ。
- 該当するのは `created_at`＝`now()` と `is_done`＝`false`。

### enum に `CREATE TYPE` を採らない理由

| # | 理由 |
|---|---|
| 1 | 値の追加が `ALTER TYPE ... ADD VALUE` になり、**値の削除・改名が実質できない**（NFR-MIGR-03 に不利）。CHECK 制約なら `DROP CONSTRAINT` → 再作成で前後どちらにも戻せる |
| 2 | 本PJの enum 値は**日本語1種（`body_part` のみ）**で変更頻度も低い。型を1つ増やす利得が小さい |
| 3 | `text` のままなら CSV 取込・API のクエリ文字列（`?body_part=`）との写像が不要 |

> ⚠️ 要確認（人間判断）: **栄養値・体重の `float`（倍精度浮動小数）は、合計・比較で丸め誤差を出す。**
> FEAT-05（ダッシュボード集計）と FEAT-09（残量＝必要量−摂取量）は `SUM(protein_g)` を伴う。
> `0.1 + 0.2 = 0.30000000000000004` 型の誤差が「残量 0g のはずが 0.0000001g 残る」という境界のズレを生む。
> 回避策は2つ。(a) 表示時に小数第1位へ丸める／(b) 列型を `numeric(6,1)` に変更する。
> **本書は規約であり物理設計を変更しない。** (b) を採るなら `01_DB物理設計.md` の改訂と ADR 起票が要る。
> 現状は `../30_データ・IF設計/01_データモデル.md` §8-5 の決定に従い `float` のまま。

## 3. 命名規約
> 📝 ここにテーブル・カラム等の命名規約を記載。{テーブル名（単数/複数・接頭辞）／カラム名（snake_case等）／主キー・外部キーの命名（{table}_id等）／インデックス・制約・シーケンスの命名／予約語回避／マルチテナントのテナント列}。

| 対象 | 規約 | 例 |
|---|---|---|
| テーブル名 | **複数形・snake_case**。業務名詞を英語化してそのまま使い、`t_` `m_` 等の接頭辞は付けない。中間テーブルは「親名＋役割」（`_details` 等） | `users` / `gyms` / `training_menus` / `training_session_details` |
| テーブル名（マスタ／履歴） | 区別を名前に埋め込まない。`01_DB物理設計.md` の節（§1マスタ／§2履歴）で表す | — |
| カラム名 | **snake_case・単数形**。**量を持つ列は単位を列名に含める**（`_kg` `_g` `_kcal`）。DB列名＝JSONフィールド名（§5） | `weight_kg` / `protein_g` / `calories_kcal` |
| カラム名（種類別） | 日付＝`_date`、時刻＝`_time`、真偽＝`is_` 接頭辞、件数＝`_count` | `eaten_date` / `visit_time` / `is_done` / `intake_count` |
| 主キー | 単一列 `id` に固定（`bigint GENERATED ALWAYS AS IDENTITY`）。**複合PKは使わない**。業務上の一意性は UNIQUE INDEX で別に表現する | `users.id` ／ `training_session_details` は `id` がPKで、業務一意は `uq_tsd_session_menu` |
| 外部キー | `<参照先テーブルの単数形>_id`。参照は必ず参照先の `id` に張る。曖昧になる場合のみ役割語を前置する（`from_gym_id` 等） | `user_id`（→`users`）／`gym_id`（→`gyms`）／`menu_id`（→`training_menus`）／`session_id`（→`training_sessions`） |
| インデックス | 非一意＝`ix_<テーブル名>_<列の要約>`／一意＝`uq_<テーブル名>_<列の要約>` | `ix_meal_logs_user_date`（`user_id, eaten_date`）／`ix_gym_visits_user_date`（`user_id, visit_date`） |
| インデックス（要約の作り方） | 共通接尾辞（`_id` `_date`）を落とした短縮でよい。ただし**テーブル名は略さない**のを原則とする（識別子上限63バイトに十分収まる） | — |
| 制約 | CHECK＝`ck_<テーブル名>_<意味>`／FK＝`fk_<テーブル名>_<参照先>`／UNIQUE＝`uq_<テーブル名>_<列の要約>`／PK＝PostgreSQL既定名（`<テーブル名>_pkey`）でよい | `ck_meal_nutrients`（→規約形は `ck_meal_logs_nutrients`）／`ck_menu_body_part`（→規約形は `ck_training_menus_body_part`） |
| 制約（命名の必須性） | **制約には必ず名前を付ける**。無名だと差分マイグレーションで特定できない | — |

### 予約語・識別子の回避

- SQL/PostgreSQL の予約語（`user` `order` `group` `time` `session` 等）を**単独では**テーブル名・列名に使わない。
- 回避はほぼ済んでいる。テーブルを複数形にする規約（`users`）と、単位・役割の接頭/接尾辞（`visit_time` `eaten_time` `session_id`）による。
- **二重引用符でのクォートが必要になる識別子を作らない**（日本語名・大文字混在・空白）。
- ※値（enum の `胸` 等）が日本語であることは識別子の話とは別で、許容する（§5）。
- 識別子は 63 バイト以内（PostgreSQL の上限。超えると**警告なく切り詰められる**）。

### 既知の不統一（実態 vs 本規約）

`01_DB物理設計.md §3` の既存DDLは、テーブル名の短縮方法が3通り混在している。

| # | 実態の名前 | 本規約に沿った名前 | 何が起きているか |
|---|---|---|---|
| 1 | `ix_train_sessions_user_date` | `ix_training_sessions_user_date` | `training_sessions` → `train_sessions`（語の短縮） |
| 2 | `uq_tsd_session_menu` | `uq_training_session_details_session_menu` | `training_session_details` → `tsd`（頭字語） |
| 3 | `ck_meal_nutrients` / `ck_menu_body_part` | `ck_meal_logs_nutrients` / `ck_training_menus_body_part` | `meal_logs` → `meal`、`training_menus` → `menu`（語の脱落） |
| 4 | `ix_gym_visits_user_date` / `ix_meal_logs_user_date` | 同左（規約どおり） | テーブル名フル。#1〜#3 と方針が揃っていない |

> ⚠️ 要確認（人間判断）: **INDEX/制約名の短縮ルールが `train_sessions`・`tsd`・`meal` の3通りに揺れている。**
> 規約側を「テーブル名を略さない」に統一するなら、既存の4つの識別子を改名するマイグレーションが要る（DDLのみで、データ移行は伴わない）。
> 逆に「略してよい」を規約にするなら、略し方（先頭2語／頭字語）を1つに決める必要がある。
> 実装着手前に決めないと、テーブルが増えるたびに揺れが再生産される。
> **本書は物理設計を編集しないため、決定後に `01_DB物理設計.md §3` を改訂すること。**

> ⚠️ 要確認（人間判断）: **FK制約に明示的な名前が付いていない。**
> `01_DB物理設計.md` は列定義表で `FK→users(id)` と示すのみで、DDL 抜粋に `ALTER TABLE ... ADD CONSTRAINT fk_...` が無い。
> Supabase の GUI で作ると `<テーブル>_<列>_fkey` の既定名になり、命名規約（`fk_<テーブル名>_<参照先>`）と一致しない。
> **また、削除時の挙動（`ON DELETE CASCADE` / `RESTRICT`）が全FKで未定。**
> `training_sessions` を消したとき `training_session_details` が残るか否かが決まっていない（FEAT-04 の記録削除に影響）。

## 4. 監査列規約
> 📝 ここに全テーブル共通の監査列（作成・更新・削除・テナント等）を記載。{列名／型／必須／既定値／更新契機}。論理削除・楽観ロック（version）・相関IDの扱いも明記。監査ログ（証跡）そのものは `05_ログ設計.md`・NFR-SEC-AUDIT を正とする。

| 列名 | 型 | 必須 | 既定値 | 更新契機 |
|---|---|---|---|---|
| created_at | `timestamptz` | ○ | `now()` | INSERT時（**採用**。全10表に付与・`01_DB物理設計.md §1` 冒頭） |
| created_by | 不採用 | — | — | INSERT時（採用時）。**不採用**: 単一ユーザー運用（NFR-SCALE-01）で作成者は常に本人。`user_id` と完全に重複する |
| updated_at | `timestamptz` | ○（採用時） | `now()` | UPDATE時。**現時点は未採用**（`01_DB物理設計.md §3` の「更新頻度の高い表は `updated_at` も検討」段階） |
| updated_by | 不採用 | — | — | UPDATE時（採用時）。**不採用**: `created_by` と同じ理由（更新者は常に本人） |
| deleted_at | 不採用 | — | NULL | 論理削除時。**不採用**: 論理削除を採らず**物理削除**（`DELETE`）で運用する |
| tenant_id | 不採用 | — | — | INSERT時（採用時）。**不採用**: NFR-SCALE-01 でマルチテナントは適用外（個人利用で確定） |
| version | 不採用 | — | — | UPDATE時（楽観ロック）。**不採用**: 単一ユーザー・単一端末が前提で、同一行への同時更新が構造的に起きない |

判断の補足。

- `updated_at` の採用候補は更新のある3表。`users`（体重・目標）・`training_session_details`（`is_done`）・`meal_logs`。
- `updated_at` を採用する場合は **BEFORE UPDATE トリガで `now()` を入れる** `[仮]`。
- 理由: 更新は PostgREST 直接呼び出しが主。アプリが値を送ると端末時刻に依存し、サーバ側で検証できない。
- `deleted_at`: 個人の記録アプリでは「消したのに残っている」ほうが利用者の期待に反する。
- 全クエリに `deleted_at IS NULL` を付ける負債も避けたい。救済は定期エクスポート（NFR-AVAIL-04／NFR-OPS-03）に委ねる。
- `tenant_id`: **`user_id` が事実上の分離キー**として同じ役割を果たしている。
- 将来のマルチユーザー化（Phase2）は `user_id` ＋ RLS で吸収する（`../30_データ・IF設計/01_データモデル.md` §7・ADR-0004）。
- `version`: 競合が現実化する（複数端末での同時編集）まで導入しない。

- **相関ID（correlation_id）は DB列として持たない。** リクエスト追跡はログ側で完結させる（`05_ログ設計.md` §6）。
- 業務テーブルに追跡用の列を持ち込むと `01_DB物理設計.md` の10表すべてに影響が及ぶ。個人利用では得られる情報が少ない。
- 監査列を増やす／減らす判断は本書で行う。
- **実際の列追加は `01_DB物理設計.md` の改訂として行う**（本書は規約であり DDL の正本ではない）。

### 4.1 RLSポリシーの標準形

ADR-0004 により、本人分離は **RLS（Row Level Security）** で行う。
全テーブルで RLS を有効化し、以下を標準形とする。
`<本人ID>` の実体は §4.2 の論点が未決のため確定していない。

```sql
-- (1) user_id を持つ表: gym_visits / training_sessions / training_menus / meal_logs
--     ※ users 自身は user_id を持たないため、条件は user_id ではなく id = <本人ID> になる
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_<table>_self ON <table>
  FOR ALL TO authenticated
  USING      (user_id = <本人ID>)   -- SELECT/UPDATE/DELETE で見える行
  WITH CHECK (user_id = <本人ID>);  -- INSERT/UPDATE で書ける値（なりすまし INSERT を防ぐ）

-- (2) user_id を持たない子表: 親テーブルを EXISTS で辿る
CREATE POLICY p_training_session_details_self ON training_session_details
  FOR ALL TO authenticated
  USING (EXISTS (SELECT 1 FROM training_sessions s
                 WHERE s.id = training_session_details.session_id
                   AND s.user_id = <本人ID>))
  WITH CHECK (EXISTS (SELECT 1 FROM training_sessions s
                      WHERE s.id = training_session_details.session_id
                        AND s.user_id = <本人ID>));

-- (3) 共通マスタ foods: user_id を持たない。本人分離の対象外。
--     認証済みなら参照可、書き込みはサーバ側（FEAT-10 のCSV取込）に限定する。
ALTER TABLE foods ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_foods_read ON foods FOR SELECT TO authenticated USING (true);
```

規約として固定する点:

- **ポリシー名は `p_<テーブル名>_<用途>`**（`p_meal_logs_self` / `p_foods_read`）。
- **`WITH CHECK` を必ず書く**。`USING` だけだと他人の `user_id` を指定した INSERT を止められない。
- **`TO authenticated` を明示**し、`anon` ロールには一切の権限を与えない（NFR-SEC-01）。
- `users` 自身も RLS 対象とし、本人行のみ参照・更新できるようにする（FEAT-06 の体重・目標）。
- **接続は常にユーザーのセッション（JWT）で行う。** Flutter は PostgREST・RPC・Edge Function をすべて本人のJWTで叩く。
- Edge Function も受け取ったJWTを引き継いで接続する。
- **service role キーの用途を限定する。** RLS を迂回するため、本人データに触れない処理だけに使う（例: `replace_foods`・FEAT-10）。
- 置き場所は Edge Function の環境変数または `security definer` 関数の内側に限る。Flutter 側には一切置かない（NFR-SEC-02）。
- **RLS が唯一の防御線になる。** Flutter が PostgREST を直接叩く構成では、サーバ側ハンドラでの二重チェックが無い。
- ポリシーの1行の誤りが、そのままデータ漏洩になる。

> ⚠️ 要確認（人間判断）: **`gyms` と `training_machines` は所有者列を持たず、RLS方針が決まっていない。**
> `gyms`（ジム）は公共施設。全ユーザー共通マスタとして `foods` と同じ扱いでよさそうに見える。
> 一方 `training_machines` は、`machine_menus`→`training_menus.user_id` を辿ると本人所有に見え、`gym_id`→`gyms` を辿ると共有マスタに見える。
> 構造は `../30_データ・IF設計/01_データモデル.md` §8-1 の「部位→器具」の多ホップと同じ。
> **共有マスタなら他人が登録した器具が見えることになり、本人所有なら FEAT-02 の絞り込みクエリに JOIN が1本増える。**
> 単一ユーザー運用では顕在化しないが、Phase2 のマルチユーザー化で必ず問題になる。

### 4.2 `users.id`（bigint）と Supabase `auth.uid()`（uuid）の紐付け ★本書が正本

ADR-0004 は「`user_id = auth.uid()` **相当**の RLS」と書いているが、**そのままでは型が合わない**。

- `01_DB物理設計.md §1.1`: `users.id` は `bigint GENERATED ALWAYS AS IDENTITY`。各履歴の `user_id` も `bigint`。
- Supabase Auth: 認証済みユーザーの識別子は `auth.users.id`＝**`uuid`**、SQL からは `auth.uid()`（`uuid` を返す）で取得する。

したがって `user_id = auth.uid()` は `bigint = uuid` の比較になり、**そのままでは実行できない**。
RLSポリシーを書く前に、どう紐付けるかを決める必要がある。選択肢は次の3つ。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | `users.id` を `uuid` に変え、`auth.users.id` と同値にする（`references auth.users(id)`） | RLSが最短形（`user_id = auth.uid()`）で書ける。Supabase の定石 | **10表すべての `id`/`user_id` 型変更**が要る。`01_DB物理設計.md` の前提（全 `id` は bigint）が崩れ、INDEXサイズも増える |
| B | `users` に `auth_user_id uuid unique not null` 列を追加し、`users.id`（bigint）は据え置く | 既存の型・DDLをほぼ維持できる。追加は1列 | RLSが `user_id = (SELECT id FROM users WHERE auth_user_id = auth.uid())` になり、**全ポリシーにサブクエリが入る**（`SELECT` を1回に畳む工夫が要る） |
| C | RLS を使わず、全アクセスを Edge Function 経由にして関数内で `user_id` を絞る | 型問題が起きない | **ADR-0004 の決定（RLSで本人分離）から外れる**。絞り忘れが即データ漏洩になり、防御が1層だけになる。さらに **PostgREST 直接アクセスを一切使えなくなり**、全CRUDを Edge Function で書き直すことになる（`07_実装共通設計パターン.md` の方式割り当てが崩れる） |

> ⚠️ 要確認（人間判断）: **上記 A / B / C のどれを採るか未決。本書では確定させない。**
> この論点は `01_DB物理設計.md`（列定義）・ADR-0004（RLS方針）・各機能設計（クエリの `user_id` 絞り込み）に同時に波及する。
> したがって**実装着手前に人間が決めて ADR を起票する必要がある**。案Aなら ADR-0004 の Superseded、案Bなら物理設計の列追加、案Cなら ADR-0004 の修正。
> それまで各機能設計の RLS 記述は「`user_id = <本人ID>` 相当」の抽象表現にとどめること。
> なお **単一ユーザー運用中は `users` に行が1件しか無いため、どの案でも動いてしまう**。問題が Phase2 まで顕在化しない点に注意。

> ⚠️ 要確認（人間判断）: **`users` に一意キーが無い**（`01_DB物理設計.md §1.1`「一意性: 単一ユーザー運用のため当面なし」）。
> 案Bを採る場合の `auth_user_id unique` がそのまま一意キーになる。
> 一方 案C を採ると、「同じ人の `users` 行が2つできる」事故を DB 側で防げない。

## 5. 物理命名規約（横断）
> 📝 旧「用語定義 §5 命名規約」から集約した、DBの外に及ぶ物理命名の横断規約。DBテーブル・カラムの命名は §2、ID接頭辞は `../../01_要件定義/00_用語定義.md §3` を正とする。本節は enum／API／JSON／エラーコード／環境／内部サービスの物理命名を扱う（将来は共通ハーネス運用へ）。

| 対象 | 規約 | 例 |
|---|---|---|
| enum | **名は snake_case・単数形**。**値は日本語をそのまま格納する**（RULE-003） | `body_part`＝`胸`/`背中`/`脚`/`肩`/`腕` |
| Edge Function | **kebab-case・`<動詞>-<目的語>`**。バージョン番号を名前に含めない | `generate-menu`（FEAT-03）／`analyze-meal`（FEAT-08） |
| RPC（Postgres 関数） | **snake_case・`<動詞>_<目的語>`**。テーブル名と同じ語を関数名にしない | `get_dashboard`／`get_protein_remaining`／`create_training_session`／`replace_foods` |
| RPC の引数 | **`p_` 接頭辞**。列名との衝突を避ける | `p_rows`／`p_user_id` |
| PostgREST のリソース | **テーブル名そのもの**。別名・ビュー経由の改名をしない | `supabase.from('training_sessions')` |
| JSONフィールド | **snake_case。DB列名と一致させる**。単位接尾辞も落とさない | `protein_g`／`calories_kcal`／`body_part`／`performed_date`／`is_done` |
| エラー/警告コード | `ERR-<DOMAIN>-<3桁連番>`。**DOMAIN はハイフンを含まない大文字英字1語** | `ERR-AUTH-001`／`ERR-VALIDATION-001` |
| 環境 | `dev` / `prod` の2環境（すべて小文字） | — |
| 内部サービス名 | `okada-fit-<役割>`（kebab-case） | `okada-fit-app`／`okada-fit-fn`／`okada-fit-db` |

補足:

| 対象 | 補足 |
|---|---|
| enum | 表示ラベルとDB値が同一なので写像表を持たない（DB表現は §1・§2 を正とする） |
| enum の改訂 | 値の追加・変更は `01_DB物理設計.md §4` の enum定義と CHECK 制約を同時に改訂する |
| Edge Function | 呼び出しは `supabase.functions.invoke('<name>')`。URL は `{SUPABASE_URL}/functions/v1/<name>` に固定され、設計側で決められるのは名前だけ |
| Edge Function のバージョン | **バージョンパスは持たない**（単一クライアントのため。[`../30_データ・IF設計/02_API設計.md`](../30_データ・IF設計/02_API設計.md) §1） |
| 呼び出し方式の使い分け | **AIを呼ぶものだけ Edge Function**。集計は RPC、単純CRUDは PostgREST 直接（`07_実装共通設計パターン.md`） |

| JSONフィールド | キャメルケース変換は**行わない**。DB列名・IF・型定義の三重管理を避けるため（`../30_データ・IF設計/02_API設計.md` §3 のスキーマ例と一致） |
| JSONフィールドの実装 | TypeScript（Edge Function）側は snake_case のまま扱う。Dart は言語規約上 lowerCamelCase になるため、**変換は `fromJson`/`toJson` の1箇所に閉じる** |
| エラーコード | 連番は `001` から機能ドメイン単位で採番する |

| 環境 | `stg` の要否は本書では決めない。[`../20_インフラ設計/01_システム構成・環境.md`](../20_インフラ設計/01_システム構成・環境.md) §2 の ⚠️ に従う（同ファイルが正本） |

> ⚠️ 要確認（人間判断）: **エラーコードの実態が規約 `ERR-<DOMAIN>-<3桁連番>` に従っていない。**
