| 項目 | 内容 |
|---|---|
| 移行元 | **なし（新規開発）**。置き換える既存システム・手作業ツールが無い |
| 根拠 | NFR-MIGR-01：データ移行は適用外 |
| 移行方式 | **該当なし**。一括／並行稼働／段階のいずれも成立しない |
| 本書が担うもの | 初期データ投入（NFR-MIGR-02）とDBスキーマ変更（NFR-MIGR-03）の2つ |
| 並行稼働 | なし。並行させる旧系が無い |

| 許容停止時間 | 移行に伴う業務停止は発生しない（NFR-MIGR-01） |

### 停止の考え方

構成が3層に分かれるため、層ごとに整理する。

| 層 | 切替時の停止 |
|---|---|
| DBスキーマ | `supabase db push` の適用中のみ。数秒〜数分 `[仮]` |
| Edge Function | `supabase functions deploy` は無停止に近い。旧バージョンの実行中リクエストが終わるまでの数秒 `[仮]` |
| Flutter アプリ | **停止という概念が無い。** 端末の旧ビルドは、利用者が新ビルドを入れるまで動き続ける |

### 「移行」の読み替え

本書における語の意味を固定する。

| 用語 | 本PJでの意味 |
|---|---|
| リハーサル | ローカル環境（`supabase start`）でのマイグレーション試行 |
| カットオーバー | **初回リリース**。スキーマ適用＋Edge Function デプロイ＋**TestFlight 配布**＋初期投入 |
| 切戻し | Edge Function 再デプロイ＋down マイグレーション＋TestFlight で前ビルド再配布（§5） |

### 配布とスコープ

- 初回リリースは **iOS 先行**。App Store への一般公開は行わない。
- 配布は **TestFlight にとどめる**。利用者1名のため、ストア審査・公開の工程を持たない。
- 過去のトレーニング・食事の記録を遡って入力することは**スコープ外**。紙・手書き記録の取り込みも行わない。
- 蓄積するのは運用開始日以降の記録だけ。

## 2. 移行対象とデータマッピング
> 📝 ここに移行するデータと変換規則を記載。**移行するもの／しないもの（対象外宣言）**を明示する。{移行元項目 → 本システム項目（DM-__）／変換規則／初期投入の要否}

### 初期投入するもの

| 移行元 | 本システム（DM-ID） | 変換規則 | 備考 |
|---|---|---|---|

| なし（新規） | `gyms`（DM-02） | 手動登録（FEAT-01・`supabase.from('gyms').insert(...)`）。ジム名のみ | `training_machines` の前提。初回は通うジム1件で足りる |

### 初期マスタ投入の方針

- 初期マスタは5つ。`users` / `gyms` / `training_menus` / `training_machines` / `foods`。

- 投入用の一括スクリプト・シードSQLは持たない。
- 理由: アプリの画面で完結させ、投入経路を二重に作らないため。

## 3. 移行手順（リハーサル→本番）
> 📝 ここに移行の実行手順を、リハーサル（検証環境）→本番の順で記載。各ステップの実行者・所要・検証方法・中断条件を明示する。%% ここに記載（実データは書かない）

本節は**DBスキーマ変更（マイグレーション）の実行手順**として読み替えて定義する（NFR-MIGR-03：可逆マイグレーション）。
初回リリースも「空のDBに全 up を適用する」という同じ手順に収まる。

### 3.1 手順の骨子

```
事前   : 本番DBの手動エクスポートを取得（無料枠に自動バックアップは無い＝これが唯一の復元元・§5）
作成   : supabase migration new <name> で up SQL を作成し、対になる down SQL を同一PRで必ず書く
         破壊的変更（列削除・型変更）は 1マイグレーションに混ぜず、下記「段階的手順」に分割する
リハーサル: ローカル（supabase start / supabase db reset）で全 up を先頭から再適用し、
         初期マスタ投入（§2）→ 主要ユースケースの疎通（§6）まで通す
可逆確認: down を適用 → スキーマが直前状態に戻ることを確認 → 再度 up を適用（up→down→up が通ること）
本番適用: supabase db push（up のみ適用）
関数配備: supabase functions deploy <name>（generate-menu / analyze-meal）
アプリ配布: iOS ビルドを App Store Connect にアップロード → TestFlight で配布 → 端末で更新
事後確認: §6 のチェックリストを消化。NGなら §5 の切戻し
```

### 3.2 適用順序は「DB → Edge Function → アプリ」に固定する

| # | 順序の理由 |
|---|---|
| 1 | アプリ配布が最も遅い（TestFlight のビルド処理・端末での更新操作） |
| 2 | 先にアプリを配ると、まだ無いテーブル・関数を呼ぶ |
| 3 | Edge Function は DB の RPC・テーブルに依存する。DBより先に配ると失敗する |
| 4 | この順序なら、途中で止めても「新しいDB＋旧アプリ」の状態にとどまる |
| 5 | §3.4 の段階的手順を守っていれば、その状態でも旧アプリは動き続ける |

### 3.3 Supabase のマイグレーション運用（規約）

| # | 規約 | 理由・補足 |
|---|---|---|
| 1 | マイグレーションSQLは `supabase/migrations/<timestamp>_<name>.sql` に置き、**git 管理する** | `20_インフラ設計/02_IaC・デプロイ・可用性配置.md` の「DBスキーマは Supabase マイグレーション `[仮]`」を具体化 |
| 2 | ダッシュボードのSQLエディタで本番スキーマを直接変更しない | 変更履歴が git から消える |
| 3 | 適用順序は必ず **ローカル → 本番** | ローカルで通っていないSQLを本番に流さない |
| 4 | **up と down は必ず対で用意する** | NFR-MIGR-03（可逆マイグレーション） |
| 5 | down は `supabase/rollback/<up と同名>.down.sql` に置き、psql で手動適用する `[仮]` | Supabase CLI は down 適用のコマンドを標準では持たない |
| 6 | 1マイグレーション＝1つの意味のある変更 | 無関係な変更を混ぜると down の粒度が粗くなり戻せない |
| 7 | RPC（Postgres 関数）も同じ仕組みで管理する | `07_実装共通設計パターン.md §2` で採用。up は `CREATE OR REPLACE FUNCTION`、down は `DROP FUNCTION`（または直前定義の `CREATE OR REPLACE`） |
| 8 | RLS ポリシーも up/down を対にする | 同上 |
| 9 | **`auth.users` へのトリガ・関数も up/down を対にする** | `handle_new_user()` と `on_auth_user_created`（ADR-0005）。up は `CREATE FUNCTION`＋`CREATE TRIGGER`、down は `DROP TRIGGER`＋`DROP FUNCTION`。`auth` スキーマ側の変更のため、消し忘れるとサインアップが壊れたまま残る |
| 10 | **Edge Function は git のコードが唯一の正** | `supabase/functions/<name>/index.ts` をデプロイする。ダッシュボードのエディタで直接書き換えない |

> ⚠️ 要確認（人間判断）: 規約5（down の置き場所と psql 手動適用）は `[仮]`。この方式で確定してよいか。

### 3.4 破壊的変更（列削除・型変更）の段階的手順

列の削除・型変更・NOT NULL 化・リネームは一発で行わない。旧アプリと新スキーマが一時的に同居するためである。
次の5段階に分け、**①〜③と⑤を別リリースにする**。

**本構成では同居期間が長い。** 端末に入った旧ビルドは、利用者が更新するまで動き続ける（§1）。段階を飛ばすリスクが旧構成より高い。

| 段階 | 作業 | 可逆性 |
|---|---|---|
| ① 追加 | 新列を **NULL 許容**で追加する（既定値があれば付ける）。旧列はそのまま残す | down で `DROP COLUMN`（データ損失なし） |
| ② 両書き | アプリと Edge Function を新旧**両方の列に書く**実装に変えて配布する。読み取りはまだ旧列 | 戻せるが即時ではない（アプリの再配布が要る・§5） |
| ③ バックフィル | 既存行の新列を UPDATE で埋める。件数を照合する | 新列を NULL に戻せば元に戻る |
| ④ 切替 | 読み取りを新列に切り替えて配布する。必要ならここで新列を NOT NULL 化する | 同上（アプリの再配布が要る） |
| ⑤ 削除 | **十分な安定期間の後、別リリースで**旧列を削除する。ここが point of no return（§5） | down では戻せない（バックアップからの復元が必要） |

## 5. 切戻し（ロールバック）
> 📝 ここに移行失敗時の戻し方を記載。**「どの判定でNGなら・どこまで・どう戻すか」**を、いつでも安全側に倒せるように定義する。{切戻し判断基準／手順／移行元の再稼働／データ二重反映の防止}

### 5.1 前提となる非対称性（最重要）

**戻す速さが層ごとに大きく違う。** いちばん遅いのがアプリで、そこが本構成の急所になる。

| 層 | 戻し方 | 所要 | 即時性 |
|---|---|---|---|
| Edge Function | git の直前コミットから `supabase functions deploy` で再デプロイ | 数分 | ○ ほぼ即時 |
| DBスキーマ | 対応する down SQL を逆順に手動適用（§3） | 数分〜数十分 | △ 手動。順序ミス・適用漏れの余地あり |
| Flutter アプリ | TestFlight で前ビルドを再配布 → 端末で再インストール | 数十分〜数時間 `[仮]` | **× 即時ではない** |

**アプリが即時に戻らない理由**

| # | 理由 |
|---|---|
| 1 | App Store Connect のビルド処理待ちが入る（アップロード後、配布可能になるまで十数分〜 `[仮]`） |
| 2 | ビルド番号は前進しかできない。実際には「前のコードにビルド番号を振り直して再アップロード」になる `[仮]` |
| 3 | 配布しても、**利用者が端末で更新操作を行うまで旧ビルドが動き続ける**。無人では切り替わらない |

**DBはアプリを戻しても戻らない**

| # | 内容 |
|---|---|
| 1 | 適用済みのマイグレーションは、アプリの再配布では元に戻らない |
| 2 | 旧アプリ＋新スキーマが動くかは、§3.4 の段階的手順を守れているかに完全に依存する |
| 3 | 具体的には「旧列を同一リリースで消していないか」に尽きる |

したがって切戻しは **「Edge Function」→「DB」→「アプリ」の3段階**で考える。
速く戻る層から順に試し、アプリの再配布は最後の手段とする。

> ⚠️ 要確認（人間判断）: **NFR-MAINT-02「以前のデプロイに戻せる」は本構成では成立しない。**
> 理由は上表のとおり、アプリの切戻しが即時にならないため。
> 同要件は Vercel の即時デプロイロールバックを前提に書かれている。
> **`01_要件定義/04_非機能要件.md §4.1` の改訂が必要。**
> 改訂案 `[仮]`: 「Edge Function とDBスキーマは即時に戻せること。アプリは前ビルドを再配布できること（即時性は問わない）」。
> 段1は別ブランチのため本書では変更しない。

### 5.2 切戻しの判断基準

次のいずれかに該当したら、前進せず切戻す。

| # | 条件 |
|---|---|
| 1 | `supabase db push` がエラーで中断した |
| 2 | `supabase functions deploy` に失敗した、または Edge Function が疎通しない |
| 3 | §6 の主要ユースケース疎通がNG |
| 4 | CSV取込件数がCSVの有効行数と一致しない |
| 5 | RLS が効かず本人以外の行が見える／未認証でアクセスできる（NFR-SEC-01） |
| 6 | AI機能以外（記録・閲覧）が使用不能 |

- AI機能だけが使えない場合は切戻さない。縮退で許容する（NFR-AVAIL-05）。

### 5.3 切戻し手順

| 順 | 手順 | 内容 | 所要 |
|---|---|---|---|
| 1 | **Edge Function を戻す** | git の直前の正常コミットをチェックアウトし `supabase functions deploy` を実行する。AI機能の不具合はここで戻る | 数分 |
| 2 | **DBを戻す** | 今回の up に対応する down SQL を適用と**逆順**に手動適用する（`supabase/rollback/*.down.sql`・§3）。適用後に現行アプリの正常動作を確認する | 数分〜数十分 |
| 3 | **アプリを戻す** | 1・2 で復旧しない場合のみ。前のコードでビルドし直し TestFlight へ上げ、端末で再インストールする。**この間はアプリが使えない**（§5.1） | 数十分〜数時間 |
| 4 | **バックアップから復元する** | 段階⑤（列削除）等で down では戻せない場合。**事前の手動エクスポート（§3.1）が唯一の復元元**。無料枠には自動バックアップも PITR も無い。エクスポートを取っていなければ復元できない。RTO 数時間（NFR-AVAIL-03）を許容とし、復元時点以降の記録は失われる | 数時間 |

**無料枠のバックアップ（確定値）**。出典は公式の料金ページ（2026-08-08 確認）。正本は `20_インフラ設計/01_システム構成・環境.md §2`。

| 機能 | 無料枠 | 切戻しへの帰結 |
|---|---|---|
| 自動バックアップ | **含まれない** | 取り忘れれば復元元がゼロになる |
| PITR（特定時点復元） | **利用できない** | 障害直前へは戻せない。戻せるのはエクスポート時点だけ |
| 手動エクスポート | 自分で実行する | **§5 の切戻しは事前の手動エクスポートが唯一の頼りになる** |

- RPO は「最後にエクスポートした時点」で決まる。
- したがって §3.1 の「事前エクスポート」は推奨ではなく**必須の手順**になる。

**日次自動エクスポートを取る（確定・ADR-0017）。** これで **NFR-AVAIL-02（RPO ≤24時間）を満たす。**

| 項目 | 値 |
|---|---|
| 手段 | `supabase db dump`（**Docker Desktop が前提**） |
| 頻度 | 日次。岡田さんの Mac の launchd。**人手を介さない** |
| RPO | 24時間 |

- 切戻し時に失うのは**最大でも直近24時間分**の記録になる。
- ただし §3.1 の事前エクスポートは**別途取る**。日次ジョブとは独立した必須手順である。
- 理由は2つ。日次ジョブは適用直前のタイミングで走るとは限らない。Mac が落ちていれば当日分が無い。
- 実行を忘れた回のリリースは、段階⑤（§3.4）に入った時点で戻す手段が無くなる。

### 5.4 データ二重反映の防止

| 対象 | 再投入時の挙動 |
|---|---|
| `foods`（CSV） | **重複しない。** `foods.name` の UNIQUE（`uq_foods_name`）＋ `import_foods` の `ON CONFLICT (name) DO NOTHING` で冪等（ADR-0007） |
| `foods` の注意 | 冪等性の担保は**DB制約側**にある。取込方式を変えても重複は入らない。ただし既存行は上書きされないため、値を直したいときは手で更新する |
| `gyms` / `training_menus` / `training_machines`（手動登録） | **重複しうる。** 一意制約が無く、画面から同じ内容を再登録できる |
| 手動登録の対策 | 切戻し前に件数を控えておく |

### 5.5 point of no return

次のいずれかを過ぎたら、切戻しではなく前進（fix-forward）を既定とする。

| # | 通過点 | 過ぎるとどうなるか |
|---|---|---|
| (a) | 本番で実データの記録が始まった時点。最初の `meal_logs` / `training_sessions` の INSERT 以降 | 復元すると、**最後の手動エクスポート以降**の記録が失われる。自動バックアップも PITR も無いため、失う量はエクスポートの間隔で決まる（§5.3） |
| (b) | 破壊的変更の段階⑤（旧列の削除）を適用した時点（§3.4） | down では戻せない。バックアップ復元のみが手段になる |

- §4 の時間割では **T+1:15（主要ユースケース疎通）以降**が (a) に該当する。
- それ以前なら「本番DBを空にして作り直す」のが最も安全な戻し方になる `[仮]`。
