## 1. 移行方針
> 📝 ここに移行の全体方針を記載。{移行元（既存システム/手作業）／移行方式（一括ビッグバン／並行稼働／段階移行）／並行稼働の有無と期間／許容停止時間（NFR-MIGR-__）／移行元の廃止時期}

| 項目 | 内容 |
|---|---|
| 移行元 | **なし（新規開発）**。既存システム・置き換え対象の手作業ツールのいずれも存在しない（NFR-MIGR-01：データ移行は適用外） |
| 移行方式 | 本PJでは該当なし（移行元が無いため一括／並行稼働／段階のいずれも成立しない）。本書が担うのは **初期データ投入（NFR-MIGR-02）** と **DBスキーマ変更（NFR-MIGR-03）** |
| 並行稼働 | なし（並行させる旧系が無い）。初回リリース後は本システム単独で稼働する |
| 許容停止時間 | 移行に伴う業務停止は発生しない（NFR-MIGR-01）。利用者は岡田さん1名のため停止調整は不要 |
| 移行元の廃止 | 本PJでは該当なし（廃止すべき旧系が無い） |

**停止の考え方（構成が3層に分かれるため整理する）**

| 層 | 切替時の停止 |
|---|---|
| DBスキーマ | `supabase db push` の適用中のみ。数秒〜数分 `[仮]` |
| Edge Function | `supabase functions deploy` は無停止に近い。旧バージョンの実行中リクエストが終わるまでの数秒 `[仮]` |
| Flutter アプリ | **停止という概念が無い。** 端末に入っている旧ビルドは、利用者が新ビルドを入れるまで動き続ける |

- 本書における「移行」の読み替えを固定する。

| 用語 | 本PJでの意味 |
|---|---|
| リハーサル | ローカル環境（`supabase start`）でのマイグレーション試行 |
| カットオーバー | **初回リリース**＝スキーマ適用＋Edge Function デプロイ＋**TestFlight へのビルド配布**＋初期投入 |
| 切戻し | Edge Function の再デプロイ＋down マイグレーション＋TestFlight での前ビルド再配布（§5） |

- 初回リリースは **iOS 先行**。App Store への一般公開は行わず、**TestFlight 配布にとどめる**。利用者は岡田さん1名のため、ストア審査・公開の工程を持たない。
- 過去のトレーニング・食事の記録を遡って入力すること（紙・手書き記録の取り込み）は**スコープ外**。運用開始日以降の記録のみを蓄積する。

## 3. 移行手順（リハーサル→本番）
> 📝 ここに移行の実行手順を、リハーサル（検証環境）→本番の順で記載。各ステップの実行者・所要・検証方法・中断条件を明示する。%% ここに記載（実データは書かない）

本節は**DBスキーマ変更（マイグレーション）の実行手順**として読み替えて定義する（NFR-MIGR-03：可逆マイグレーション）。初回リリースも「空のDBに全 up を適用する」という同じ手順に収まる。

```
事前   : 本番DBのバックアップ／エクスポートを取得（NFR-AVAIL-02 RPO≤24時間・実仕様は §5 ⚠️）
作成   : supabase migration new <name> で up SQL を作成し、対になる down SQL を同一PRで必ず書く
         破壊的変更（列削除・型変更）は 1マイグレーションに混ぜず、下記「段階的手順」に分割する
リハーサル: ローカル（supabase start / supabase db reset）で全 up を先頭から再適用し、
         初期マスタ投入（§2）→ 主要ユースケースの疎通（§6）まで通す
可逆確認: down を適用 → スキーマが直前状態に戻ることを確認 → 再度 up を適用（up→down→up が通ること）
本番適用: supabase db push（up のみ適用）
関数配備: supabase functions deploy <name>（generate-menu / analyze-meal）
アプリ配布: iOS ビルドを App Store Connect にアップロード → TestFlight で配布 → 端末で更新
事後確認: §6 のチェックリストを消化。NGなら §5 の切戻し
```

**適用順序を「DB → Edge Function → アプリ」に固定する。**

| # | 順序の理由 |
|---|---|
| 1 | アプリ配布が最も遅い（TestFlight のビルド処理・端末での更新操作）。先に配ると、まだ無いテーブル・関数を呼ぶ |
| 2 | Edge Function は DB の RPC・テーブルに依存する。DBより先に配ると失敗する |
| 3 | この順序なら、途中で止めても「新しいDB＋旧アプリ」の状態にとどまる。§3 の段階的手順を守っていれば旧アプリは動き続ける |

**Supabase のマイグレーション運用（規約）**

- マイグレーションSQLは `supabase/migrations/<timestamp>_<name>.sql` に置き、**git 管理する**（`20_インフラ設計/02_IaC・デプロイ・可用性配置.md` の「DBスキーマは Supabase マイグレーション `[仮]`」を具体化）。ダッシュボードのSQLエディタで本番スキーマを直接変更しない（変更履歴がgitから消えるため）。
- 適用順序は必ず **ローカル → 本番**。ローカルで通っていないSQLを本番に流さない。
- **up と down は必ず対で用意する**（NFR-MIGR-03）。Supabase CLI は down 適用のコマンドを標準では持たないため、規約として `supabase/rollback/<up と同名>.down.sql` に置き、切戻し時は psql で手動適用する `[仮]`。⚠️ 要確認（人間判断）。
- 1マイグレーション＝1つの意味のある変更。複数の無関係な変更を1ファイルに混ぜない（down の粒度が粗くなり戻せなくなる）。
- `07_実装共通設計パターン.md §2` で採用する Postgres 関数（RPC）も同じ仕組みで管理する。up で `CREATE OR REPLACE FUNCTION`、down で `DROP FUNCTION`（または直前定義の `CREATE OR REPLACE`）を書く。RLS ポリシーも同様に up/down を対にする。
- **Edge Function は git のコードが唯一の正**。`supabase/functions/<name>/index.ts` をデプロイし、ダッシュボードのエディタで直接書き換えない。

**破壊的変更（列削除・型変更）の段階的手順**

列の削除・型変更・NOT NULL 化・リネームは、旧アプリと新スキーマが一時的に同居するため一発で行わない。次の5段階に分け、**①〜③と⑤を別リリースにする**。

**本構成では同居期間が長い。** 端末に入った旧ビルドは、利用者が更新するまで動き続ける（§1）。段階を飛ばすリスクが旧構成より高い。

| 段階 | 作業 | 可逆性 |
|---|---|---|
| ① 追加 | 新列を **NULL 許容**で追加する（既定値があれば付ける）。旧列はそのまま残す | down で `DROP COLUMN`（データ損失なし） |
| ② 両書き | アプリと Edge Function を新旧**両方の列に書く**実装に変えて配布する。読み取りはまだ旧列 | 戻せるが即時ではない（アプリの再配布が要る・§5） |
| ③ バックフィル | 既存行の新列を UPDATE で埋める。件数を照合する | 新列を NULL に戻せば元に戻る |
| ④ 切替 | 読み取りを新列に切り替えて配布する。必要ならここで新列を NOT NULL 化する | 同上（アプリの再配布が要る） |
| ⑤ 削除 | **十分な安定期間の後、別リリースで**旧列を削除する。ここが point of no return（§5） | down では戻せない（バックアップからの復元が必要） |

- リハーサル: **ローカルの Supabase（`supabase start`）で全手順を通す**。所要時間と失敗点を洗い出し、本番適用のウィンドウ（§4）を見積もる。⚠️ 要確認（人間判断）: 本番と別のステージング用 Supabase プロジェクトを持つか（無料枠のプロジェクト数制限に依存。`20_インフラ設計/02_IaC・デプロイ・可用性配置.md` は dev/prod を環境変数で切替 `[仮]` とだけ定めている）。
- 凍結ウィンドウ: 利用者が岡田さん1名（＝作業者本人）のため、**形式的な更新凍結の手続きは不要**。適用中は本人がアプリを操作しないだけでよい。凍結の告知・受付停止画面は作らない。

## 5. 切戻し（ロールバック）
> 📝 ここに移行失敗時の戻し方を記載。**「どの判定でNGなら・どこまで・どう戻すか」**を、いつでも安全側に倒せるように定義する。{切戻し判断基準／手順／移行元の再稼働／データ二重反映の防止}

**前提となる非対称性（最重要）**

戻す速さが層ごとに大きく違う。**いちばん遅いのがアプリ**である点が本構成の急所になる。

| 層 | 戻し方 | 所要 | 即時性 |
|---|---|---|---|
| Edge Function | git の直前コミットから `supabase functions deploy` で再デプロイ | 数分 | ○ ほぼ即時 |
| DBスキーマ | 対応する down SQL を逆順に手動適用（§3） | 数分〜数十分 | △ 手動。順序ミス・適用漏れの余地あり |
| Flutter アプリ | TestFlight で前ビルドを再配布 → 端末で再インストール | 数十分〜数時間 `[仮]` | **× 即時ではない** |

**アプリが即時に戻らない理由**

| # | 理由 |
|---|---|
| 1 | App Store Connect のビルド処理待ちが入る（アップロード後、配布可能になるまで十数分〜 `[仮]`） |
| 2 | ビルド番号は前進しかできない。実際には「前のコードにビルド番号を振り直して再アップロード」になる `[仮]` |
| 3 | 配布しても、**利用者が端末で更新操作を行うまで旧ビルドが動き続ける**。無人では切り替わらない |

**DBは戻らない**

- 適用済みのマイグレーションは**アプリの再配布では元に戻らない**。
- 旧アプリ＋新スキーマの組合せが動くかどうかは、§3 の段階的手順を守れているか（旧列を同一リリースで消していないか）に完全に依存する。

したがって切戻しは **「Edge Function を戻す」→「必要ならDBを戻す」→「必要ならアプリを戻す」の3段階**で考える。速く戻る層から順に試し、アプリの再配布は最後の手段とする。

> ⚠️ 要確認（人間判断）: **NFR-MAINT-02「以前のデプロイに戻せる」が、本構成では成立しない。** 同要件は Vercel の即時デプロイロールバックを前提に書かれている。Flutter + Supabase では上表のとおりアプリの切戻しが即時にならず、要件の文言をそのまま満たせない。**非機能要件（`01_要件定義/04_非機能要件.md §4.1`）の改訂が必要**。改訂案は「Edge Function とDBスキーマは即時に戻せること。アプリは前ビルドを再配布できること（即時性は問わない）」`[仮]`。段1は別ブランチのため本書では変更しない。

- 切戻し判断: 次のいずれかに該当したら前進せず切戻す —— (1) `supabase db push` がエラーで中断した、(2) `supabase functions deploy` に失敗した、または Edge Function が疎通しない、(3) §6 の主要ユースケース疎通がNG、(4) CSV取込件数がCSVの有効行数と一致しない、(5) RLS が効かず本人以外の行が見える／未認証でアクセスできる（NFR-SEC-01）、(6) AI機能以外（記録・閲覧）が使用不能（AI機能のみの不達は縮退で許容・NFR-AVAIL-05）。
- 切戻し手順:
  1. **Edge Function を戻す**: git の直前の正常コミットをチェックアウトし `supabase functions deploy` を実行する（数分）。AI機能の不具合はここで戻る。
  2. **DBを戻す**: 今回適用した up に対応する down SQL を、適用と**逆順**に手動適用する（`supabase/rollback/*.down.sql`・§3）。適用後に現行アプリが正常動作することを確認する。
  3. **アプリを戻す**: 1・2 で復旧しない場合のみ。前のコードでビルドし直し、TestFlight へアップロードして端末で再インストールする。**この間はアプリが使えない状態が続く**（上表）。
  4. **down で戻せない場合**: 段階⑤（列削除）を実施済み等でデータが失われている場合は、**Supabase のバックアップ／事前エクスポート（§3 事前）から復元**する。RPO は ≤24時間（NFR-AVAIL-02）、RTO は数時間（NFR-AVAIL-03）を許容とし、復元時点以降の記録は失われる。⚠️ 要確認（人間判断）: 無料枠でどのバックアップ機能が使えるか（自動バックアップの有無・保持世代・PITR の可否）は未検証（NFR-AVAIL-04 も「無料枠のバックアップ範囲は限定的」として ⚠️ のまま）。ここが確定するまで、**事前の手動エクスポートを切戻しの前提**とする `[仮]`。
- 移行元の再稼働: **本PJでは該当なし**（再稼働させる旧系が存在しない・§1）。切戻し後の状態は「本システムの1つ前のバージョン」であり、旧系への退避先は無い。
- データ二重反映の防止:

| 対象 | 再投入時の挙動 |
|---|---|
| `foods`（CSV） | **重複しない。** FEAT-10 の `replace_foods` が全置換（DELETE ALL → バルクINSERT）で冪等 `[仮]`。ただし `foods.name` に一意制約が無いため upsert は選べず、全置換以外の実装に変えると重複する（`01_DB物理設計.md §1.5`） |
| `gyms` / `training_menus` / `training_machines`（手動登録） | **重複しうる。** 一意制約が無く、画面から同じ内容を再登録できる。切戻し前に件数を控えておく |

- **point of no return**: 次のいずれかを過ぎたら切戻しではなく前進（fix-forward）を既定とする。
  - **(a) 本番で実データの記録が始まった時点**（最初の `meal_logs` / `training_sessions` の INSERT 以降）。これ以降にバックアップから復元すると、最大24時間分（NFR-AVAIL-02）の記録が失われる。§4 の時間割では **T+1:15（主要ユースケース疎通）以降**が該当し、それ以前は「本番DBを空にして作り直す」のが最も安全な戻し方になる `[仮]`。
  - **(b) 破壊的変更の段階⑤（旧列の削除）を適用した時点**（§3）。down では戻せず、バックアップ復元のみが手段になる。

**敵対的検証・要確認事項**

| # | 論点 | 内容 | 重大度 |
|---|---|---|---|
| 1 | NFR-MAINT-02 が成立しない | 同要件は「以前のデプロイに即時ロールバックできる」ことを前提に書かれている。Flutter + Supabase ではアプリの切戻しに TestFlight の再配布と端末での再インストールが要り、**即時性を満たせない**（§5）。要件の改訂と、切戻し所要の実測が要る | 🔴 高 |
| 2 | down の適用手段が確立していない | Supabase CLI に down 適用コマンドが無く、§3 では「`supabase/rollback/*.down.sql` を psql で手動適用」を `[仮]` としている。手順が実際に通るか未検証で、**NFR-MIGR-03（可逆）が仕組みとして担保されていない**。手動適用は順序ミス・適用漏れが起きやすい | 🔴 高 |
| 3 | バックアップの実仕様が未確認 | 切戻し最後の砦がSupabase無料枠のバックアップだが、自動バックアップの有無・保持世代・PITR の可否が未検証（NFR-AVAIL-04 も ⚠️ のまま）。事前の手動エクスポートに依存する運用は、実行忘れが単一障害点になる | 🔴 高 |
| 4 | 旧ビルドと新スキーマの同居が常態になる | 端末の旧ビルドは利用者が更新するまで動き続ける（§1）。旧構成の「デプロイした瞬間に全員が新版」という前提が失われ、§3 の段階的手順を省略できる場面が実質的に無くなった。単一利用者のため実害は小さいが、Phase2 で複数端末になると顕在化する | 🟡 中 |
| 5 | ステージング環境が無い | §3 のリハーサルはローカルのみ。ローカルの Supabase と本番の Supabase で拡張機能・バージョン差があると、本番で初めて失敗する経路が残る。Edge Function（Deno）もローカルと本番でランタイム差が出うる | 🟡 中 |
| 6 | `foods` に一意制約が無い | 全置換（`replace_foods`）で冪等性は確保しているが、これは**DB関数の実装に依存した担保**であり、制約による担保ではない。取込方式を変えた瞬間に重複が復活する。一意制約の追加は `01_DB物理設計.md` の改訂を伴うため本書では提案にとどめる | 🟡 中 |
| 7 | 初期投入がUI依存 | §2 のとおり `foods` 以外は画面からの手動登録のみで、シードSQL・再現手順を持たない。環境を作り直すたびに手作業が発生し、リハーサル環境と本番でマスタ内容がずれる | 🟡 中 |
| 8 | `users` 行の作成契機が未定義 | 初回サインアップで `users` を作るとしているが、Supabase Auth のユーザー作成（`auth.users`）と `public.users` の同期方法（トリガーか、アプリ側の遅延作成か）が未確定。`users.id`(bigint) と `auth.uid()`(uuid) の紐付け方式が決まらないと初期投入手順も確定しない | 🟡 中 |
| 9 | point of no return の判定が主観的 | §5 の (a) は「実データの記録が始まった時点」だが、初回リリース当日は検証のために自分で記録を作るため、検証データと実データの区別が曖昧になる。検証で作った記録を削除してよいかの判断基準が無い | 🟢 低 |
