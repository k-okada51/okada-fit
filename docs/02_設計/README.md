# 02_設計

> **どう作るか**（②）。設計6段（基本→インフラ→データ・IF→機能→詳細→テスト）＋見積・WBS。**上位段の合意なしに下位段へ進まない**。書く順序は段ごと（フォルダ採番順）、**承認は4つのPRに束ねる**（下記「承認ゲート」）。

## サブフォルダ
| フォルダ | 段 | 中身 |
|---|---|---|
| `10_システム基本設計/` | 段1 | 構成要素／境界／**データフロー(DFD)**／外部連携／技術選定 |
| `20_インフラ設計/` | 段2 | システム構成・環境(dev/stg/prod)・ネットワーク／IaC・デプロイ・冗長化/可用性配置。非機能要件（`../01_要件定義/04_非機能要件.md`）の直接の受け皿。**段2で承認するのは構成・環境・可用性配置の決定**（IaCコードの完成ではない。IaCは構築フェーズでも育つ） |
| `30_データ・IF設計/` | 段3 | **データモデル**（概念＋ドメイン集約＋ACL/Port）／API設計（共通規約・想定API一覧・IF契約）／ドメインイベント（用語・ID規約は `../01_要件定義/00_用語定義.md`）。複数チーム協働の**共通IF契約はここで確定（フリーズ）**し、以降は系統別に並行できる |
| `40_機能設計/` | 段4 | **シーケンス図・詳細フロー**（設計視点。要件視点のユースケースは `01_要件定義/03_ユースケース/`）。**動くモック（正本tsx）のUX承認はこの段**（作成開始は段3と並行可 — モックはIF契約に依存しない） |
| `50_詳細設計/` | 段5 | 物理ERD/DDL・バッチ・外部連携IF仕様・**移行設計**（切替/切戻し）・**ログ設計**（監査ログ/証跡）・**DB設計規約**・**実装共通設計パターン**（AIが実装できる詳細度） |
| `60_テスト設計/` | 段6 | テスト戦略（レイヤード・カバレッジ）／**RED母集合**（受入基準G/W/T・状態機械ST・エラー母集合ERR＝TDDのRED源泉）／テスト観点表 |
| `70_見積・WBS.md` | — | **確定見積もり・WBS・納期**（顧客合意対象。概算は `../01_要件定義/06_概算見積もり.md`） |

> **ADR（意思決定記録）は本層外・リポジトリ直下 `../意思決定_ADR/`**（1決定=1ファイル・Proposed→Accepted→Superseded）。

## 承認ゲート（設計は4PR）
書く順序（段1〜6）は保ちつつ、承認単位は次の4PRに束ねる。**束ねたPR内は段の順にコミットを積み**、レビューはコミット単位で読めるようにする。

| PR | 含む段 | ゲートの意味 |
|---|---|---|
| 設計PR1 基盤アーキ | 段1＋段2（基本設計・インフラ） | 技術骨格の確定（技術選定とインフラは不可分） |
| 設計PR2 データ・IF | 段3（データ・IF設計） | **IF契約フリーズ**。協働IFがある案件はここを単独PRで切り、マージ以降は系統別に並行 |
| 設計PR3 機能設計 | 段4（機能設計） | 振る舞いとUXの確定。**動くモックのUX承認をマージ条件**にする |
| 設計PR4 実装設計 | 段5＋段6＋見積・WBS | **実装着手ゲート**。マージ＝設計着手チェックリスト（`../00_プロジェクト概要/05_設計着手チェックリスト.md`）充足＝TDD開始Go。確定見積・納期の顧客合意もここ |
