# IaC・デプロイ・可用性配置 — okada-fit

> **目的**: インフラのコード化（IaC）・デプロイ方式・冗長化/可用性配置を固定し、「安全に・繰り返し・戻せる」形で環境を構築/更新できるようにする。
> **書き方**:（記入例は example-suido-fax の対応ファイル参照）実データ（実アカウント・鍵・エンドポイント）は書かず、`{ }` を自プロジェクトの語に置き換える。構成・環境は `01_システム構成・環境.md`、可用性要件（稼働率・RPO/RTO）は NFR-AVAIL（`01_要件定義/04_非機能要件.md`）、運用（監視・Runbook）は NFR-OPS を正とし矛盾させない。決定は関連DEC/ADRを併記。

> 📖 ID（`FEAT-` `NFR-` `RULE-` 等）の意味は [ID早見表](../00_ID早見表.md) を参照。

## 1. IaC（Infrastructure as Code）
> 📝 ここにIaC方針を記載。{ツール（Terraform/CDK等・`05_技術選定.md` に従う）／管理範囲（ネットワーク・コンピュート・DB・シークレット）／状態（tfstate）の保管・ロック／環境差分の扱い（変数・ワークスペース）／シークレット管理（値はIaCに直書きしない）／レビュー・適用フロー}。

| 項目 | 方針 |
|---|---|
| ツール | 個人・小規模のためフルIaC（Terraform等）は当面不採用 `[仮]`。Supabase CLI ＋ ダッシュボードで管理 |
| 管理範囲 | DBスキーマ（`supabase/migrations/`）・Edge Function（`supabase/functions/`）・シークレット（Function Secrets） |
| 状態管理 | マネージドサービス側が保持。tfstate等は持たない `[仮]` |
| 環境差分 | dev/prod で **Supabase プロジェクトを分ける**。アプリの接続先はビルド時引数で切替 `[仮]`（`01_システム構成・環境.md §2`） |
| シークレット管理 | `GEMINI_API_KEY`・service role キーは Supabase の Function Secrets。コード・リポジトリに直書きしない |
| gitが正 | マイグレーションSQLと Edge Function のコードは git 管理する。ダッシュボードで直接書き換えない（`50_詳細設計/04_移行設計.md §3.3`） |
| 対象外 | Webホスティングを持たないため、ホスティング設定のコード化は存在しない |

## 2. デプロイ
> 📝 ここにデプロイ方式を記載。{CI/CDパイプライン（トリガ・ステージ）／デプロイ戦略（ローリング/ブルーグリーン/カナリア）／マイグレーション適用の順序（可逆・`04_移行設計.md` と整合）／ロールバック手順／承認ゲート（人間承認）／リリース単位}。「失敗しても戻せる」ことが読み取れるように。

デプロイは**3系統**に分かれる。1回のリリースで3つとも動くとは限らない。

| 系統 | 手段 | 反映のされ方 |
|---|---|---|
| DBスキーマ | `supabase db push`（`supabase/migrations/` の up SQL） | 適用と同時に全アクセスへ反映 |
| Edge Function | `supabase functions deploy generate-menu` / `analyze-meal` | デプロイと同時に切替 |
| アプリ | iOS ビルドを App Store Connect へアップロード → TestFlight 配布 | **利用者が端末で更新するまで旧ビルドが動く** |

**適用順序は「DB → Edge Function → アプリ」に固定する**（理由は `50_詳細設計/04_移行設計.md §3.2`）。

| 項目 | 方針 |
|---|---|
| CI/CD | 自動デプロイは持たない `[仮]`。3系統とも手動で実行する |
| デプロイ戦略 | カナリア・段階リリースは行わない `[仮]`。利用者1名のため |
| マイグレーション適用 | up と down を対で用意し、後方互換を保つ順序で適用 `[仮]`（詳細は `50_詳細設計/04_移行設計.md §3.3・§3.4`） |
| ロールバック | **層ごとに速さが違う**（下記の非対称性）。旧構成のような即時デプロイロールバックは無い |
| 承認ゲート | 個人開発のため PRマージ＝リリース `[仮]`。画面（SCR）は `02_機能要件/02_画面` の人間承認が前提 |
| リリース単位 | 3系統をまとめて1リリースとして扱う。`50_詳細設計/04_移行設計.md §4` の時間割に従う |

### ロールバックの非対称性

**戻す速さが層ごとに大きく違う。** いちばん遅いのがアプリで、そこが本構成の急所になる。

| 層 | 戻し方 | 所要 | 即時性 |
|---|---|---|---|
| Edge Function | git の直前コミットから再デプロイ | 数分 | ○ ほぼ即時 |
| DBスキーマ | 対応する down SQL を逆順に手動適用 | 数分〜数十分 | △ 手動。順序ミスの余地あり |
| Flutter アプリ | TestFlight で前ビルドを再配布 → 端末で再インストール | 数十分〜数時間 `[仮]` | **× 即時ではない** |

アプリが即時に戻らない理由は3つ。

| # | 理由 |
|---|---|
| 1 | App Store Connect のビルド処理待ちが入る `[仮]` |
| 2 | ビルド番号は前進しかできない。実際は「前のコードを新しい番号で再アップロード」になる `[仮]` |
| 3 | 配布しても、利用者が端末で更新するまで旧ビルドが動き続ける |

- 切戻しは **「Edge Function」→「DB」→「アプリ」** の順に試す。アプリの再配布は最後の手段とする。
- 適用済みのマイグレーションは、アプリを戻しても元に戻らない。
- 旧アプリと新スキーマが同居できるかは、段階的手順（`50_詳細設計/04_移行設計.md §3.4`）を守れているかに依存する。

> ⚠️ 要確認（人間判断）: **NFR-MAINT-02「以前のデプロイに戻せる」は本構成では成立しない。**
> 同要件は Vercel の即時デプロイロールバックを前提に書かれている。
> 本構成にホスティングは無く、アプリの切戻しは TestFlight の再配布と端末での再インストールを伴う。
> **`01_要件定義/04_非機能要件.md §4.1` の改訂が必要。** 詳細と改訂案は `50_詳細設計/04_移行設計.md §5.1` を参照。

## 3. 冗長化・可用性配置
> 📝 ここに冗長化・可用性配置を記載。{マルチAZ/リージョン配置／コンピュートの冗長度（最小インスタンス数・オートスケール）／データストアの冗長化（レプリカ・フェイルオーバー）／バックアップ（頻度・保持・復元手順→RPO/RTO）／障害時の縮退・退避（安全側に倒す）}。NFR-AVAIL の目標値（稼働率・RPO・RTO）に紐づける。

| 対象 | 冗長化/配置 | 対応NFR |
|---|---|---|
| コンピュート | Edge Functions は Supabase のマネージド実行に委譲（自前の冗長化なし・ADR-0016） | NFR-AVAIL-_ ⚠️（非機能要件 未作成） |
| クライアント | アプリは端末で動くため冗長化の対象外。Supabase 障害時は操作できない（ADR-0010・ADR-0016） | NFR-AVAIL-_ ⚠️（非機能要件 未作成） |
| データストア | Supabase 無料枠のマネージド構成に依存（**DB 500 MB**・Shared CPU・RAM 500 MB）。レプリカ・フェイルオーバーは持たない | NFR-AVAIL-_ ⚠️（非機能要件 未作成） |
| バックアップ/復元 | ~~⚠️ 要確認: 無料枠のバックアップ範囲は限定的~~（**解決**・2026-08-08）。**無料枠に自動バックアップは含まれず、PITR も利用できない。** 代わりに**手元 Mac の launchd で日次自動エクスポート**を取る（ADR-0017・下記） | **NFR-AVAIL-02 を満たす**（RPO 24時間） |
| プロジェクトの停止 | **1週間の無操作で一時停止**（無料枠・確定）。**許容する**（ADR-0020）。データは失われず手動で復帰できる | NFR-AVAIL-01（停止週は稼働率0%・下記） |
| 障害時の縮退・退避 | Gemini API 不達時は AI機能だけを止める（安全側・ADR-0016）。範囲は下表 | NFR-AVAIL-_ ⚠️ |
| AI経路の代替 | 自動フォールバック先を持たない。`GEMINI_MODEL` の手動変更のみ（ADR-0011・ADR-0016／`10_システム基本設計/04_外部連携.md §4`） | NFR-AVAIL-_ ⚠️ |

### 縮退の範囲

| 対象 | 縮退時 |
|---|---|
| 食事の解析・記録 | **できない**（手入力の経路を持たない・ADR-0015） |
| メニュー提案 | できない |
| トレーニング記録 | できる |
| 閲覧 | できる |

- 食事だけは「記録も止まる」。NFR-AVAIL-05（AI障害時の縮退）の文言と実態が合わない（ADR-0015 で要件側へ申し送り）。

### 無料枠の確定値と可用性への影響

数値の正本は `01_システム構成・環境.md §2`（公式の料金ページ・2026-08-08 確認）。可用性に効くのは3つ。

| 事実 | 可用性への影響 |
|---|---|
| 自動バックアップが**含まれない** | 何もしなければ復元元が1つも無い |
| PITR が**利用できない** | 障害直前の時点へは戻せない。戻せるのはエクスポートを取った時点だけ |
| **1週間の無操作で一時停止** | 停止した週は稼働率0%。復旧は障害ではなく手動の再開操作 |

> ~~決めるのは2択。手動エクスポートの運用を定めるか、有料プランに上げるか。~~
> **手元 Mac の launchd で日次自動エクスポートを取る**（ADR-0017）。**RPO 24時間となり NFR-AVAIL-02 を満たす。**

**バックアップ運用（確定・ADR-0017）**

| 項目 | 値 |
|---|---|
| 手段 | `supabase db dump`（Supabase CLI・**Docker Desktop が前提**） |
| 頻度 | 日次（1日1回） |
| 実行元 | 岡田さんの Mac。launchd の定時ジョブ。**人手を介さない** |
| 保管先 | ローカル。クラウド同期は下記 ⚠️ |
| RPO | **24時間**（NFR-AVAIL-02 を満たす） |
| RTO | 数時間（NFR-AVAIL-03・変更なし） |

- **本番システムのバッチではない。** 岡田さんの Mac で動く運用手順であり、`50_詳細設計/02_バッチ設計.md` の「定期実行バッチ0本」は変わらない。
- 有料プランには上げない。案D（Pro）は却下した（ADR-0017）。

> ⚠️ 要確認（人間判断）: **Mac が落ちている期間はエクスポートされない**（🟡 中・ADR-0017）。
> launchd は Mac の電源が入っている時しか走らない。長期不在では RPO 24時間が崩れる。
> **実行ログを残し、最終取得日時を確認できるようにする。** 確認の頻度・方法は運用開始後に定める。

> ⚠️ 要確認（人間判断）: **保管先が手元の1箇所である**（🟡 中・ADR-0017）。
> Mac の故障・紛失でバックアップも同時に失われる。クラウド同期フォルダへ置くかを決める必要がある。
> ただし**エクスポートには食事・トレーニングの記録が入る**。同期先の扱いは NFR-SEC-06（必要以上に保存しない）と併せて判断する。

> ~~⚠️ 要確認（人間判断）: **1週間の無操作でプロジェクトが停止する**（無料枠・確定・2026-08-08）。~~（**解決**・2026-08-08・ADR-0020）
> **許容する。** データは失われず、ダッシュボードから復帰できる（猶予1年）。停止検知も keep-alive も実装しない。
> **停止した週の稼働率は0%になる**が、原因は障害ではなく無料枠の仕様であり、復旧は手動操作1回である。
> NFR-AVAIL-01 に除外条件を書くかは要件ブランチへの申し送り（🟢 低）。正本は `01_システム構成・環境.md §2`。

> ⚠️ 要確認（人間判断）: 可用性目標（稼働率・RPO・RTO）は非機能要件（`../01_要件定義/04_非機能要件.md` NFR-AVAIL）が未作成のため未確定。個人アプリの許容度に応じて非機能要件で定義する。
