# テスト戦略 — okada-fit

> **目的**: レイヤードテスト（単体／結合／受入）の役割分担・カバレッジ目標・受入基準やNFR（品質）との接続を定義し、「何を・どの層で・どこまで検証するか」を固定する。**受入基準がTDDのRED**であり、その源泉は `02_RED母集合_受入基準・状態・エラー.md`。
> **書き方**:（記入例は example-suido-fax の対応ファイル参照）実データは書かず、`{ }` を自プロジェクトの語に置き換える。受入基準・ST・ERRの母集合は `02_RED母集合_受入基準・状態・エラー.md`、品質NFR（カバレッジ・脆弱性等）は `01_要件定義/04_非機能要件.md` を正とし矛盾させない。

> ⚠️ **本書はたたき台（2026-08-08 生成）**。岡田さんのレビューで確定する。前提: Flutter（Dart）＋ Supabase（Auth / PostgreSQL + RLS / Edge Functions）。**Vercel・Next.js は使わない**。AI（EXT-01）は Edge Function から Google Gemini API を直接呼ぶ。

## 1. テスト方針
> 📝 ここに全体のテスト方針を記載。{TDD（受入基準＝REDを先に書く）／分岐網羅（ERR母集合を1対1でカバー）／テストピラミッドの考え方／自動化の範囲／CIでの実行タイミング}。

| # | 方針 | 内容 |
|---|---|---|
| 1 | 起点 | 受入基準（AC）が TDD の RED。源泉は `02_RED母集合_受入基準・状態・エラー.md` §2 |
| 2 | 完了条件 | **RED母集合を全て緑にすること。** カバレッジの数値目標は置かない（§3） |
| 3 | 最も厚くする層 | **Dart 純関数の単体テスト**（NFR-QUAL-01）。§2 の L1 |
| 4 | 分岐網羅 | ERR母集合の各 ERR-ID に1対1でテストを対応させる |
| 5 | RLS | **必ずテストする。** RLS が唯一の防御線であるため（§2） |
| 6 | AI（EXT-01） | 実 API はモックする。既定では叩かない（§2） |
| 7 | AI の出力内容 | **正しさをテストしない。** 検証は構造までに限る（下表） |
| 8 | 自動化 | CI は持たない `[仮]`。手元実行が前提（§2） |
| 9 | 実行タイミング | 実装者が手元で実行する。マージを機械的に止めるゲートは無い `[仮]` |

テストピラミッドの形。

| 位置 | 層 | 厚み |
|---|---|---|
| 底 | Dart 純関数（L1） | **最も厚い** |
| 中 | RPC・DB（L2）／Edge Function（L3） | 中 |
| 頂 | 結合・実機（L4） | 薄い |

**AI の出力そのものの正しさはテストしない。**

| 検証する | 検証しない |
|---|---|
| 構造化出力が zod スキーマを満たすこと（ERR-AI-SCHEMA） | 提案されたメニューが良いかどうか |
| `menu_id` が入力候補集合に含まれること（ERR-MENU-007） | 推定された栄養値が実物と合っているか |
| `order` が `1..N` の連番であること（ERR-MENU-007） | 料理名の認識精度 |
| 栄養4項目が妥当域内であること（ERR-MEAL-005） | 提案理由（`reason`）の文章の質 |

- 栄養推定の精度（MAPE）は**実測で評価する話**である。自動テストの対象にしない。
- 精度は入力画像とモデル更新で動く。テストにすると常に落ちるか、常に通るかのどちらかになる。
- 医療的正確性は適用外（NFR-OOS-01）。

## 2. レイヤードテスト（単体/結合/受入）
> 📝 ここに各テスト層の役割・対象・手段を記載。{層／目的／対象範囲／モック/実物の別／主なテスト対象（ロジック・IF契約・状態遷移・E2Eシナリオ）}。層の責務が重複しないように。

| 層 | 目的 | 対象範囲 | モック/実物 | 主な対象 |
|---|---|---|---|---|
| 単体（Unit） | ロジックを入出力だけで固定する | Dart 純関数（`app/lib/domain/**`）・Edge Function の純関数 | 実物のみ。DB もネットワークも使わない | ロジック・BR |
| 結合（Integration） | 契約・RLS・状態遷移を実物のDBで確かめる | RPC・PostgREST・RLS・Edge Function | Supabase はローカル実物。Gemini API は**モック** | IF契約・DB・状態遷移 |
| 受入（Acceptance/E2E） | AC を実機で満たすか確かめる | Flutter アプリ（iOS 実機） | 実物。EXT-01 は手動で最小回数だけ叩く `[仮]` | 受入基準（G/W/T）・ユースケース |

本PJでは上の3層を**4つの実行単位**に分ける。呼び出し方式が3通りあり、実行手段が層ごとに違うためである。

| # | 実行単位 | 上の層 | 実行手段 | 対象 | 外部依存 |
|---|---|---|---|---|---|
| L1 | Dart 純関数の単体 | 単体 | `flutter test`（`package:test`） | `app/lib/domain/**` | 無し |
| L2 | RPC・DB（SQL） | 結合 | ローカル Supabase への SQL 実行 `[仮]` | RPC・RLS・制約・INDEX | ローカル Postgres |
| L3 | Edge Function | 結合 | `supabase functions serve` ＋ HTTP `[仮]` | `generate-menu`・`analyze-meal` | Gemini API は**モック** |
| L4 | 結合（実機） | 受入 | iOS 実機（TestFlight 配布物） | 画面・カメラ・ファイル選択 | 実 Supabase・実 EXT-01 |

- L2 の対象 RPC は4本。`create_training_session` / `get_dashboard` / `get_protein_remaining` / `import_foods`。
- 器具の RPC 3本は採否が未決 `[仮]`。`create_machine` / `update_machine` / `delete_machine`（FEAT-01 §10 #12）。

### 数値の丸めを確かめる（ADR-0022）

栄養値・体重は **`numeric(6,1)`** に変えた（2026-08-08・ADR-0022）。`float` の丸め誤差を消すためである。
**型を変えただけでは足りない。** 次の3点を実際に確かめる。

| # | 層 | 確かめること |
|---|---|---|
| 1 | L2 | `0.1 + 0.2` を含む `SUM(protein_g)` が **`0.3`** になること |
| 2 | L1 | 残量がちょうど 0 のとき、「あと0g」ではなく**達成として扱われる**こと（FEAT-09・RULE-002） |
| 3 | L2 | 小数第2位を含む値を保存すると**第1位に丸められる**こと |

- 2 が本丸である。**誤差は表示ではなく分岐に効く。** 表示だけ丸めても判定は直らない。
- 3 は AI（EXT-01）が任意の小数を返すため要る。丸めは Edge Function 側でも行う（FEAT-08 §4）。

> ⚠️ 要確認（人間判断）: **`supabase_flutter` が `numeric` をどう返すか未確認**（🟡 中・ADR-0022）。
> ドライバによっては**文字列で返る**。Dart 側で `double.parse` が要るかもしれない。
> **実装初日（W-03 の前）に実挙動を1回確認すること。** 変換は1箇所に集約する。

### L1（最も厚くする層）の主な対象

業務ロジックは全て純関数に寄せてある。したがって L1 が本PJの主戦場になる。

| 対象 | 所在 | 由来 |
|---|---|---|
| `calcTargetProteinG` / `roundProteinG` | `app/lib/domain/nutrition.dart` | FEAT-07（RULE-001） |
| `calcRemainingG` / `pickSuggestions` | `app/lib/domain/protein_remaining.dart` | FEAT-09（RULE-002・RULE-005） |
| CSV パース・文字コード判定・行検証 | FEAT-10 §4 の純関数 | FEAT-10 |
| 名称の正規化（`normalizeName`） | `app/lib/domain/machines.dart` | FEAT-01・FEAT-10 |
| 検証関数（`validateWeightKg` ほか） | `app/lib/domain/profile.dart` | FEAT-06 |
| 畳み込み・整列（`groupMachines` / `sortMachines`） | `app/lib/domain/machine_mapping.dart` | FEAT-02 |
| 達成率（`calcGaugeRatePct`）・期間解決（`resolveDateRange`） | `app/lib/domain/gauge.dart` ほか | FEAT-05 |
| 日付（`todayOnDevice` / `isFutureDate`） | `app/lib/domain/date.dart` ほか | FEAT-04・08・09 |
| AI 出力の照合（`verifySelection`） | `supabase/functions/generate-menu/validate.ts` | FEAT-03 |

- 純関数は DB もモックも要らない。速く、壊れにくく、原因の切り分けが要らない。
- 詳細設計が「式を1箇所にしか置かない」と決めている（FEAT-07 §4.5）。その担保も L1 で行う。

### RLS のテスト（必須）

| 事項 | 内容 |
|---|---|
| なぜ必須か | **RLS が唯一の防御線**。anon キーはアプリに埋め込まれ公開される |
| 中間層 | 無い。PostgREST・RPC の経路に Edge Function が挟まらない |
| 何を試すか | 他人の JWT で本人の行を SELECT / UPDATE / DELETE **できない**こと |
| 対象（本人のみ） | `users`・`training_menus`・`gym_visits`・`training_sessions`・`meal_logs` |
| 対象（親経由） | `machine_menus`・`training_session_details` |
| 対象（共通マスタ） | `gyms`・`training_machines`・`foods`。**遮断されない**ことを確認する |
| 由来 TC | TC-FEAT01-15・TC-FEAT02-08・TC-FEAT06-14・TC-FEAT08-13・TC-FEAT09-16 |
| 層 | L2。アプリを通さず DB に直接当てる |

- 「アプリ側で `.eq('user_id', ...)` している」ことはテストの根拠にならない。絞り込みであって防御ではない。
- 共通マスタは認証済みなら誰でも書き換えられる。単一利用者では実害が無い（Phase2 で見直す）。

### Edge Function のテスト

| 事項 | 内容 |
|---|---|
| Gemini API | **モックする。** 既定では実 API を叩かない |
| 理由 | EXT-01 は従量課金。テストのたびに課金が発生する |
| 実 API を叩くテスト | 明示フラグでのみ実行する `[仮]`。既定の実行から外す |
| モックで作る応答 | 正常／JSON 不正／スキーマ不適合／429 2種／400 `failed_precondition`／504／5xx |
| 検証すること | ERR-ID の写像と `retryable` が各 FEAT §6 の表どおりであること |
| 検証すること | 未認証・入力不正のとき **EXT-01 を呼ばない**こと（課金を発生させない） |
| 検証しないこと | AI の出力内容の妥当性（§1） |

- 「EXT-01 を呼ばない」ことの確認が本PJでは重要である。呼べば課金するため。
- 該当 TC は TC-FEAT03-02/03/04/05/17/18・TC-FEAT08-05。

## 3. カバレッジ目標
> 📝 ここにカバレッジ目標を数値で記載。{指標（行/分岐）／目標値（数値＋単位）／対象範囲／未達時の扱い}。品質NFR（`01_要件定義/04_非機能要件.md`）の値と一致させる。

| 指標 | 目標値 | 対象範囲 | 対応NFR |
|---|---|---|---|
| 行カバレッジ | **数値目標を置かない** `[仮]` | `app/lib/domain/**`（L1） | NFR-QUAL-01 ⚠️ |
| 分岐カバレッジ | **数値目標を置かない** `[仮]` | 同上 | NFR-QUAL-01 ⚠️ |
| ERR母集合の網羅 | 100%（各ERRに1対1のテスト） | 全ERR | NFR-QUAL-01 |

数値の代わりに置く完了条件。**RED母集合を全て緑にすること**である。

| # | 完了条件 | 母集合の所在 |
|---|---|---|
| 1 | 受入基準（AC）が全て緑（**65件**。廃止1件を除く） | `02_RED母集合_受入基準・状態・エラー.md` §2 |
| 2 | 状態遷移（T01・T02）のテストが緑 | 同 §3 |
| 3 | ERR-ID に1対1のテストがある（**67件**。欠番6件を除く） | 同 §4 |

数値目標を置かない理由。

| 理由 | 内容 |
|---|---|
| 正本が無い | `../../01_要件定義/04_非機能要件.md` はテンプレートのまま。NFR-QUAL-01 の数値が存在しない |
| 数値が目的化する | 行カバレッジだけを上げるテストは AC を1つも守らない |
| 母集合で数えられる | AC・ST・ERR は ID で数えられる。未達は「どの ID が赤か」で示せる |

- 未達時の扱い: 赤い ID を残したまま実装完了としない。落とすなら AC・ERR 側を改訂して理由を残す。

> ⚠️ 要確認（人間判断）: NFR-QUAL-01 の本文が本ブランチに無い。カバレッジの数値要求があれば本節に反映してください。
