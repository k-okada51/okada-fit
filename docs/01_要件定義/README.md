# 01_要件定義

> **何を作るか**（①）。要件定義の型「森→機能→非機能→木」の4層に対応（層の順序どおりに書く）。**受入基準がそのままTDDのRED（テスト）**になる（正本は `02_設計/60_テスト設計/`）。

## サブフォルダ
| フォルダ/ファイル | 層 | 中身 |
|---|---|---|
| `00_用語定義.md` | — | 用語・ID付番規則の正本（全層参照）。命名規約=物理命名は `../02_設計/50_詳細設計/06_DB設計規約.md` |
| `01_全体像/` | 層1 森 | 目的・対象ユーザ・システム概要（`01`）／課題・解決・業務フロー As-Is→To-Be（`02`）／**制約・前提**（`03`）／**リスク分析**（`04`）／**未決定事項**（`05`） |
| `02_機能要件/` | 層2 機能要件 | 機能要件インデックス（俯瞰1枚：FEATサマリ・外部連携一覧・業務ルール一覧）（`00`）／機能概要（`01_機能一覧/`）／画面概要＋画面モック規約＋**簡単なモック（ラフ）**（`02_画面/`）／帳票概要（`03_帳票一覧/`） |
| `03_ユースケース/` | 層2 機能要件 | 要件視点のユースケース（ユーザージャーニー・業務シナリオ・主/代替フロー・関連FEAT） |
| `04_非機能要件.md` | 層3 非機能 | 性能／可用性／セキュリティ（権限・監査ログ含む）／運用・保守・拡張／**移行性**（移行対象・方式・切戻し）を1枚に。**大タスク分解の入力になるため木より先** |
| `05_タスク一覧/` | 層4 木 | 大タスク（機能→作業ブロック・10〜30）／想定タスク。機能要件と非機能要件の**両方**を入力に分解する |
| `06_概算見積もり.md` | — | 概算見積もり（梅/竹/松のレンジ・前提・変動要因）。**要件定義ゲートの顧客合意対象** |

## モックの2段階
| 段階 | モック | 目的 | 承認 |
|---|---|---|---|
| 要件定義・層2 | **簡単なモック**（静的ラフ・主要画面のみ、`02_画面/`） | 「作るもの」のイメージ齟齬を顧客合意の前に潰す | 要件PR2に同梱＋人間承認 |
| 設計・段4 | **動くモック**（正本tsx、規約は `02_機能要件/02_画面/00_画面モック規約.md`） | 操作感・遷移・トーンのUX承認 | 設計PR3のマージ条件（`../02_設計/README.md`） |

## 承認ゲート（要件定義は3PR）
書く順序（層1〜4）は保ちつつ、承認単位は次の3PRに束ねる。**束ねたPR内は層の順にコミットを積む**。

| PR | 含むもの | ゲートの意味 |
|---|---|---|
| 要件PR1 全体像 | `00_プロジェクト概要/` ＋ 層1（`00_用語定義`・`01_全体像/`） | 方向性の合意（ここが揺れると全部やり直しになるため単独PR） |
| 要件PR2 機能要件 | 層2（`02_機能要件/`・`03_ユースケース/`・簡単なモック） | 「何を作るか」の確定。モックの人間承認込み |
| 要件PR3 非機能＋大タスク＋概算 | 層3＋層4＋`06_概算見積もり` | **要件定義完了ゲート＝顧客合意**（要件定義書＋概算見積もりの受領確認） |
