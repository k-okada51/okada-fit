# 非機能要件（NFR）

> **目的**: 性能・可用性・セキュリティ・運用・移行性の非機能要件を、一意なIDと**測定可能な目標値**で定義する。
> **書き方**: 目標値は必ず数値＋単位で（「速い」ではなく「≤ 5秒」）。安全側に倒す原則が読み取れるように。閾値・SLOが未確定なら設計層/ADRへ委譲と明記。記入例は example-suido-fax/01_要件定義/04_非機能要件.md 参照。

> 前提: 本システムは**岡田さん個人利用のWebアプリ**（マネージドPaaS・無料枠中心）。多人数・高負荷・厳格SLAは想定しないため、目標値は個人利用相当（緩め）で置き、多くは `[仮]`（実運用で調整）。

## 1. 性能（NFR-PERF）
> 📝 ここに性能要件を記載。含める項目: ID（NFR-PERF-XX）／シナリオ（対象の操作・処理）／目標値（数値＋単位で測定可能に）。応答時間・スループット・処理時間・データ量などを網羅する。未確定の閾値は設計層/ADRへ委譲と明記。

| ID | シナリオ | 目標値 |
|---|---|---|
| NFR-PERF-01 | 画面表示（ダッシュボード等の初期表示） | ≤ 2秒 `[仮]` |
| NFR-PERF-02 | 器具絞り込み・記録保存など決定的処理（AI不使用） | ≤ 1秒 `[仮]` |
| NFR-PERF-03 | AIメニュー提案（generate押下→結果表示、FEAT-03/EXT-01） | ≤ 15秒 `[仮]`（Claude生成に依存。待機はローディング表示） |
| NFR-PERF-04 | 食事写真のタンパク質計算（FEAT-08/EXT-01・画像入力） | ≤ 20秒 `[仮]`（画像送信＋推定に依存） |
| NFR-PERF-05 | 食事マスタCSVインポート | 数百件を ≤ 5秒 `[仮]` |

> ⚠️ 要確認（人間判断）: AI応答（NFR-PERF-03/04）はClaude側の律速で変動。厳密な上限・タイムアウト・ストリーミング表示の要否は `02_設計/40_機能設計/`・`02_設計/10_システム基本設計/04_外部連携.md` で確定する。

## 2. 可用性・信頼性（NFR-AVAIL）
> 📝 ここに可用性・信頼性要件を記載。含める項目: ID（NFR-AVAIL-XX）／要件（稼働率・RPO・RTO・バックアップ・障害時の退避や滞留の方針など）。安全側に倒す原則が読み取れるように。稼働率・RPO・RTOは数値で。閾値・SLOが未確定なら設計層/ADRへ委譲。

| ID | 要件 |
|---|---|
| NFR-AVAIL-01 | 稼働率: 個人利用のため厳格SLAは設けず、マネージド（Vercel/Supabase）の可用性に準拠。目安 99% 程度（ベストエフォート）`[仮]` |
| NFR-AVAIL-02 | RPO（データ損失許容）: ≤ 24時間 `[仮]`（1日1回の想定でデータを保全） |
| NFR-AVAIL-03 | RTO（復旧時間）: ≤ 数時間 `[仮]`（個人利用のため許容度は高い） |
| NFR-AVAIL-04 | バックアップ: 無料枠のバックアップ範囲は限定的。定期エクスポート等で補完する ⚠️ 要確認（無料枠の仕様に依存） |
| NFR-AVAIL-05 | 障害時の縮退（安全側）: Claude不達時はAI機能（提案・写真計算）を一時不可とし、記録・閲覧は継続する |

> ⚠️ 要確認（人間判断）: 稼働率・RPO・RTOの確定値と無料枠バックアップの実仕様は `02_設計/20_インフラ設計/02_IaC・デプロイ・可用性配置.md` で確定する。

## 3. セキュリティ・権限（NFR-SEC）
> **書き方**: まず攻撃面を洗い出し、各対策を実施/理由つきで。権限は主体×権限×制約の表で最小権限を示す。未確定はADRへ委譲。

### 3.1 攻撃面
> 📝 ここに攻撃面（守るべき境界・入口）を記載。含める項目: 外部公開エンドポイント／ブラウザ保持の鍵／サーバ間連携など、攻撃者が触れうる面を箇条書きで。公開しない受け口があればそれも明記。

- **公開エンドポイント**: Webアプリ（Vercel/HTTPS）のみ。DB・Claudeへの経路は直接公開しない。
- **ブラウザ側の鍵**: Claude APIキー・DB資格情報は**ブラウザに置かない**（サーバ側のみ）。
- **外部送信**: 食事写真を外部（Claude）へ送信する（プライバシー上の攻撃面／情報流出面）。
- **入力**: 器具名・CSV・食事写真・体重などのユーザ入力（検証が必要）。

### 3.2 セキュリティ要件一覧（NFR-SEC）
> 📝 ここにセキュリティ要件を記載。含める項目: ID（NFR-SEC-XX）／項目（Web一般対策・レート制限・認証authN・認可authZ・暗号化・MFA・監査など）／実施内容と理由。

| ID | 項目 | 実施/理由 |
|---|---|---|
| NFR-SEC-01 | 認証（authN） | 本人限定ログインで、岡田さん以外のアクセスを遮断 `[仮]`（DEC-D03。公開ホスティングのため必須） |
| NFR-SEC-02 | シークレット秘匿 | Claude APIキー・DB資格情報はサーバ側環境変数のみ。クライアント・リポジトリに出さない |
| NFR-SEC-03 | 通信暗号化 | ブラウザ↔アプリ↔DB↔Claude を全経路 HTTPS/TLS |
| NFR-SEC-04 | Web一般対策 | XSS/CSRF等の基本対策（フレームワーク標準＋入力検証）`[仮]` |
| NFR-SEC-05 | レート制限 | AI呼び出し（generate・写真計算）の乱発を抑止（コスト・悪用防止）`[仮]` |
| NFR-SEC-06 | 食事写真の外部送信・保持 | 送信先（Claude）の保持ポリシーを確認し、必要以上に保存しない ⚠️ 要確認（DEC-D04） |

### 3.3 権限・スコープ
> 📝 ここに権限を記載。含める項目: 主体（利用者・運用担当・内部サービスなど）／権限（できること）／制約（できないこと・最小権限）。誰が何をできて何をできないかが一目で分かるように。

| 主体 | 権限 | 制約 |
|---|---|---|
| 岡田さん（唯一の利用者） | 自分の器具・記録・体重・食事データの参照/登録/更新、AI機能の利用 | 他ユーザは存在しない（単一ユーザ）。シークレットには触れない |
| 岡田さん（運用担当） | 環境変数（Claude/DB鍵）の管理・デプロイ | 鍵はコードに残さない |
| サーバ（アプリ） | DB接続・Claude呼び出し | クライアントへ鍵を渡さない |

> 関連する権限境界のテスト（TC-SEC-*）や鍵ローテ・失効の方針は設計層/ADRへ委譲する場合は、そのIDを明記する。※本PJは単一ユーザのため認可（authZ）は単純。詳細は `02_設計/50_詳細設計/` へ委譲。

### 3.4 監査ログ・証跡（NFR-SEC-AUDIT）
> 📝 ここに監査ログ（**誰が・いつ・何を・結果どうなったか**）の要件を記載。業務ログとは別に、可監査性・不正検知・インシデント調査のための証跡を定義する。含める項目: ID（NFR-SEC-AUDIT-XX）／記録対象イベント（認証・権限変更・重要操作・データ更新・外部送信/確定など）／記録項目（主体・時刻・対象・結果・相関ID）／保持期間／改ざん防止・アクセス制限。**設計は `02_設計/50_詳細設計/05_ログ設計.md` を正**とし、保持・監視の運用面は §4（NFR-OPS）へ。

| ID | 記録対象イベント | 記録項目 | 保持/保護 |
|---|---|---|---|
| NFR-SEC-AUDIT-01 | 外部送信（Claude呼び出し：メニュー提案・食事写真計算） | 時刻・用途・成否 | 個人利用のため最小限 `[仮]`（詳細は `02_設計/50_詳細設計/05_ログ設計.md`） |
| NFR-SEC-AUDIT-02 | 認証（ログイン成否） | 時刻・成否 | `[仮]` |

> ⚠️ 要確認（人間判断）: 個人利用のため厳格な監査は必須ではない。最低限、外部送信・エラーの記録に留め、詳細はログ設計で確定する。

## 4. 運用・保守性・拡張性（NFR-OPS / NFR-MAINT / NFR-SCALE）
> **書き方**: 「何を可視化/管理/自動化するか」を運用者視点で。拡張は「改修なしで増やせるか」を軸に。品質はカバレッジ等を数値で。

### 4.1 運用・保守性（NFR-OPS / NFR-MAINT）
> 📝 ここに運用・保守要件を記載。含める項目: ID（NFR-OPS-XX / NFR-MAINT-XX）／要件（監視・可視化・アラート・構造化ログ・鍵ローテ・IaC・Runbook・可逆マイグレーションなど）。

| ID | 要件 |
|---|---|
| NFR-OPS-01 | エラー監視・ログ: Vercel/Supabase のログを活用し、エラー・AI連携失敗を確認できる `[仮]` |
| NFR-OPS-02 | シークレット管理: 環境変数で管理し、漏洩時はローテできる |
| NFR-OPS-03 | バックアップ運用: 定期エクスポートでデータを保全（NFR-AVAIL-02/04と整合）⚠️ |
| NFR-MAINT-01 | 保守負担の最小化: 単一言語（TypeScript）・単一Webアプリ・マネージドPaaSで、個人（実装者＝岡田さん）でも保守できる |
| NFR-MAINT-02 | デプロイ可逆性: Vercelの以前のデプロイに戻せる。DB変更は可逆マイグレーション（`02_設計/50_詳細設計/04_移行設計.md`）|

> 監査ログ（誰が・いつ・何を）の**要件**は §3.4（NFR-SEC-AUDIT）を正とし、本節は**その保持・監視・ローテーション（運用面）**を担う。ログ設計は `02_設計/50_詳細設計/05_ログ設計.md`。

### 4.2 拡張性・マルチテナント（NFR-SCALE）
> 📝 ここに拡張性要件を記載。含める項目: ID（NFR-SCALE-XX）／要件（テナント追加・データ量増加・書式/項目追加をコード改修なしで扱えるか、ピーク平準化など）。

| ID | 要件 |
|---|---|
| NFR-SCALE-01 | マルチテナント（多人数）は**適用外**（個人利用で確定）。将来のプロダクト化はPhase2 |
| NFR-SCALE-02 | データで増やせる: 器具・食事マスタ（CSV）はデータ追加で拡張でき、コード改修を要しない |

### 4.3 その他NFR（データ/コンプラ/品質/適用外）
> 📝 ここにその他のNFRを記載。含める項目: ID／種別（データ・コンプラ・品質・適用外）／要件（保持期間・法令準拠・テストカバレッジ・脆弱性ゼロなど）／状態。**明示的に「適用外」とするもの**も列挙し、スコープ外を宣言する。

| ID | 種別 | 要件 | 状態 |
|---|---|---|---|
| NFR-DATA-01 | データ | 扱うのは岡田さん本人のデータのみ。食事写真の保持は最小限とする | ⚠️ 要確認（DEC-D04） |
| NFR-QUAL-01 | 品質 | 主要ロジック（器具絞り込み・必要量算出・残量算出）に単体テストを用意。受入基準（G/W/T）は `02_設計/60_テスト設計/` を正 | `[仮]` |
| NFR-OOS-01 | 適用外 | 多言語対応・多人数/SLA厳格・法令コンプラ（医療/栄養指導としての正確性保証等）は適用外（個人アプリ） | 確定 |

### 補足（適用外の明示）
- 目標体型に基づく食事メニュー生成、3日ルール/ローテーション提案は機能スコープ外（`01_全体像/03_制約・前提.md` §2）であり、本非機能要件でも対象外。

## 5. 移行性（NFR-MIGR）
> 📝 ここに移行性要件を記載。含める項目: ID（NFR-MIGR-XX）／要件（移行対象データ・移行方式（一括ビッグバン／並行稼働／段階）・許容停止時間・切戻し条件・移行元の廃止時期・移行対象外の宣言など）。**「失敗しても安全に戻せる」**ことが読み取れるように。具体的な移行手順・データマッピングは設計層（`02_設計/50_詳細設計/04_移行設計.md`）へ委譲。未確定はADRへ。

| ID | 要件 |
|---|---|
| NFR-MIGR-01 | 既存システムからのデータ移行は**適用外**（新規開発）。移行元システムなし |
| NFR-MIGR-02 | 初期データ投入: 食事マスタはCSVインポート（FEAT-10）で投入。器具は手動登録（FEAT-01）。失敗時は再取込で戻せる |
| NFR-MIGR-03 | スキーマ変更時は可逆マイグレーションとし、失敗時に切戻せる（詳細は `02_設計/50_詳細設計/04_移行設計.md`）|
