# 概算見積もり

> **目的**: 要件定義完了時点の概算見積もり（レンジ）を顧客に提示し、設計フェーズへ進む合意を得る（＝要件定義ゲートの顧客合意対象）。確定見積もりは設計完了時の `../02_設計/70_見積・WBS.md` が正。
> **書き方**: 単一の数字ではなく**必ずレンジ（梅/竹/松）**で示し、精度と変動要因を明記する。入力は `05_タスク一覧/`（大タスク・想定タスク）。金額・工数の根拠が大タスクにトレースできること。

> 前提: 本PJは**岡田さん個人が自作**（発注者＝実装者）。そのため「金額」は開発人件費ではなく**工数（人日）＋ 運用コスト（AI従量費・ホスティング）**で示す。人日単価・予算は未提供のため金額換算は保留（⚠️ TODO-C01）。

| 案 | 工数 | 金額 | 想定納期 | 備考 |
|---|---|---|---|---|

### 運用コスト（ランニング）概算 `[仮]`
- **Claude API（従量）**: `claude-opus-4-8` 既定 `[仮]`。目安単価＝入力 $5／出力 $25（1Mトークンあたり・要検証）。1回のメニュー提案≈数千トークン、食事写真1枚≈画像で多め。
  - 例（利用想定 `[仮]`）: 月30回のメニュー提案＋月60回の食事撮影 → **ざっくり 数百円〜数千円/月**（利用量とモデルtierで変動。**Haiku採用なら大幅減**＝DEC-D02）
- **ホスティング/DB**: Vercel・Supabase とも **無料枠内なら ¥0** `[仮]`（利用量が枠を超えたら課金）
- ⚠️ 要確認: 実際のAI従量費は「月の利用回数×トークン量×モデル単価」で決まる（`01_全体像/05_未決定事項.md` TODO-C02）。

## 3. 前提条件・精度
> 📝 ここに見積もりの前提と精度を記載。含める項目: 精度レンジ（例: −25%〜+50%）／前提とした体制・期間／顧客側の役割分担（データ提供・環境準備・レビュー応答期限など）／技術前提（利用サービス・既存資産の再利用）。前提が崩れた場合は再見積もりとなることを明記。

- 精度レンジ: **−25%〜+50%**（要件定義時点の概算。設計完了時に確定見積へ）
- 体制・期間の前提: **岡田さん1名（個人開発）**。想定納期は「概ねフルタイム相当」で算出 `[仮]`。パートタイム（週2〜3人日相当）なら期間は約2倍に延びる
- 顧客側の前提（提供物・応答期限）: 発注者＝実装者（岡田さん本人）。食事マスタCSV・器具情報の用意、未決DEC（D01〜D04・B03/B05）の確定
- 技術前提: Next.js／Supabase(無料枠)／Vercel(無料枠)／Claude（`claude-opus-4-8` `[仮]`）。いずれも `[仮]`（DEC-D01・B03・D02）。既存資産の再利用なし（新規）
- 前提が崩れた場合（スタック変更・多人数化・スコープ追加）は再見積もり

## 4. 変動要因
> 📝 ここに金額・納期が変動しうる要因を記載。`01_全体像/04_リスク分析.md`（リスク）と `01_全体像/05_未決定事項.md`（未決）のうち、見積もりに影響するものをIDで参照し、影響方向（増/減）と影響幅を書く。

| 要因（リスク/未決のID） | 影響 | 影響幅の目安 |
|---|---|---|
| DEC-D02 モデルtier（opus/sonnet/haiku） | 運用コスト 増減 | Haiku採用で従量費を大幅減／Opusで増 |
| DEC-D03 認証方式（未確定） | 開発工数 増 | TASK-002 が +2人日程度 |
| DEC-D04 食事写真の保持ポリシー（未確定） | 開発工数 増 | TASK-016 が +1人日程度 |
| AIメニュー提案/写真計算の精度不足（04_リスク分析） | 開発工数 増 | 手動補正・プロンプト作り込みで TASK-007/012 が松側へ |
| TODO-C02 AI従量費 | 運用コスト 変動 | 利用量とモデル単価で月額が上下 |
| 無料枠の制約（Supabaseバックアップ等・NFR-AVAIL-04） | 運用/工数 増 | 枠超過時は課金、または代替実装 |

## 5. スコープ外（本見積もりに含まないもの）
> 📝 ここに「やらないこと」を明文化する。含める項目: 対象外の機能・データ移行・運用保守・多言語対応など、顧客が含まれていると誤解しやすいもの。契約上のスコープ境界は `../00_プロジェクト概要/03_契約・スコープ.md` を正とし、ここは見積もり観点の除外リスト。

- 多人数／他ユーザ展開・マルチテナント（Phase2）
- 目標体型に基づく食事メニュー生成、3日ルール／ローテーション提案（機能スコープ外）
- 多言語対応、厳格SLA運用、法令コンプラ（栄養指導としての正確性保証など）
- 既存システムからのデータ移行（新規のため対象なし）
- 開発の人件費（自作のため計上外）／継続的な運用保守の人件費

## 6. 有効期限・条件
> 📝 ここに見積もりの有効期限と、確定見積もりへの移行条件を記載。例: 本見積もりの有効期限（提示から{N}日）／確定見積もりは設計完了時（`../02_設計/70_見積・WBS.md`）に提示／要件定義書のスコープ変更時は再見積もり。

- 有効期限: 提示から **30日** `[仮]`
- 確定見積もりの提示タイミング: **設計完了時**に `../02_設計/70_見積・WBS.md` で提示
- 再見積もり条件: 要件定義スコープの変更、技術スタック（DEC-D01/B03）やモデルtier（DEC-D02）の変更時
