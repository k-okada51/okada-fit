# ドキュメント構成ツリー（AI請負開発 設計ドキュメント標準）

> 統一開発フローの **要件定義の型（要件4層: 森→機能→非機能→木）** と **設計6段（基本→インフラ→データ・IF→機能→詳細→テスト）＋見積・WBS** に整合させた、設計ドキュメントの標準構造。**書く順序はフォルダ採番順、承認は要件定義3PR＋設計4PRに束ねる**（各層READMEの「承認ゲート」参照）。
> **フォルダ・ファイルは `NN_` で採番**（＝上から順に書けばよい）。**新設・改番時は 10 刻み（`10_,20_,30_…`）を標準**とし、間に差し込む余地を残す（連番だと挿入で参照が玉突きになるため）。**参照は番号位置ではなくファイル名・ID（FEAT-/EXT-/SCR-等）で**行う。既存の `01_,02_` は当面据え置き、触れた領域から都度 10 刻みへ寄せる。
> **2つの最大要件**:
> - **① 人間がパッと見てシステム・ビジネスの仕組みが分かる** → `00 概要 → 01 要件`
> - **② AIがデータ構造・モデル・他システム連携を理解しAI駆動開発できる** → `02 設計` ＋ 共通Claudeプラグイン（規約）
>
> **今回スコープ = 要件定義・（簡易）設計（00〜02）**。実装/テスト実行/リリース/運用等は将来フェーズ（`_backlog/`）。

### 承認ゲート（PRの束ね方）
書く順序（採番順）は上表のとおり、**承認は要件定義3PR＋設計4PR**に束ねる。束ねたPR内は層/段の順にコミットを積む。詳細は `01_要件定義/README.md`・`02_設計/README.md` の「承認ゲート」。

| PR | 含むもの | ゲート |
|---|---|---|
| 要件PR1 全体像 | `00_プロジェクト概要/`＋層1 | 方向性の合意 |
| 要件PR2 機能要件 | 層2（簡単なモック含む） | 何を作るかの確定＋モック人間承認 |
| 要件PR3 非機能＋大タスク＋概算 | 層3＋層4＋概算見積もり | **要件定義完了＝顧客合意** |
| 設計PR1 基盤アーキ | 段1＋段2 | 技術骨格の確定 |
| 設計PR2 データ・IF | 段3 | **IF契約フリーズ**（以降は系統別に並行可） |
| 設計PR3 機能設計 | 段4 | 振る舞い確定＋**動くモックUX承認** |
| 設計PR4 実装設計 | 段5＋段6＋見積・WBS | **実装着手ゲート**（設計着手チェックリスト充足＝TDD開始Go） |

## 大規模時の展開規約（BC・機能のスケール）
テンプレの器で足りない大規模案件（subscbase級のDDD戦術設計・多機能）は、次の規約で**多ファイル展開してよい**。**判定単位はフォルダ/FEAT**（個々のクラスは列挙しない → `00_プロジェクト概要/04_適用マトリクス.md` の「完全性判定の単位」）。

- **G1 ドメイン（BC）展開**: `02_設計/30_データ・IF設計/` 配下に **1 BC = 1 サブフォルダ**を作る。各BCの**必須構成**＝ `マクロ設計.md` ／ `データモデル.md`（集約・ACL） ／ `Domain_Event.md`。必要に応じ `Application/`・`Domain/` にクラス別ファイルを追加（**クラスは完全性の判定対象外**）。**小規模はBC分割せず `01_データモデル.md` 1枚**でよい。
- **G2 機能展開**: `01_要件定義/02_機能要件/01_機能一覧/` に **1機能 = 1概要ファイル**（`{FEAT-ID}_{名}.md`）を展開する。**小規模は数FEATを1ファイルに集約**してよい。受入基準等の詳細は `02_設計/60_テスト設計/` に FEAT番号で紐づける。
- **G3 トピックのフォルダ化**: 1つの `NN_トピック.md` が**複数ドキュメントに育つ**とき（例: `03_外部連携IF` に kintone/FAX/… 複数連携先）、**`NN_トピック/` フォルダ**へ昇格し、`README.md`（索引＋共通）＋子ファイル（`10_,20_…` で採番）に分ける。参照はフォルダ/IDで行う。**単一のままなら1ファイルで据え置き**（1〜2ファイルの深い階層を無闇に作らない）。**画面（`02_画面/`）は規約のみ採番・成果物は無番号**（画面名・SCR-ID順）。
- 展開したユニット（BC名・必須FEAT-ID）は **`04_適用マトリクス.md` の完全性マニフェスト（YAML）に宣言**し、**GitHub Actions が充足を監査**する（仕様＝`_backlog/09_開発プロセス/完全性監査CI_仕様.md`）。

## 設計思想
- **NN_採番＝書く順序**: 上から順に埋めれば、上流合意→下流の流れになる。
- **リスクファースト**: `01_全体像/` で 制約・前提・リスク・未決を先に晒し、設計（02）へ渡す。
- **要件＝何を作るか／テスト設計＝どう検証するか**: 機能要件は俯瞰＋概要（FEAT番号）、**受入基準・状態・エラー母集合（RED源泉）は `02_設計/60_テスト設計/` に集約**。TDDのREDはそこから書く。
- **概念→実装の縦串**: `02_設計/30_データ・IF設計/01_データモデル`（概念・集約・ACL）⇄ `02_設計/50_詳細設計/`（物理ERD/DDL）。
- **正本は1つ・他は参照**: 外部連携の"要件"=`01_要件定義/02_機能要件/00_機能要件インデックス`、"設計"=`02_設計/10_システム基本設計/04_外部連携`。
- **Claude設定・規約は共通プラグイン**: 各リポの `.claude/settings.json` で共通プラグイン（aic-harness）を有効化し、**規約・エージェント憲法・共通スキルはプラグイン側**で共通利用（ローカルに rules/agents は置かない）。**CLAUDE.md は残す**——プラグインが持てない「このPJ固有の索引」を担うため（薄く）。
- **必須/任意は2点で統制**: 入口＝`00_プロジェクト概要/04_適用マトリクス.md` で「作る文書」を宣言、出口＝リリース承認基準のドキュメントゲートで充足を照合。**該当なしは理由必須**。
