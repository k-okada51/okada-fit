# ADR-0008: トレーニング記録は実施有無のみを持つ

> **目的**: 1つの設計決定を記録する雛形（1決定＝1ファイル）。本ファイルをコピーし `NNNN-短い決定名.md`（NNNN＝DEC番号のゼロ埋め）で起票する。

## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: FEAT-04（トレーニング記録）・REQ-03・FEAT-05（ダッシュボード）。
- 要件定義の FEAT-04 概要は「トレーニング記録（回数・重量・メニュー）」と記述されている。
- しかし**本機能の目的は、ジムに行ったか・その日に何をやったかの記録**である。
- 詳細設計の作成過程で、この記述が実態と合っていないことが判明した。
- 物理設計の `training_session_details`（DM-08）は `is_done boolean` のみを持つ（`01_DB物理設計.md §2.3`）。
- FEAT-04 の RPC も `is_done` しか受け取らない。
- **前提**: 個人利用。負荷の推移を追う機能は本PJの範囲に含まない。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | 実施有無のみを持つ。要件の記述を実態に合わせる | 機能の目的と一致する。入力が1タップで済む | 要件定義の文言（FEAT-04 概要・REQ-03）を直す必要がある |
| B | `reps`・`weight_kg` 列を足し、要件の記述どおりにする | 負荷の推移を追える | 目的に無い機能が増える。入力の手間で記録が続かなくなる |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **A** を採用する。**実施有無のみを持つ。列は追加しない。**

| 項目 | 内容 |
|---|---|
| 保持する列 | `training_session_details.is_done boolean not null default false` |
| 追加しない列 | `reps`（回数）・`weight_kg`（重量） |
| 記録する種目 | `training_session_details.menu_id`（実施種目）はこれまでどおり保持する |
| 入力操作 | 実施した種目にチェックを入れる。数値入力欄は画面に置かない（FEAT-04） |
| 集計 | FEAT-05 は実施有無だけを数える。回数・重量の集計は行わない |

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

- 機能の目的は「実施したかどうか」の可視化にある。ヒートマップと継続の把握がそれにあたる。
- 回数や重量は、この目的に含まれない。
- 岡田さんの確認（2026-08-08）で、**もともと回数・重量は持たない想定**だったことが確認された。
- 案Bを却下した理由: 目的に無い入力を増やすと、1回あたりの記録の手間が上がる。
- 案Bは将来も採れる。列追加は後方互換で、既存データは失われない。
