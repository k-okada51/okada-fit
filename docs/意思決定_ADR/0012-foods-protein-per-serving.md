## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: FEAT-09（タンパク質残量と不足分提示・RULE-005）・FEAT-10（食事マスタCSVインポート）・DM-09。
- `foods.protein_amount` は「タンパク質量(g)」としか定義されていない（`01_DB物理設計.md §1.5`）。
- **1食分あたり／100gあたり／1個あたりのどれかが未定だった。**
- RULE-005 は残量との差が小さい順に候補を並べる。単位が決まらないと比較が成立しない。
- 同じ数値が別の意味で混在すると、提示の意味が壊れる。
- FEAT-10 は §4-2 で「1食分あたり」を `[仮]` として先に進めていた。
- **前提**: `foods` の CSV は `name` と `protein_amount` の2列のみ。分量の列は無い。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | 1食分あたりの g 数 | 残量と直接比較できる。換算が要らない | 「1食分」の量を作成者が決める。基準がぶれる |
| B | 100gあたりの g 数 | 栄養成分表の値をそのまま引き写せる | 「何g食べればよいか」の計算が要る |
| C | 1個・1本あたりの g 数 | 個数で数える食品には合う | ご飯・肉など個数で数えない食品を表せない |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **A** を採用する。`foods.protein_amount` は **1食分あたりのタンパク質量(g)** とする。

| 項目 | 内容 |
|---|---|
| 単位 | g |
| 基準 | 1食分（その食品を1回食べる量） |
| 採らない基準 | 100gあたり・1個あたり |
| 分量の列 | 追加しない。`name` と `protein_amount` の2列のまま |
| 提示の意味 | 「これを食べれば X g 取れる」（RULE-005） |
| 比較の相手 | 当日の残量 `remaining_g`。換算を挟まない |

- 例: 「ゆで卵」なら1個分、「納豆」なら1パック分の g 数を入れる。
- 候補の並び順（FEAT-09 §4.1 L4）はこの前提で意味を持つ。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

**採用理由**

- 提示の形が「これを食べれば補える」であるため、換算を挟まずに済む。
- 残量が 20g のとき、20g に近い行をそのまま選べる。計算が要らない。
- 分量の列を持たないので、テーブルと CSV の列数が増えない。

**却下理由**

| 案 | 却下理由 |
|---|---|
| B（100gあたり） | 「何g食べればよいか」の計算を利用者に強いる |
| B（100gあたり） | 量り売りでない食品（納豆1パック・ゆで卵1個）に当てはめにくい |
| C（1個あたり） | ご飯・肉など個数で数えない食品を表せない。対象が狭い |

- 換算は分量の列を足せばできる。ただし個人利用に見合う複雑さではない。
