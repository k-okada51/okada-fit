## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

詳細設計の敵対的検証で、可用性とコスト防御に関する 🔴 が4件挙がった。

| # | 論点 | 出どころ |
|---|---|---|
| 1 | 単一プロバイダ依存 | FEAT-03 #6・`10_GeminiAPI連携.md` #2 |
| 2 | AI提案の幻覚 | FEAT-03 #3 |
| 3 | レート制限の置き場所 | FEAT-03 #4・FEAT-08 #11 |
| 4 | 入力検証の層 | FEAT-06 #8 |

- 4件はいずれも同じ形をしている。**守りを厚くするか、構成を簡素に保つか**のトレードオフである。
- 個別に決めると判断がばらつく。まとめて1本の方針として決める。

**対象要件**

| 種別 | ID |
|---|---|
| 機能 | FEAT-03・FEAT-06・FEAT-08 |
| 外部連携 | EXT-01（Gemini API） |
| 非機能 | NFR-SEC-01・NFR-SEC-05・NFR-AVAIL-05・NFR-SCALE-01・NFR-MAINT-01 |

**前提**

- 利用者は**1人**。マルチテナントは適用外（NFR-SCALE-01）。
- 用途は**日次の記録**。リアルタイム性も業務継続性も求めない。
- 保守は**個人**で行う（NFR-MAINT-01）。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A | 守りを厚くする | 障害・悪用・誤入力に強い | 構成が増え、個人保守の対象が増える |
| A | 内訳＝二重化・カウンタテーブル・DB制約の強化・幻覚の事後フィルタ | 要件の文言をそのまま満たせる | 想定コスト（月$1前後）に対し基盤が過大 |
| **B（採用）** | 最小限にとどめる | 構成が簡素。保守対象が増えない | 障害時は止まる。キー漏洩は防げない |
| B | 4件すべてで簡素な側を採る | 実装が早い | 要件（NFR-SEC-05）との差分が残る |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **B** を採用する。**4件すべてで簡素な側を採る。**

| 論点 | 決定 |
|---|---|
| Gemini API の障害 | 縮退のみ。代替プロバイダもモデル切替も持たない |
| AI提案の幻覚 | 除外しない。提案は参考情報として利用者が判断する |
| レート制限 | 実装しない。UI の二重送信防止と Gemini の日次クォータに委ねる |
| 入力検証 | アプリ側のみ。DB の CHECK は強めない |

具体的に持たないものを次に挙げる。

| 持たないもの | 対象 |
|---|---|
| 代替プロバイダ・宣言的なモデル切替 | FEAT-03・FEAT-08 |
| 幻覚の事後フィルタ（提案の除外処理） | FEAT-03 |
| 呼び出し回数のカウンタテーブル・閾値 | FEAT-03・FEAT-08 |
| 範囲・桁を見る DB の CHECK 制約 | FEAT-06 |

- 入力検証の範囲（体重20.0〜300.0kg・目標0〜31）は**アプリ側で維持する**。
- DB の CHECK は `weight_kg > 0`・`target_training_count >= 0` のままとする。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

| 根拠 | 内容 |
|---|---|
| 利用者は1人 | マルチテナントは適用外（NFR-SCALE-01）。悪意ある入力・大量呼び出しの動機が無い |
| 用途は日次の記録 | 数時間の停止は撮り直しで吸収できる。業務が止まる性質の機能ではない |
| コストが小さい | 想定は月$1前後（1日3〜5回）。カウンタ基盤を持つ方が高くつく |
| 個人保守 | 守る仕組みを増やすと保守対象が増える（NFR-MAINT-01） |

**却下理由**

| 案 | 却下理由 |
|---|---|
| A（二重化） | 2つ目のプロバイダの精度検証・プロンプト調整が新たに要る |
| A（カウンタテーブル） | 守る対象（月$1前後）より基盤の維持コストが大きい |
| A（CHECK 強化） | 1人の利用者が自分のデータを壊すだけの事象に、移行を伴う制約を足すことになる |
| A（幻覚フィルタ） | 利用者は自分のジムの器具を知っている。人が読めば判別できる |

## 影響（Consequences）
> 📝 ここに決定がもたらす影響を記載。{反映先ドキュメントの該当箇所／関連テスト観点／前提が崩れた場合の再検討条件}

### 1. NFR-SEC-05 を掲げながら実装しない（🟡 中）

| 項目 | 内容 |
|---|---|
| 要件の記述 | レート制限を設ける |
| 実態 | 実装しない。UI の二重送信防止と Gemini の日次クォータに委ねる |
| 判断 | **要件側の見直しが要る。** 文言が実態と合っていない |

- ⚠️ 要確認（人間判断）: NFR-SEC-05 の適用範囲を、要件側で見直すこと。

### 2. APIキーが漏れた場合は防げない

- 呼び出し回数を数える仕組みが無い。異常な呼び出しを検知できない。
- **鍵の管理が唯一の防御になる。** キーは Edge Function の環境変数のみに置く（NFR-SEC-02）。
- 気づく手段は Google 側の請求・クォータ超過（`ERR-AI-QUOTA`）だけになる。

### 3. AI提案の信頼度は担保されない（🟡 中）

- 登録していない器具のメニューが提案されうる。除外しない。
- **利用者が毎回、自分の器具かどうかを判断する。** 提案は参考情報である。

### 4. 端末を改変すれば範囲外の値が入る（🟢 低）

- `validator` を通さずに `users` を更新すれば、300 kg 超の体重も保存される。
- ただし壊れるのは**自分のデータのみ**。他人への影響も課金への影響も無い。

### 5. AI が落ちると該当機能は止まる

- 復旧まで食事は記録できない（ADR-0015）。メニュー提案も出ない。
- トレーニング記録と閲覧は継続する。縮退の範囲は NFR-AVAIL-05 に従う。

### 6. 再検討の条件

- **マルチユーザー化（Phase2・NFR-SCALE-01）に進む場合、4件すべてを見直す必要がある。**
- 前提「利用者は1人」が崩れると、根拠が4件とも同時に失われるためである。
- ほかに、想定を大きく超える課金が実際に発生した場合も見直す。
