## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: NFR-AVAIL-02（RPO ≤24時間）・NFR-AVAIL-04（復元手順）・NFR-MIGR-03（切戻し）。
- 2026-08-08 に Supabase 無料枠の実仕様を公式の料金ページで確認した。**判明した事実は2つ。**

| 事実 | 帰結 |
|---|---|
| 自動バックアップが**含まれない** | 何もしなければ復元元が1つも無い |
| PITR（特定時点復元）が**利用できない** | 障害直前へは戻せない |

- **無料枠のままでは NFR-AVAIL-02 を満たせない。** 手段を決める必要があった。
- `04_移行設計.md §5.3` の切戻しは「バックアップからの復元」を最終手段に置いている。段階⑤（旧列の削除）は down では戻せず、復元元が無ければ詰む。
- **制約**: ADR-0016 でコスト最小を方針としている。利用者は岡田さん1人。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | **手元 Mac の launchd で日次自動エクスポート** | RPO 24時間で **NFR-AVAIL-02 を満たす**。手作業ゼロ。追加費用ゼロ | Mac が落ちている期間は取得されない。**保管先が手元の1箇所** |
| B | マイグレーション適用前のみ手動で取得 | 手順が最小。スキーマ変更の失敗からは戻せる | **日々の記録データが守られない**。RPO 不定 |
| C | 手動で週1回 | 習慣化すれば運用は軽い | RPO 最大7日。**実行忘れがそのまま単一障害点** |
| D | Supabase 有料プランに上げる | マネージドの日次自動バックアップ。手元の運用が不要 | 月額費用が発生する。ADR-0016（コスト最小）と再調整が要る |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **A** を採用する。**手元 Mac の launchd で日次自動エクスポートを取る。**

| 項目 | 値 |
|---|---|
| 手段 | `supabase db dump`（Supabase CLI） |
| 前提 | **Docker Desktop**。`supabase db dump` は Docker を要求する |
| 頻度 | **日次**（1日1回） |
| 実行元 | 岡田さんの Mac。launchd の定時ジョブ |
| 実行者 | 自動。人手を介さない |
| 接続 | `--db-url "$(cat supabase/.db-url)"` を明示する |
| 保管先 | ローカル。任意でクラウド同期フォルダに置く |
| RPO | **24時間**（NFR-AVAIL-02 を満たす） |
| RTO | 数時間（NFR-AVAIL-03・変更なし） |

- 接続は**プーラー**（`aws-0-ap-northeast-1.pooler.supabase.com:5432`）を使う。この回線は IPv6 非対応で直接接続が通らない。
- `supabase link` は CLI の不具合で通らないため、`--db-url` を毎回明示する。
- **実行ログを残す。** 失敗や未実行に気づけないと、復元元が無いことに障害時まで気づけない。

### 本番システムのバッチではない

**`02_バッチ設計.md` の「定期実行バッチは0本」という結論は変わらない。**

| 観点 | 本エクスポート |
|---|---|
| 実行場所 | 岡田さんの Mac。**デプロイされるシステムの外** |
| 実装物 | アプリにも Edge Function にも DB にも無い |
| 基盤 | pg_cron でも Scheduled Edge Function でもない |
| 位置づけ | **運用手順**。設計上のバッチではない |

- したがって pg_cron の利用可否（`02_バッチ設計.md §1.4` の `[仮]`）とは無関係である。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

- **要件を満たす最小の手段である。** RPO 24時間を追加費用ゼロで達成できる。
- **Docker Desktop は既に他の用途で使っている。** `04_移行設計.md §3` のリハーサル（`supabase start` でのローカル up→down→up）は 2026-08-08 に実証済み。バックアップのために新たな前提を増やすわけではない。
- **人手を挟まない点が効く。** 案C（手動・週1）の弱点は頻度ではなく実行忘れである。自動化はそこを構造的に消す。

**却下理由**

| 案 | 却下理由 |
|---|---|
| B | 守れるのはスキーマ変更の失敗だけ。日々のトレーニング記録・食事記録が対象外になる |
| C | RPO 7日は NFR-AVAIL-02 を満たさない。実行忘れが単一障害点として残る |
| D | 月額費用が発生する。個人利用の規模で、案Aが要件を満たせる以上は見合わない |

## 影響（Consequences）
> 📝 ここに決定がもたらす影響を記載。{反映先ドキュメントの該当箇所／関連テスト観点／前提が崩れた場合の再検討条件}

- **NFR-AVAIL-02（RPO ≤24時間）を満たせるようになる。** 移行設計 §6.2 #3 の 🔴 高が解消する。
- **Docker Desktop が実行環境の前提になる。** 無いと日次エクスポートもリハーサルも走らない。
- ⚠️ 要確認（人間判断）: **Mac が落ちている期間はエクスポートされない（🟡 中）。**
  - launchd は Mac の電源が入っている時しか走らない。長期不在では RPO 24時間が崩れる。
  - **実行ログを残し、最終取得日時を確認できるようにする。** 気づける仕組みが要る。
  - 確認の頻度・方法は運用開始後に定める。
- ⚠️ 要確認（人間判断）: **保管先が手元の1箇所である（🟡 中）。**
  - Mac の故障・紛失でバックアップも同時に失われる。
  - クラウド同期フォルダへ置くかを決める必要がある。ただし**エクスポートには食事・トレーニングの記録が入る**ため、同期先の扱いは NFR-SEC-06（必要以上に保存しない）と併せて判断する。
- 反映先:
  - `02_設計/20_インフラ設計/02_IaC・デプロイ・可用性配置.md §3`（バックアップ／復元・🔴 の解消）
  - `02_設計/50_詳細設計/04_移行設計.md §3.1・§5.3・§6.1・§6.2 #3`
  - `02_設計/50_詳細設計/02_バッチ設計.md §1`（バッチ0本の結論は不変である旨）
- 関連テスト観点: TC- は次の3点。
  - 日次ジョブが実際に走り、エクスポートファイルが生成されること
  - エクスポートから**復元できること**（取得しただけで復元未検証にしない）
  - 失敗時に実行ログへ記録が残ること
- 前提が崩れた場合の再検討条件:
  - 長期不在が常態化し RPO 24時間を維持できない場合 → 案D（有料プラン）を新ADRで再検討する
  - マルチユーザー化（NFR-SCALE-01 Phase2）で他人のデータを預かる場合 → 手元保管の妥当性を再検討する
