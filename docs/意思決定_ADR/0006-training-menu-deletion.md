## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: FEAT-01（器具登録＝ジム・種目・器具の登録と削除）・FEAT-04（トレーニング記録）。
- `training_session_details.menu_id` は `training_menus(id)` を NOT NULL FK で参照する（DM-04・DM-08）。
- 種目を消すと、過去の履歴が「何をやったか」を失う。
- **FK の `ON DELETE` 方針が全FKで未定だった**（`06_DB設計規約.md`・`01_DB物理設計.md §1.6` の未決#2）。
- 中間表 `machine_menus`（DM-10）の行が残りうる点も未決だった。
- **制約**: 監査列規約は論理削除を採らない（`06_DB設計規約.md §4`）。`deleted_at` は不採用。
- **前提**: 個人利用。記録を残し続けることが本PJの目的（FEAT-05）。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **a（採用）** | `ON DELETE NO ACTION`。履歴がある種目は削除できない | 列を足さずに履歴を守れる。DB が保証する | 種目名を間違えても消せない。画面で理由を伝える必要がある |
| b | 論理削除。`training_menus` に `deleted_at` を足す | 一覧から隠しつつ履歴を残せる | 監査列規約の「論理削除を採らない」に反する。全クエリに条件が増える |
| c | `ON DELETE CASCADE`。種目とともに明細を消す | 削除操作が常に成功する | **過去の履歴が消える。** 復旧できない |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **a** を採用する。**履歴がある種目は物理削除できない。**

### FK の `ON DELETE` 方針（正本は `01_DB物理設計.md`）

| FK | ON DELETE | 理由 |
|---|---|---|
| `users.id` → `auth.users(id)` | CASCADE | 退会で本人データを消す |
| `gym_visits.user_id` → `users` | CASCADE | 同上 |
| `training_menus.user_id` → `users` | CASCADE | 同上 |
| `training_sessions.user_id` → `users` | CASCADE | 同上 |
| `meal_logs.user_id` → `users` | CASCADE | 同上 |
| `training_session_details.session_id` → `training_sessions` | CASCADE | セッションを消せば明細も消える |
| `machine_menus.machine_id` → `training_machines` | CASCADE | 紐づけだけが消える。履歴に影響しない |
| `machine_menus.menu_id` → `training_menus` | CASCADE | 同上 |
| **`training_session_details.menu_id` → `training_menus`** | **NO ACTION** | **案a。履歴がある種目は削除できない** |
| `gym_visits.gym_id` → `gyms` | NO ACTION | 履歴を守る |
| `training_machines.gym_id` → `gyms` | NO ACTION | 器具が残るジムは消せない |

### 画面のふるまい（FEAT-01）

- 削除操作は試みてよい。DB が FK 違反を返したら、削除できない旨を画面に出す。
- 文言は「このメニューは記録に使われているため削除できません」相当 `[仮]`。
- エラーコードは FEAT-01 の `ERR-MACHINE-` 系に1件追加する `[仮]`。
- 履歴が無い種目は、これまでどおり削除できる。
- 種目を削除すると `machine_menus` の紐づけ行は CASCADE で消える。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

**案aを採る理由**

- 列を足さずに履歴を守れる。テーブル構成が変わらない（NFR-MAINT-01）。
- 判定を DB が行う。アプリ側の実装漏れで履歴が消えることが無い。
- 削除できない種目は、実際に記録に使った種目だけである。数は多くない。

**却下理由**

| 案 | 却下理由 |
|---|---|
| b | `deleted_at` は `06_DB設計規約.md §4` で不採用と決めている |
| b | 全クエリに `deleted_at IS NULL` が要る。付け忘れが表示バグになる |
| c | 過去の履歴が消える。記録を残す目的（FEAT-04・FEAT-05）に反する |

**`machine_menus` を CASCADE にする理由**

- 中間表が持つのは器具と種目の対応であり、履歴ではない。
- 紐づけが消えても、過去に何をやったかの記録は残る。
