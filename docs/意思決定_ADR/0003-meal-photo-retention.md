## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。

- **対象要件**: FEAT-08（食事撮影タンパク質計算）。EXT-01 経由で食事写真を外部（Vercel AI Gateway → Gemini）へ送信する。※経路は現在 **Edge Function → Gemini API 直接**（2026-08-08・ADR-0011。下記「補記」）。
- **決定が必要な理由**: DEC-D04 が `⚠️ 要確認` のまま、写真を保存するか・保持期間をどうするかが未定だった。ストレージ構成・プライバシー・NFR-SEC-06 の充足に直結するため確定が必要。
- **前提**: 送信そのものは FEAT-08 の成立に必須（ADR-0001）。個人利用・単一ユーザー。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | **保存せず、解析後に破棄** | 写真がサーバにもDBにも残らずプライバシーリスク最小。ストレージ不要で構成が単純・無料枠を消費しない | 写真の履歴を後から見返せない。再解析には撮り直しが必要 |
| B | ストレージに保存（保持期間を設定） | 履歴として見返せる。再解析が可能 | Supabase Storage等の構成が増える。保持期間の管理・削除処理が必要。漏洩時の影響範囲が拡大 |
| C | 端末内のみに保存 | サーバに送らずに済む場面がある | AI解析には結局送信が必要。ブラウザの永続化は容量・信頼性に難あり |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **A** を採用する。**食事写真は永続化しない。**

- **保存しないもの**: 食事写真そのもの（サーバ・DB・ストレージのいずれにも保存しない）
- **保存するもの**: AI解析の結果（カロリー・タンパク質・糖質・脂質、料理名、日時）のみをDBに記録する
- **ストレージ**: 食事写真用のオブジェクトストレージは**採用しない**
- **処理フロー（確定）**:
  ```
  📷 撮影（capture属性でカメラ直起動）
     → 🖼 プレビュー確認（ブラウザ内。この時点では未送信）
     → [解析する] 押下
     → 📤 サーバ(Route Handler)へ画像を送信
     → 🔒 AI Gatewayへ送信 → 栄養価を取得
     → 💾 栄養価をDBに保存
     → 📊 結果を表示 → 関数終了とともに画像はメモリごと破棄
  ```
- **自動送信はしない**: 撮影直後の自動アップロードは行わず、プレビュー確認後の明示操作で送信する（失敗写真によるAI従量課金の無駄を防ぐため）
- **⚠️ クライアント側リサイズを必須とする**: ストレージを経由せず画像をサーバへ直接送るため、サーバーレス関数のリクエストサイズ上限に抵触しうる。送信前に Canvas API で長辺1024px程度へリサイズ・圧縮する（PoC実測では480px相当でもAI認識に支障なし）。

> **補記（2026-08-08）: 上の処理フローは起票時のブラウザ前提であり、実装経路が変わった。**
> ADR-0010（Flutter アプリ）と ADR-0011（Gemini API 直接）による。
> **決定そのもの——写真を永続化しない・ストレージを採用しない——は変わらない。**

| 段階 | 起票時（2026-07-23・ブラウザ） | 現行（Flutter） |
|---|---|---|
| 撮影 | `capture` 属性でカメラ直起動 | `image_picker`（`ImageSource.camera`） |
| プレビュー | ブラウザ内 | アプリ内。**この時点では未送信**（変更なし） |
| リサイズ | Canvas API で長辺1024px | Flutter 側で長辺1024px |
| 送信先 | サーバ（Next.js Route Handler） | **Supabase Edge Function**（`analyze-meal`） |
| AI 経路 | Vercel AI Gateway → Gemini | **Gemini API 直接**（`inline_data`・ADR-0011） |
| 破棄 | 関数終了とともにメモリごと破棄 | 同左（変更なし） |

- **リサイズが必須である点も変わらない。** 画像は Edge Function へ直接 POST する。
- ただし **Supabase Edge Function のリクエストボディ上限は公式に記載が無い** `[仮]`。実装時に実測する。
- PoC 実測では長辺1024px で中央値 163 KB・最大 303 KB（base64 で約400 KB）。
- 正本は `../02_設計/50_詳細設計/08_機能別詳細設計/FEAT-08_食事撮影タンパク質計算.md`。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

- **プライバシーリスクの最小化**: 写真を保持しなければ、漏洩・不正アクセス時の影響が構造的に発生しない。NFR-SEC-06（必要以上に保存しない）を最も確実に満たす。
- **構成の単純化**: ストレージ、署名付きURL発行、保持期間管理、削除バッチのいずれも不要になり、個人開発の保守負担（NFR-MAINT-01）が下がる。無料枠のストレージ容量も消費しない。
- **サーバーレスとの整合**: サーバーレス関数は処理終了とともにメモリが解放されるため、**削除処理を実装せずとも構造的に写真が残らない**。実装漏れによる意図しない残存が起きない点で、案Bより安全。
- **案Bを却下した理由**: 「履歴を見返せる」価値はあるが、記録の本質はタンパク質量などの数値であり、写真自体を後から参照する要求は現時点でない。得られる価値に対して、構成の複雑さとプライバシーリスクの増加が見合わない。
- **案Cを却下した理由**: AI解析には結局送信が必要で、端末内保存だけでは要件を満たせない。
