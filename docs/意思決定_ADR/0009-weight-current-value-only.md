## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: FEAT-05（ダッシュボード）・FEAT-06（初期設定）・FEAT-07（必要タンパク質量算出）。
- `users.weight_kg`（DM-01）は現在値1点のみを持つ（`01_DB物理設計.md §1.1`）。
- タンパク質の目標は体重×2g で算出する（DEC-B06）。
- **過去日のダッシュボードも、当時ではなく現在の体重で目標値を計算する。**
- 体重を変えると、過去期間の達成率が遡って変わる。
- **前提**: 個人利用。体重の増減は緩やかで、過去の目標値との差は小さい。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A | 体重履歴テーブルを新設する | 当時の体重で目標値を出せる。推移も見られる | テーブルが11本目になる。集計に日付範囲の結合が1本増える |
| B | 日次スナップショットを持つ | 当時の値が確実に残る | 記録しない日の扱いが要る。行が毎日増える |
| **C（採用）** | 現在値のみで受容する | テーブルを増やさない。集計が単純なまま | **過去の達成率が遡って変わる。** UIでの説明が要る |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **C** を採用する。**体重は現在値1点のみを持つ。**

| 項目 | 内容 |
|---|---|
| 保持する列 | `users.weight_kg float NULL CHECK (weight_kg > 0)` のみ |
| 新設しないもの | 体重履歴テーブル・日次スナップショット |
| 目標値の算出 | 参照時点の `users.weight_kg` から毎回算出する（体重×2g・DEC-B06） |
| 過去日の扱い | 同じ計算を使う。当時の体重は復元しない |
| 提供しないもの | 体重の推移グラフ |

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

- 岡田さんの判断（2026-08-08）。
- テーブルを増やさず構成を保つ（NFR-MAINT-01）。個人開発の保守負担を上げない。
- 案A・案Bは、FEAT-05 と FEAT-07 の集計に日付範囲の結合を1本足す。
- 体重の増減は緩やかで、過去の目標値との差は小さい。得られる正確さが小さい。
- 案Aは将来も採れる。履歴テーブルの追加は既存データを壊さない。
