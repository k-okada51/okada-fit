## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **C** を採用する。**Google ログイン（OAuth）を使う。**

| 項目 | 内容 |
|---|---|
| 方式 | Supabase Auth の Google プロバイダ |
| Flutter の呼び出し | **`supabase.auth.signInWithIdToken(...)`**（ネイティブは公式がこちらを推奨） |
| ネイティブ側 | `google_sign_in` で ID トークンを取り、それを Supabase に渡す |
| ブラウザ | **開かない。** アプリ内で完結する |
| nonce | **両側に渡す。** 渡し方は非対称（下記「実装で判明したこと」） |
| 他の方式 | **持たない。** メール＋パスワードもメールリンクも実装しない |
| サインアウト | `supabase.auth.signOut()` |
| セッション | `supabase_flutter` が端末に保持し、期限前に自動更新する |

### `handle_new_user()` の `name` が確定する

**Google が `full_name` を返すため、`name` の既定値問題が解消する。**

| 項目 | 内容 |
|---|---|
| 現行の実装 | `COALESCE(NEW.raw_user_meta_data ->> 'name', '')` |
| Google が入れるキー | `full_name`・`name`・`email` など（プロバイダ依存） |
| **確定する読み方** | `COALESCE(raw_user_meta_data->>'full_name', raw_user_meta_data->>'name', raw_user_meta_data->>'email', '')` |

- 空文字のフォールバックは**残す**。`users.name` が `NOT NULL` のため。
- 表示名は FEAT-06 の初期設定で上書きできる。**Google の値は初期値にすぎない。**

### 必要な外部設定

**コードだけでは動かない。** 次の設定が要る。

| # | どこで | 何を |
|---|---|---|
| 1 | Google Cloud Console | OAuth 同意画面を構成する |
| 2 | 〃 | **iOS 用のクライアントID**を作る（Bundle ID: `jp.co.classlab.okadaFit`） |
| 3 | 〃 | **Web 用のクライアントID**を作る（Supabase がトークン交換に使う） |
| 4 | Supabase ダッシュボード | Authentication → Providers → Google を有効化 |
| 5 | 〃 | Web 用の Client ID / Client Secret を登録する |
| 6 | Flutter | `google_sign_in` パッケージを追加する |
| 7 | iOS | `Info.plist` に URL Scheme（逆順クライアントID）を追加する |
| 8 | Flutter | `crypto` を追加する（nonce のハッシュに使う） |

- **1〜5 は岡田さんの手作業**になる。コードでは行えない。
- 6〜7 は実装で行う。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

- **毎日使うアプリである。** 食事のたびに開くため、ログインの手間が積み上がる。ワンタップが効く。
- **パスワードを持たない。** 漏洩する対象がそもそも無い（NFR-SEC-01）。
- **`name` が自動で入る。** `handle_new_user()` の `[仮]` が同時に解けた。
- 案B（メールリンク）も Deep Link の設定が要る。**外部設定の手間は案C と大差ない**割に、ログインのたびメールを見る負担が残る。

**却下理由**

| 案 | 却下理由 |
|---|---|
| A | 実装は最も楽だが、毎日のログインでパスワード入力が発生する |
| B | Deep Link の設定コストは案Cと同程度。にもかかわらず利便性で劣る |

### 実装で判明したこと（2026-08-22 実機で確認）

**nonce を両側に渡す必要がある。** 渡さないとサインインが 400 で失敗する。

| 症状 | 内容 |
|---|---|
| 例外 | `AuthApiException: Passed nonce and nonce in id_token should either both exist or not.` |
| 原因 | `google_sign_in` 7.x が **ID トークンに nonce を埋め込む**。Supabase 側に渡さないと「片方だけある」と判定される |
| Supabase 側 | 監査ログが**0件**。リクエストが1件も届いていなかった |

**渡し方が非対称である。同じ値を渡すと通らない。**

| 渡す先 | 値 |
|---|---|
| Google（`initialize` の `nonce`） | **SHA-256 でハッシュした値** |
| Supabase（`signInWithIdToken` の `nonce`） | **ハッシュ前の生の値** |

- Supabase は受け取った生の値をハッシュし、ID トークン内の nonce と突き合わせる。
- **nonce は起動ごとに1つで足りる。** `authenticate()` は nonce を受け取らず、`initialize()` でしか渡せない。
- 目的は「このアプリの起動が要求したトークンか」の確認である。起動単位で固定されていれば足りる。
- 生成は `Random.secure()` を使う。`Random()` は予測可能で nonce の意味が消える。
