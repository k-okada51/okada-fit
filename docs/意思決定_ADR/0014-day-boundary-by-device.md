# ADR-0014: 「当日」は端末の時刻で判定する

## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: FEAT-05（ダッシュボード）・FEAT-08（食事記録）・FEAT-09（残量）・FEAT-04（トレーニング記録）。
- **「当日」の判定基準が未定義だった。** FEAT-05 §5.1 は案A／案B の二択のまま残っていた。
- Supabase の Postgres セッションは UTC で動く。
- サーバ時刻を素で使うと、**日本時間の朝9時までが前日扱い**になる。
- 前日扱いになると、当日の摂取量が 0 のままで残量が過大に出る。
- `eaten_date`・`performed_date` は TZ を持たない `date` 型（`06_DB設計規約.md`）。
- **記録側と集計側で基準が揃わないと整合しない。**
- **前提**: 個人利用。利用者は1人。旧構成にあったサーバ側の TZ 解決は無くなった。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | 端末の時刻で日付を決める | 利用者の体感と一致する。海外でも現地の日付になる | 端末の日付を変えると記録日がずれる |
| B | JST 固定（RPC 内で `AT TIME ZONE`） | 端末の設定に依存しない | 海外滞在時に現地の日付と食い違う |
| C | 起床基準（朝4時区切り等） | 夜更かし時の記録が同じ日に入る | 暦日とずれる。利用者への説明が要る |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **A** を採用する。**Flutter が端末のタイムゾーンで日付を決め、RPC に渡す。**

| 項目 | 内容 |
|---|---|
| 日付を決める場所 | Flutter（端末TZ）。Dart 側1箇所に集約する |
| 渡し方 | RPC の引数（`p_today` / `p_range_start` / `p_range_end` 等）で受け取る |
| RPC 内で使わないもの | **`CURRENT_DATE` / `now()::date`**（セッションTZが UTC のため） |
| 固定TZ | 持たない。`APP_TIMEZONE` 相当の設定値を置かない |
| 週・月の境界 | 端末TZの暦で決める。暦週（月曜〜日曜）・当月1日〜末日 |

**適用する3か所**

| # | 対象 | 機能 |
|---|---|---|
| 1 | `meal_logs.eaten_date` の採番 | FEAT-08 |
| 2 | 残量のリセット（当日集計の範囲） | FEAT-09 |
| 3 | ヒートマップと「今月」の範囲 | FEAT-05 |

- FEAT-04 の `performed_date` も同じ規則に従う。記録側と集計側で基準を揃える。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

**採用理由**

- 利用者の体感と一致する。日付が変わったと感じた時点で新しい日になる。
- 海外にいるときは現地の日付で区切られる。これが自然な区切りである。
- 日付の規則が Dart 側1箇所に集まる。RPC と Flutter の二重実装を避けられる。
- 記録側と集計側が同じ規則になる。`date` 型に TZ を持たせずに済む。

**却下理由**

| 案 | 却下理由 |
|---|---|
| B（JST 固定） | 海外滞在時に現地の日付とずれる。深夜・早朝の記録が別の日に入る |
| B（JST 固定） | 週・月の境界規則が RPC 側にも要る。Flutter 側と二重になる |
| C（起床基準） | 暦日とずれる。ヒートマップの1セルが何日を指すか説明が要る |

- **残課題（🟢 低）**: 端末時刻を信頼する。利用者が端末の日付を変えると記録日がずれる。
  - 個人利用のため実害は小さい。サーバ側で検知も補正もしない。
  - 単一ユーザー運用（NFR-SCALE-01 でマルチテナントは適用外）を前提とした割り切り。
- 関連テスト観点: TC-（端末TZ=JST の 00:30 に当日判定が前日にならないこと／RPC が `CURRENT_DATE` を参照しないこと）
- 前提が崩れた場合の再検討条件: 複数ユーザー化した場合。他人の端末時刻は信頼できない。
