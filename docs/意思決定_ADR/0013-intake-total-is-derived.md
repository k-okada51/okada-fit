## 背景・課題（Context）
> 📝 ここに何を・なぜ決める必要があるかを記載。関連する要件ID（FEAT/NFR/DM/IF/ST/ERR）を明記する。{決定が必要な理由／制約／前提}

- **対象要件**: FEAT-08（食事撮影タンパク質計算）・FEAT-09（残量と不足分）・FEAT-05（ダッシュボード）・DM-08。
- `meal_logs.intake_count`（摂取数）は**手書きER図に由来する列**で、そのまま残っていた。
- 業務的意味が定義されず、`01_データモデル.md §8-6` に未解決として残っていた。
- 解釈が2つあった。「何人前」なら `SUM(protein_g * intake_count)`、「便宜上の個数」なら掛けない。
- **画面ごとに解釈が割れると、同じ当日摂取量が違う値になる**（FEAT-05 の論点#9）。
- 確認の結果、当初の意図は「**その日の合計タンパク質量を持ちたい**」だった。
- **前提**: 個人利用。1日の食事記録は数件。RULE-002 の残量は当日合計から算出する。

## 選択肢（Options / Alternatives）
> 📝 ここに検討した案を記載（採用案・却下案の両方）。{案／概要／長所／短所}

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A | 列を残し、その日の合計を保持する | 集計せずに読める | 追加・削除・修正のたびに再計算が要る |
| B | 列を残し、栄養4項目に掛ける倍率とする | 「2人前」を1行で表せる | 元の意図と違う。全画面で乗算の有無を揃える必要がある |
| **C（採用）** | 列を削除し、合計は都度算出する | 常に正しい。解釈の論点が消える | 参照のたびに `SUM` が走る |

## 決定（Decision）
> 📝 ここに採用案と、具体値・方式を実装が迷わない粒度で記載。{採用案／確定した具体値・方式}

案 **C** を採用する。**`meal_logs.intake_count` を列ごと削除する。**

```sql
ALTER TABLE meal_logs DROP COLUMN intake_count;
```

| 項目 | 内容 |
|---|---|
| 削除する列 | `meal_logs.intake_count` |
| 日次合計 | `SUM(protein_g)`（当日分）。RULE-002 の既存設計のまま |
| 倍率 | 持たない。栄養4項目は撮影1回分の値 |
| 合計を保持する列 | 作らない。合計は**導出値**として扱う |
| 消滅する論点 | 「`SUM` に係数を掛けるか」 |
| 「2人前」の扱い | 2回に分けて記録する。1行に倍率は持たせない |

- `meal_logs` の列は7本になる（`id` / `user_id` / 栄養4項目 / `eaten_date` / `eaten_time`）。
- 当日の絞り込みは `ix_meal_logs_user_date` が効く。INDEX は7本のまま変わらない。

## 根拠（Rationale）
> 📝 ここになぜその案かを記載。トレードオフ・却下理由を明示する。{選定理由／却下した案の理由}

**採用理由**

- 合計は導出値である。列に持つと、記録の追加・削除・修正のたびに再計算が要る。
- 再計算を1か所でも漏らすと、列の値と実データがずれる。**ずれは静かに起きる。**
- `SUM(protein_g)` なら常に正しい。整合を保つ仕組みそのものが要らない。
- 個人利用の件数では速度も問題にならない。1日数件・期間絞り込みで足りる。
- 解釈の食い違い（FEAT-05 と FEAT-09 で乗算の有無が違う）が構造的に起きなくなる。

**却下理由**

| 案 | 却下理由 |
|---|---|
| A | 冗長な合計列は実データとずれる。ずれても誰も気づかない |
| A | 記録の削除・修正のたびに再計算の経路が要る。実装が増える |
| B | 元の意図（合計を持ちたい）と違う。倍率は求められていなかった |
| B | 全画面で乗算の有無を揃える負担だけが残る |
