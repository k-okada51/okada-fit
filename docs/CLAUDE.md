## ドキュメント生成ルール（template → docs）

案件ドキュメントを `template/` から起こす／記入するときは、次を厳守する。

- **テンプレの引用文は変更・削除しない**。テンプレ由来の引用（`> 📝` ガイド行、`> **目的/書き方/重複させない**` 等の blockquote、参照・引用行）は**そのまま保持**する。言い換え・要約・削除をしない。
- **埋めるのは値スロットだけ**。`（記入）`・`{...}` プレースホルダ・表のセル・Mermaid の骨組みだけを実データに置換する。
- **情報不足は警告で明示**。埋められない箇所を推測で確定させない。`> ⚠️ 要確認（人間判断）: …` を**追記**して人間の判断を促す。暫定値には `[仮]`（必要に応じ `DEC-xx`）を付す。
- **正本は1つ**。各文書の「正本」が別ファイルにある場合は値を複製せず参照（ID/リンク）にとどめる。

## 不備マーカー（GitHub Actions が検知する）

情報が足りない・未決定の箇所は勝手に埋めず、次のマーカーで明示する。CI（`docs-overview` 等）がこれらを拾い、**PRコメントにチェックボックス化**して人間が修正確認を管理する。

- `ファイルがない` … 標準ファイルが未作成（作成すべき文書の欠落）
- `（記入）` … 値スロットが未記入（テンプレの記入欄が残っている）
- `⚠️ 未提供` … 値の入力元（件数・単価・工数など）が提供されていない
- `⚠️ 要確認（人間判断）` … 人間の判断・確定が必要

CI は `⚠️` を後続語で区別せず、`⚠️` 単体で拾う（実データでは `未確定`・`未定`・`未確認` など後続語が一定しないため）。

暫定確定には `[仮]`（必要に応じ `DEC-xx`）を付す。**これは不備ではないので CI は検知しない**。`[仮]` のまま実装に進んでよいかの判断は `00_プロジェクト概要/05_設計着手チェックリスト.md` の責務。

## 段階的作成フローとフェーズゲート

- 作成順序は **概要 → 要件定義 → 基本設計 → 詳細設計**。上流フェーズが「不備なし」になってから下流に着手する。
- **下流フェーズの骨格が未作成でもエラーにしない**（警告にとどめる）。フェーズごとのPRで、CI が前段フェーズの完了をゲートする。
- 「ドキュメント一式を作成して」の依頼では、対象フェーズの**標準ファイルを全て作成**し、埋められない箇所は上記マーカーで残す（後から人間が解消）。勝手に「完成」にしない。
- **プロジェクト概要の一式が不備なし**になったら、要件定義→基本設計→詳細設計の作成に進むよう促す。

## 設計・実装の基本プロセス

設計判断やコード生成を伴うタスクでは、**必ず「生成」と「敵対的検証」の2フェーズ**を実行すること。片方だけで完了扱いにしない。

### フェーズ1：生成（Generation）
- 要件・上位設計を起点に、第一案をゼロから作る。
- 案は具体的に出す。DBならエンティティ・正規化・リレーション、画面なら画面一覧・遷移・情報構造、コードなら実装まで。
- この時点では「たたき台」であることを明示する。完成品として提示しない。

### フェーズ2：敵対的検証（Adversarial Review）
生成した案を、自分で敵対的にレビューする。最低限、次の観点で穴を洗い出す：
- **曖昧さ**：複数の解釈ができる箇所はどこか
- **矛盾**：ドキュメント内・層間で食い違う箇所はないか
- **考慮漏れ**：エッジケース、エラー時、境界条件、異常系
- **暗黙の前提**：明文化されていない仮定を明示化する
- **将来リスク**：後から変更コストが大きくなる設計判断はどれか（特にDBスキーマ）

検証結果は「指摘リスト」として提示し、重大なものは案に反映してから次に進む。

### 適用範囲と例外
- 対象：要件定義／基本設計／詳細設計／DB設計／画面設計／実装。
- 適用しなくてよい：単純な質問への回答、既存コードの説明、typo修正など、設計判断を含まない軽微な作業。
- **最終判断は人間が下す。** 特にDBスキーマと画面のUX/導線は、検証結果を材料として提示し、人間の承認を得てから確定する。勝手に「正」として先へ進めない。

# ドキュメント検査 CI（`.github/`）

ドキュメントは**人間が手動で PR を作る**。CI は「作られた PR をチェックする処理」だけを持つ。
**決定論・LLM 不使用**。rate limit も prompt injection も構造的に起きない。

詳しい設計と、チェックの追加手順は `.github/checks/README.md` を読むこと。

## 構成

検査は 2 系統。`docs/` 配下の変更を含む PR（`main` / `develop-docs` 宛て）で走る。

| 系統 | workflow | 単位 |
|---|---|---|
| フェーズ別チェック | `docs-overview` `docs-requirements` `docs-external-design` `docs-internal-design` | 触ったフェーズのフォルダだけ |
| 横断リンクチェック | `docs-links` | `docs/` 全体（フェーズに属さない） |

```
.github/
  workflows/
    _docs-check.yml       フェーズ別チェックの実体（再利用可能ワークフロー）
    docs-*.yml            各フェーズは「いつ動くか」と phase 名だけを持つ
    docs-links.yml        横断リンクチェック
  checks/
    run.mjs               フェーズ別チェックのエントリポイント
    cross-links.mjs       横断リンクチェック
    core/phases.mjs       ★ フェーズ定義（唯一の真実）
    common/               全フェーズで実行される *.check.mjs
    <phase-id>/           そのフェーズだけで実行される *.check.mjs
```

## ふるまい

- **対象フォルダにファイルが 1 つでもあるときだけ**検査する。無い／空ならスキップし、PR コメントも出さない（未着手のフェーズに検査を課さない）。
- チェックは `.github/checks/` に**ファイルを置くだけ**で実行される。workflow の編集は不要。
- PR コメントは**フェーズごとに 1 個**。不備は `- [ ]` のチェックボックスで掲示し、人間のチェック状態は再実行しても保持される。GitHub のコメントは作成順にしか並ばないため、順序は見出しの「フェーズ 2/4」で示す。

## マージをブロックするもの

段階的作成を前提とするため、既定は**警告**（チェックボックスで管理・マージは通る）。
赤くしてマージを止めるのは次の 2 つだけ。

- **前段フェーズ完了ゲート** … 前段に `（記入）` や `⚠️` が残ったまま下流フェーズの PR を出したとき。
  フェーズの順序は `core/phases.mjs` の配列順から自動導出される。
- **リンク切れ** … `docs/` 全体を対象に検査する。壊れた箇所は PR の差分上にインライン注釈で出る。

リンクだけを横断で見るのは、リンクが「リンク元」ではなく**「リンク先」の変更で壊れる**ため。
`01_要件定義/` のファイルを消すと `00_プロジェクト概要/` から張られたリンクが壊れるが、
フェーズ別 workflow は自分のフォルダしか走査しないので見逃す。

## ローカル実行

CI と同じものが手元で動く。PR を出す前に確認できる。

```bash
node .github/checks/run.mjs overview        # フェーズ別（引数はフェーズ id）
node .github/checks/cross-links.mjs         # 横断リンクチェック
DOCS_ROOT=example-suido-fax node .github/checks/run.mjs requirements
```

終了コード: `0` = 合格または警告のみ ／ `1` = 要修正あり ／ `2` = 使い方が誤り。
