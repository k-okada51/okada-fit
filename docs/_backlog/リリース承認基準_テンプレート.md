# リリース承認基準（開発KPI）— {プロジェクト名}

> **位置づけ**: リリース判定ゲート **G4** の合否根拠（テンプレート）。リリースは将来フェーズのため本リポでは `_backlog/` に保存。
> **監査観点の原則**（システム監査技術者視点）:
> 1. **客観的・測定可能** … 各基準は「閾値のあるKPI」で表す（主観・"なんとなくOK"を排除）。
> 2. **証跡（エビデンス）必須** … 合格の根拠となる成果物（レポート/ログ/記録）を紐付け保全する。
> 3. **トレーサブル** … 各KPIは 要件（REQ/FR/NFR）→ テスト（TC）へ追跡できる。
> 4. **職務分離・承認記録** … 判定者は実装者と分離。自己承認禁止。承認は記録に残す。
> 5. **二値判定** … MUST基準が**全てGreen**でのみリリース可。Redが1つでもあれば非リリース（または承認済みリスク受容の記録が必須）。

## 3. 承認・例外の扱い（監査要件）

- **承認記録**: 判定者・日付・対象バージョン・各判定を残し、変更不可の形で保全する（自己承認禁止）。
- **条件付きGo（例外）**: Redがある状態でのリリースは、**リスク受容の意思決定記録**（誰が・何を・なぜ受容・期限・緩和策）を必須とし、`01_要件定義/01_全体像/04_リスク分析` と紐付ける。口頭合意のみでのリリースは不可。
- **証跡の保全期間**: {契約/法規制に従い定義}。
